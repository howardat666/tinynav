# map→odom 与重定位：日志 bug、拟合滞后、三道新门限

> 2026-09-02。起因是现场两个症状：**箭头/目标慢慢跑偏**、以及**一次要手动重开 map_node
> 才恢复**。结论：主因是 `map->odom` 拟合**结构性地落后**，而不是重定位解不好；顺带发现
> 一个把我自己骗了好几轮的日志 bug。

## 1. 🔴 先修日志：报出来的 `map->odom yaw` 一直是噪声

`_ground_yaw_deg(T)` 的定义是「**相机光学位姿**的地面朝向」，取 `R[:, 2]`（相机 +z 朝前）。
但它被同时用来打 `map->odom` 这个**变换矩阵**的 yaw。对近似纯偏航的变换
`R[:,2] ≈ [0,0,1]`，`atan2(R[1,2], R[0,2])` 量的是**倾角轴的方位角** —— 倾角只有
0.2~2.6°，所以这个数是纯噪声、满量程 ±180° 乱跳。

🔑 **判据就在同一行里：`tilt` 越小，报出来的 `yaw` 越野。**

```
前 150 s   tilt 0.2~0.6°   yaw 报成 -177 → +171 → +39 → +131 → -8   （满量程乱跳）
后 250 s   tilt 1.7~2.6°   yaw 稳在 -130                            （倾角大反而稳）
```

倾角大反而稳，物理上不可能。已修：新增 `_transform_yaw_deg`，变换矩阵用
`atan2(R[1,0], R[0,0])`（绕世界 z）。相机位姿仍用旧函数，**两者不能混**。

**被它污染的旧结论全部作废**：「一次运行 map→odom 漂了 190°」「一拍跳 99°」
「解不跟着约束走」。修完之后同一份数据：段 1 相邻最大跳变 **3.9°**、段 2 **1.3°**。

**不改日志也能算真值**：`reloc pose` 和 `reloc odom` 是配对打印的同一时间戳，
两行的 `yaw_map` / `yaw_odom` 相减就是这一次观测蕴含的 map→odom 朝向。这条路径没有 bug。
⚠️ 但**不要**去二维重建整个变换 —— 那个重建和日志真值差 p50 128°、p90 167°。

## 2. 「跑偏」的机制：拟合天生落后 150 秒

`compute_transform_from_map_to_odom` 取 `relative_pose_constraint[-100:]`，权重只有内点率，
**没有时间衰减、没有鲁棒核**。0.65 关键帧/s 下 100 条 = **150 秒历史** —— 车开到地图另一头
时，150 秒前那一片蕴含的变换和现在这一片**等权**。

新加的日志字段 `recent5 resid` 直接把它量出来：

| | 全体残差 p50 | **最近 5 条残差 p90** |
|---|---|---|
| 要手动重开那段 | 5.8° | 🔴 **123°** |
| 重开之后（健康） | 5.5° | ✅ 16° |

🔑 **全体中位被历史稀释，只有最近几条能说明「解跟不跟得上现在这一片」。**
手动重开 map_node 就是在清这个缓冲 —— 这是现场那个现象的完整解释。

暂停之前那段离线复现等权拟合：`|拟合 − 最近5条中心|` p50 **6.0°** / p90 13.5° /
max **16.2°** → 在 3.8 m 的目标距离上就是 **1.08 m 横向误差**。

### 已加时间衰减 `TINYNAV_MAP_ODOM_HALF_LIFE_S`（默认 20 s，0=关）

回测（判据 = 解离最近 5 条约束的圆心多远；代价 = 解自己的相邻抖动）：

| 半衰期 | 段1 p90 | 段2 p90 | 相邻抖动 p50 |
|---|---|---|---|
| 不衰减（旧） | 🔴 138° | 15.6° | 0.5° |
| 60 s | 105° | 13.0° | 0.5° |
| 30 s | 29.8° | 11.2° | 0.6° |
| **20 s** | **10.0°** | **10.0°** | **0.6°** |
| 10 s | 4.4° | 7.7° | 0.5°（但 max 抖到 57°）|

⚠️ 这个判据有点自证（衰减就是让解跟着最近的走），**抖动那一列是独立的反向约束**。

## 3. 🔴 重锁通道在车停着时把好坐标系换成了差的

`_reloc_agrees_with_odom` 有一条恢复通道：连续 5 次被拒的解如果彼此一致，就认为是我们
锁错了地方，丢掉全部约束重锁。**它在车停着时触发了**：

```
reloc gate: 5 consecutive rejects agree on [-0.63,+0.57] -- re-locking there and dropping 92 constraints
```

代价：map 帧被搬走 **3.9 m**、朝向变约 **145°**。之后 250 秒 `clean=0/N`、`ratio_p50` 死在
0.33；重锁前是 `clean=45/91`、`ratio_p50=0.80`。**换掉的是好的那个。**
触发它的 5 个解内点率 0.31~0.35（门限就是 0.25，全是贴着门进的）、候选散布 2.89~3.16 m，
而整条 streak 里**里程计只动了 0.52 m**。

🔑 **恢复通道的前提是「有新证据」，车不动就没有新证据** —— 变的只是检索这次挑了哪个候选。

### 已加三道前置条件（任一不满足就不重锁，日志说明是哪条）

| 条件 | 环境变量 | 阈值 | 那次的实测值 |
|---|---|---|---|
| streak 内里程计位移 | `TINYNAV_RELOC_RELOCK_MIN_ODOM_M` | ≥ 1.0 m | **0.00 m** ❌ |
| 当前坐标系 clean 占比 | `TINYNAV_RELOC_RELOCK_MAX_CLEAN_FRAC` | ≤ 30% | **49%** ❌ |
| 触发解的候选散布 | `TINYNAV_RELOC_RELOCK_MAX_SPREAD_M` | ≤ 1.5 m | **2.89 m** ❌ |

三条各自都能拦住这一次。真锁错时车在动（0.25 m/s 下 5 个关键帧≈1.9 m），位移条件不挡它。

## 4. 高度门 `TINYNAV_RELOC_MAX_Z_DEV_M`（默认 0.30 m）

地面车的相机高度是常数，解不该比它**参考的关键帧**高/低太多。先量常态再定阈值 ——
209 个接受解 `|z解 − z参考帧|`：

```
p50 = 0.04    p90 = 0.07    p99 = 0.22    max = 0.66 m
|dz| > 0.30 的只有 2 个（1.0%）
```

其中一个 `z = +1.10 m`（相机离地只有 0.124 m，**物理上不可能**），而它**正好是「到达 POI」
判定前的最后一条约束**，把拟合朝向拉偏 11.5°。

⚠️ **判据必须是「和参考关键帧比」而不是「和全局中位比」**：全局 z 本身横跨 0.19~0.51 m。

实测新门限每段触发 3 次（0.38 m / 0.51 m 偏差），没有暴涨。

## 5. 已回退的两道门限，以及为什么

我曾加 `TINYNAV_MAP_ODOM_MIN_CONSTRAINTS` / `MIN_CLEAN_FRAC` 想在**引导阶段**挡住坏的
第一解。**买不到质量、只买到延迟**：第二次运行首次采信仍然 `clean=0/10 ratio_p50=0.34`、
解错 31°，而副作用是「UI 说已定位但地图上没箭头」的空窗第一次 27 秒、第二次 **67 秒**。
按用户要求（「重定位只要定上了就应该显示出来，不管对错」）**已全部回退**。

## 6. 还没解决的：地图有一片区域根本定不了位

```
时段(s)     成功率   失败时 landmarks 中位
  0-150      ~95%    -
150-180        5%    41
180-210        0%    39
210-240       10%    40
```

🔑 **landmarks 从 300~400 掉到 40** —— 不是 PnP 解不出来，是检索给的候选帧里能匹配上的
地图点只剩十分之一。那一片地图基本没有可用信息，只能**重新建图**补覆盖。
后果是那 80~150 秒纯靠轮速推算，「到达 POI」的判定也建在推算上。

## 🔴 2026-09-03：首解错 3.5 m + 重锁守卫 = 死锁（已修）

15:12 那趟 80 秒，`No POI found` × 44、`reloc rejected` × 25、`NOT re-locking` × 3，
最后只能人去重启 nav。

| | 会话1 首解（错） | 会话1 后续被拒的（对） | 会话2 首解（对） |
|---|---|---|---|
| `cam_map` | **[-3.76,+1.68]** | [-0.5,+0.2]~[-0.8,+0.2] | **[-0.23,+0.27]** |
| `cand_spread` | **2.48 m** | 0.17~0.62 m | 0.58 m |
| `ratio` | **0.27** | 0.47~0.62 | 0.42 |
| matches / landmarks / inliers | **30 / 75 / 31** | 39~58 / 105~144 / 53~84 | — |

🔑 **重启后的首解正是之前一直被拒的位置** —— 这是判定"谁错了"的决定性证据，
不需要任何外部真值。

**死锁闭环**：引导解错 → 地图帧错 → 拿不到目标 → 车不动 → 里程计 0.00 m →
`relock_min_odom_m=1.0` 永不满足 → 正确解永远换不上来。

### 两条修法

| 改动 | 环境变量 | 依据 |
|---|---|---|
| 只有**已被第二个解印证过**的锁才要求"新证据" | （`_reloc_accepted_n >= 2`，无开关） | 孤立引导解不配拿这个特权 |
| 引导解加唯一的质量门 `cand_spread <= 1.0` | `TINYNAV_RELOC_BOOTSTRAP_MAX_SPREAD_M` | 按真实数据回放：拒第1(2.48)第2(8.64)，第3个(0.41，位置正确)锁上，**代价 13.7 s** |

⚠️ 散布做**稳态**门限是坏的（>2.0 m 误伤 36% 好解，见 `first-relocalization-has-no-gate`）。
这里只用在引导那一次。全程 spread>1.0 的解占 14~15%，不算激进。

## 2026-09-03：移植上游 #178 + #225（全局路线不再挂在关键帧上）

### #178 —— 全局路线改由独立定时器驱动

**为什么**：`try_publish_nav_path` 原来在 `keyframe_callback` 里调，而关键帧实测只有
**0.64 Hz**（270 帧 / 419 s）—— 也就是**每 1.5 秒才更新一次 `/control/target_pose`**。
这正是记过的「target 跳变 = 关键帧饿死」。

| 改动 | 位置 |
|---|---|
| `self.latest_odom_pose` / `latest_odom_ns` | `continuous_odom_callback`（20 Hz） |
| `create_timer(TINYNAV_NAV_TARGET_PERIOD_S=0.5, nav_target_timer_callback)` | `__init__` |
| `try_publish_nav_path(timestamp, odom_pose=None)` | 传了就用最新里程计，不传退回关键帧那份（预热/离线工具） |
| 从 `keyframe_callback` 里摘掉那个 `with Timer("nav path")` 块 | — |

🔴 **必须配路径缓存，否则 2 Hz 要 16% 的核**：`try_publish_nav_path` 实测 73~94 ms，
其中 SDF 走廊搜索只占 10 ms，剩下是发布和日志。`_nav_replan_reason()` 三个触发条件
（无缓存 / POI 变了 / 偏离缓存路线 > `TINYNAV_NAV_REPLAN_DEVIATION_M=1.0`）之外用缓存，
但**前视点选择和到达判定每一拍都重算** —— 那才是 2 Hz 要买的东西。

顺带把三条早退日志加了 `throttle_duration_sec=2.0`（2 Hz 下会刷屏），删掉一个裸 `print`。

⚠️ 单线程执行器（`rclpy.spin`），所以定时器和关键帧回调互斥、没有竞态；代价是每 0.5 s
会把关键帧处理推迟最多约 70 ms。**验收要看关键帧率有没有掉、重定位 Hz 有没有掉。**

### #225 —— 卡在路线上时强制重规划（⚠️ 默认关）

只按「偏离缓存路线」重规划，永远拦不住**车停在路线【上】、前面是建图后才出现的障碍**
这一类：偏差是 0，所以永不触发。上游原话是 *"a deadlock that used to require manual
intervention"*。我们那趟 `route_clear < 0.172` 占 **47%**，正是这一类。

`_nav_stall_reason()`：沿缓存路线的**剩余弧长**在 `TINYNAV_NAV_STALL_TIMEOUT_S` 内没缩短
超过 `TINYNAV_NAV_STALL_EPS_M=0.05` 就重搜。用剩余弧长而不是位移 —— 车在障碍前摆头时
位移不小，但沿路线的进展是 0。`time.monotonic()` 不用 `time.time()`（板上无 RTC，对时会
让墙钟跳约 344 天）。

**默认 `TINYNAV_NAV_STALL_TIMEOUT_S=0` = 关。** 先单独验 #178，再打开这个，别混在一起。
上游用的是 8 s。

⚠️ **它是破死锁，不是根治**：占据图是静态的，重搜要靠**起点变了**才能出不同的路。
根治仍然是让 `map_node` 吃实时障碍。

### 离线自测（已过）

```
无缓存 -> "no cached path"        在路线上 -> None
偏离 1.5 m -> "deviated 1.50m"    POI 换了 -> "poi changed 1 -> 0"
stall 关 -> None                  stall 开且车不动 -> 1.2 s 时触发，随后重置基准
车持续前进（x 1.0->1.8）-> 全程 None
```
