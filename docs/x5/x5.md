## 1. 结论摘要

| 判断 | 结论 |
|---|---|
| 里程计可插拔性 | 🟢 下游只认 `/slam/odometry` 等话题，换轮速**不用改** `planning_node`/`map_node` |
| 重定位周期要求 | 🟢 **5 秒足够**（Jetson 版实测约 3 s/次）—— 详见 [`README.md`](README.md) |
| SuperPoint + LightGlue 在 X5 CPU | 🔴 **15.1 s/次**（top_k=3），极限优化后仍 3.9–5.8 s，全程吃满 CPU |
| ORB + BF-Hamming 在 X5 CPU | 🟢 **0.39 s/次，47 MB，1–2 核** |
| DINOv2-base 在 X5 CPU | 🔴 5.19 s / 峰值 816 MB（关 arena 504 MB）/ **实际触发过 OOM**，会拖挂固件 |
| BPU | 🟡 时间占用 87–95%；🔴 **无 depth 帧率参数**（sensor mode 最低 20 fps），"降到 5 fps 释放 5.5 TOPS" **做不到** |
| VIO | 🟡 运动时占 **2.11 核**；关掉可让空闲从 4.5 升到 6.6 核。🔴 但固件里**不存在 VIO 开关**，需 Looper 放开 |
| BPU 与内存的关系 | 🔴 **BPU 与 CPU 共用同一块 DDR，没有独立显存** —— 上 BPU 不省内存 |
| 内存优化 | 🟢 关 ORT arena：816 → **504 MB，延迟不变**，零代价 |
| LightGlue 的处置 | 🟢 **不要加速它，而是不用它** —— cv2 BF 匹配 38.6 ms 替代 2870 ms |
| 存储 | 🟢 64GB 版 `/userdata` **53 G（剩 44 G）**，双时段地图够用；🔴 但内存一分没多 |
| **白天检索** | 🟢 **所有路线都够用（86–96%）**。经典路线（ORB + 自训练 1 万词 DBoW3）R@1 **90.1%**，超过 main 现行 DINOv2 配置，零神经网络、检索层 **118 MB / 13.8 ms** |
| **夜间检索** | 🟡 **ORB 不行（最好 21.6%），但换局部特征能救一大半**：SuperPoint BoW **44.0%**、DINOv2 VLAD-64 **48.8%**。机理是 **ORB 特征点从 916 掉到 333 个/帧** —— 卡在提取不在检索 |
| **主导变量** | 🔑 **是描述子，不是检索算法**。同样 cv2 BoW：SuperPoint 夜间 44.0% vs ORB 9.9%（4.4 倍）。BoW/DBoW3 之选只影响速度和内存 |
| 最优落点 | 🟢 **白天/开灯场景上方案 1**（0.38 s + 118 MB）。若必须应对夜间，走 **DBoW3 + SuperPoint**（§ 13.2 ⑤，没人测过，理论上兼得 #210 的 recall 和本项目的速度）|

**核心矛盾与出路**：这颗芯片的 CPU 跑不动神经网络的局部特征匹配（SP+LG 要 15.1 s），而 BPU 被固件占着且帧率不可调。原本的出路是"只把最该上 BPU 的模型上 BPU（DINOv2），把最贵的模型整个删掉（LightGlue）"。

⭐ **2026-08-03 的实测调整了这个判断**：白天场景经典路线（ORB + 自训练 DBoW3）就够（90.1%，比 main 现行配置还高），**便宜一个数量级**（0.38 s vs 1.5 s，118 MB vs 480 MB）→ **第一版直接上方案 1，不用等 BPU。**

⚠️ **但不要过度解读成"经典全面胜出"**：
- 它超过的是 **main 当前的默认 VLAD 配置**，而 #210 的词典扫描显示**那个默认值（512 词）正落在崩溃区**。调好的 DINOv2（VLAD-64）夜间 48.8%，仍明显强于任何 ORB 方案。
- 白天真正最高的是 **SuperPoint BoW-128 的 96.0%**，不是经典路线。
- 所以准确的定位是：**方案 1 是"性价比最优的第一版"，不是"精度最优"。** 夜间需求一旦确认存在，就得把局部特征换成 SuperPoint。

### 2.2 🔴 64GB 机器的 MIPI 故障 —— 已定位为**软件问题**（lane 数不匹配）

> ⚠️ **本节推翻了早前"物理连接问题"的判断。** 早前依据是"I2C 正常但 D-PHY 起不来 + 冷启动/重启都复现"，
> 看似指向排线。深挖后发现是 **sensor 被写成 1 lane、而 CSI host 被配成 2 lane**，host 永远等不到 D1 进入 LP-11。

**症状**：`insight_full` 启动后立即 abort，systemd 重试 5 次后放弃（`Start request repeated too quickly`）：

```

signal: SIGABRT (6)   thread: insight_full
  insight_full::CreateAndRunVflow(...)              ← 崩溃点
  insight_full::HobotFullNode::initCameras(...)
```

```
vin sensor0: sc132gs open i2c4@0x32                   ← ✅ I2C 上能识别到传感器
vin mipi2: 2 lane 1088x1280 20fps datatype 0x2b       ← ⚠️ host 配成 2 lane
vin mipi2: ipiclk set 600000000 get 600000000         ← ✅ 时钟锁定正常
vin mipi2: lane state of host phy is error: 0x1000d   ← 🔴 D1 通道起不来

#### `0x1000d` 的确切含义

寄存器可读路径：`/sys/class/vps/mipi_host{0..3}/status/regs`（`debugfs` 下只有 `sif0-3/fps`，无 mipi 节点）。

`0x04c` = DW MIPI CSI-2 host 的 **`PHY_STOPSTATE`**：`bit16` = clock lane，`bits[3:0]` = data lane 0..3。

```
shutdownz=0x1  dphy_rstz=0x1  N_LANES=0x1(=2lane)  PHY_RX=0x10000  PHY_STOPSTATE=0x1000d
```

🔑 **所有错误计数器全为 0**（`phy_fatal`/`phy`/`pkt_fatal`/`crc_frm_fatal`/`pld_crc_fatal`/`ecc_corrected`/`data_id`/`line`/`ipi`）→ **D1 不是"信号质量差"，而是从来没被驱动过。**

**和正常机器（桌面 B）的逐寄存器对照** —— 这才是决定性的：

| 寄存器 | 正常 host2（左目）| 正常 host3（右目）| 正常 host0（RGB）| **64GB 故障** |
|---|---|---|---|---|
| `0x004` **N_LANES** | **0x1（=2 lane）** | 0x1 | 0x3（=4 lane）| **0x1（=2 lane）→ 完全相同** |
| `0x04c` **PHY_STOPSTATE** | **0xf** | **0x3** | 0xf | 🔴 **0x1000d → 不同** |
| `0x008` CSI2_RESETN | 0x1 | 0x1 | 0x1 | — |
| `0x048` PHY_RX | 0x30000 | 0x30000 | 0x30000 | — |
| `icnt` 全部错误计数 | 全 0 | 全 0 | 全 0 | 全 0 |
| `mipi_phy` 参数 | lane=2, mipiclk 1200 Mbps, settle=20, laneclk=575 Mbps, init_cnt=1, **reset_cnt=0** | 同 | — | — |

> ⚠️ **修正早前对 `0x1000d` 的解码。** `bit16` = clock lane 的 **stop state**（LP-11 空闲）标志，**置 1 表示时钟 lane 停着、没在跑 HS**：
> - 正常机 `0xf` → **bit16 = 0 → HS 时钟在跑** ✅（数据 lane 位在包间隙置 1 是正常的）
> - 64GB `0x1000d` → **bit16 = 1 → 时钟 lane 停在 LP-11 空闲**，且 **bit1 = 0 → D1 连有效 stop state 都没进**
>
> 所以早前写的"clk ✓ · D0 ✓ · D1 ✗"是**错的** —— 实际是**时钟 lane 根本没起来**。
>
> **两台的 CSI host 侧配置一模一样（`N_LANES=0x1` 就是 2 lane，不是故障点）**，差别全在 sensor 有没有按 2 lane 发数据 → **问题 100% 在 sensor 侧，与 host / 驱动 / dtb 无关。**

**两条容易带偏的干扰项**（正常机器上也有，不是故障标志）：
- `hobot-sif: WARNING: Reviced more hsync than expect, check configuration!` ×2（左右目各一条）—— 正常机器也报
- `host1 = not inited` —— 正常现象：4-lane 模式下 host0/host1 并成一组（`change group0 lane_mode to 1 for 4lane`），host1 不单独初始化

#### 根因：sensor 寄存器被写成 1 lane

在 PHY 起来的 3 s 窗口内用 `i2ctransfer` 活体读 sensor 寄存器：

```
样本11-13  shutdownz=0x0 stop=0xc      3018=0x72 3019=0x00 301f=0x00  ← 刚上 mclk，复位默认值
样本14-20  shutdownz=0x1 stop=0x1000d  3018=0x12 3019=0x0e 301f=0x45  ← 驱动写完寄存器表
```

SmartSens 约定：`0x3018[7:5] = lane_num - 1` → `0x12` = **1 lane**（`0x32` 才是 2 lane）；`0x3019` = lane 禁用掩码，`0x0e` = **禁用 D1/D2/D3**。两个寄存器互相印证。

而且 `0x301f`（setting/table ID）**在所有模式下都是 `0x45`** —— 1lane-30fps / 2lane-30fps / 2lane-60fps / 2lane-HDR 全一样 → **这个 sensor 库对所有模式只写同一张 1-lane 寄存器表。**

#### ⭐ 内存瓶颈可能不是硬件限制 —— 2.5 GiB 被 ion 预留了

⬤ 实测：**这颗 X5 的物理 DRAM 是 3.9 GiB，其中约 2.5 GiB 在启动时被 ion（媒体/BPU 缓冲池）静态预留**，剩下的才是 Linux 的 `MemTotal 1338644 kB ≈ 1307 MB`。

**这意味着"1307 MB 无 swap"不是芯片的物理上限，而是一个可调的分配决策。** 如果能把 ion 预留砍下来一部分（DT / bootargs 层面的改动），CPU 可用内存能多出几百 MB —— **这会直接改变所有方案的内存判断**：

| 若 ion 预留减少 | `MemTotal` | 影响 |
|---|---|---|
| 现状（~2.5 GiB ion）| 1307 MB / 可用 ~911 MB | 🔴 DINOv2 504 MB 就贴到上限；曾实际 OOM 并杀到固件的 `imu_pub` |
| ○ −512 MB | ○ ~1.8 GB / 可用 ~1.4 GB | 🟢 方案 6 的 480 MB 变得很宽裕 |
| ○ −1 GB | ○ ~2.3 GB / 可用 ~1.9 GB | 🟢 内存不再是约束，方案选择完全由用时决定 |

⚠️ **代价与风险（未验证）**：ion 池是相机流水线（VPF 缓冲、ISP、深度推理、BPU 张量）在用的。砍太多会让固件申请缓冲失败 —— 表现可能就是各种 `CreateAndRunVflow` 类的启动失败。所以这件事**必须 Looper 那边评估，不能自己硬改**。

> 🔴 **这应该加进 LooperHub 索取清单，而且优先级很高** —— 内存是全项目最硬的约束，而这是唯一一个能从根上放宽它的手段。相比之下"关 VIO"只省 2 个 CPU 核、"depth 降帧率"只释放 BPU，都不解决内存。
> 要问清的具体问题：① 当前 ion 预留 ~2.5 GiB 的依据是什么、实际水位多少 ② 能否降到 1.5–2 GiB ③ 有没有运行时可查的 ion 使用量（这样能实测水位而不是猜）。

### 2.4 CPU 算力基准（自造 onnx 模型实测，6 线程）

为判断"fp16 是否是瓶颈"专门造了对比模型：

| 算子 | fp16 | fp32 | 结论 |
|---|---|---|---|
| Conv | ⬤ **654 ms** | ⬤ 1631 ms | 🟢 **fp16 快 2.5 倍** —— A55 有 ARMv8.2 FP16 硬件支持 |
| GEMM | ⬤ 181 ms | ⬤ **126 ms** | fp32 快 1.4 倍（仅 attention 类算子有小幅收益）|

> **结论：fp16 不是瓶颈，不要浪费时间转 fp32。** 这条推翻了早期假设。

## 4. BPU 分析

### 4.1 占用与帧率

⬤ `hrut_somstatus` 显示 BPU `ratio` 在固件运行时稳定 **87–95%**（早期读到 100 是瞬时值）。这是**时间占用率**，不等于算力利用率 —— 其中含大量内存等待，所以"BPU 有水分"的判断是对的。

🔴 **但帧率降不下来**（⬤ 实测）：

- `ros2 param dump /insight_full` **没有任何帧率参数**（只有 `perception_engine: depth`、`enable_hand: false`、`stereo_sensor_name: sc132gs-1088x1280-20fps-2lane`）
- 可用 sensor mode 只有 **20 / 30 / 40 / 50 / 60 fps**，最低就是 20
- 所以 **"depth 降到 5 fps 释放 5.5 TOPS" 这条路堵住了**，除非 Looper 改固件

⚠️ 板上另有一个更小的深度模型 `DStereoV2.5_int16_544_448.bin`（当前用 `DStereo.bin`）。**未替换 —— 动固件文件需要授权。**

### 4.2 🟢 BPU **能**被第二个进程使用（2026-07-31 实测 —— 方案 6 的一票否决项已解除）

**结论：固件在跑（BPU ratio 87–96%）的时候，第二个进程可以完整拿到 BPU context 并持续成功推理，零失败，且对固件没有可测量的吞吐影响。**

做法：板上没有编译器，但 **`/usr/include/dnn/` 下有完整官方头文件**（`hb_dnn.h`、`hb_sys.h`），所以结构体布局是照头文件抄的、不是猜的。ctypes 直调 `/usr/lib/libdnn.so`（hbDNN `1.23.10_(3.15.54 HBRT)`，BPU Platform 1.3.6）。

⚠️ **坑**：`libdnn.so` 依赖 `libcnn_intf.so.1` / `libhbmem.so.1` / `libalog.so.1`，都在 `/usr/hobot/lib` → **`LD_LIBRARY_PATH=/usr/hobot/lib` 是 ctypes dlopen 的必需条件**（不只 `hrut_*` 需要）。

用固件自带的现成 `.bin`（没自己编）：`palm_det_192_192.bin`（1.9 MB）· `yolo11n_pose_bayese_640x640_nv12.bin`（3.7 MB）· `DStereo.bin`（13.3 MB）。

#### a) 能否拿到 context —— ⬤ 能

```

hbDNNGetModelHandle      rc=0
hbDNNInfer               rc=0
hbDNNWaitTaskDone        rc=0   latency=32.36ms
output[0] first16: [99,100,25,192,187,200,235,63,...]   ← 真实非零数据

#### b) 延迟是双峰，不是抖动

| 模型 | mean | p50 | p95 | **min（抢到空隙）** | 快路占比 |
|---|---|---|---|---|---|
| palm_det 192² | 40.1 ms | 70.6 ms | 74.9 ms | ⬤ **5.4 ms** | 49% |
| yolo11n 640² | 58.3 ms | 75.0 ms | 78.2 ms | ⬤ **9.7 ms** | 27% |
| stereonet 544×448 | 181.4 ms | 209.1 ms | 211.2 ms | ⬤ 139.2 ms | **0%** |

**p95 只比 p50 高 6%，但 p50 比 min 高 13 倍** → 关键不是抖动，而是**二值化排队**：任务要么撞上固件 FC 的空隙（~5–10 ms），要么整整等一个固件 FC 结束（~70–77 ms）。`hrut_bpuprofile -b 0 -t` 的 FC 交织记录直接可见（`0:790` = 固件，`0:3603` = 第二进程）：

```

752  35:15224  0:3603  0  1202278 1202346  67901us   ← 排在固件后面，跟着一起结束
758  37:15227  0:3603  0  1202424 1202427   2287us   ← 抢到空隙，纯 BPU 计算只 2.3ms

由此分离出**纯 BPU 计算时间**：palm_det ⬤ **2.3 ms** · yolo11n@640 ⬤ **5.6 ms** · stereonet@544×448 ⬤ **139 ms**。第二进程实测吞吐 ⬤ **18–21 FC/s**。

|---|---|---|---|
| baseline（仅固件）| 12.8 FC/s | 80.5 / 81.9 ms | 74.2–76.2 ms |
| 跑 palm_det 循环时 | **13.0 FC/s** | 84.7 ms | 77.7 ms |
| 跑 yolo11n 640 循环时 | **12.5 FC/s** | 83.0 ms | 75.1 ms |

FC 速率变化 **±2%（采样噪声内）**，FC 耗时 +1.3~5%。其他指标全程不动：`insight_full` CPU **176% → 176–179%**、RSS **223524 KB 恒定**、线程数 **61 恒定**；BPU ratio 无系统性变化；`dmesg` 里 BPU 相关 error/timeout/fail **0 条**；PID 全程 790，**没重启**。

#### d) 🟢 顺带发现：BPU 路线的内存代价比 CPU 路线便宜一个量级

| 进程内容 | 峰值 RSS |
|---|---|
| python + libdnn + palm_det（1.9 MB 模型）| ⬤ **24.5 MB** |
| python + libdnn + yolo11n 640（3.7 MB）| ⬤ **28.0 MB** |
| python + libdnn + stereonet（13.3 MB）| ⬤ **46.7 MB** |
| *（对照）onnxruntime 跑 SuperPoint* | *⬤ 130–148 MB* |

经验公式约为 **20 MB 基座 + 模型文件大小 × ~2**。在 1307 MB 无 swap 的机器上这条非常关键 —— 印证了 § 5.2 里"hbDNN int8 约 150–200 MB"的估算。

#### e) ○ 对 DINOv2 的外推（推断，非实测）

以 yolo11n@640（约 13 GOPs → 实测 5.6 ms 纯 BPU）为锚点，DINOv2 int8 的 22.9 GOPs 线性外推约 10 ms；考虑 ViT 在 Bayes-e 上的映射效率通常明显差于 CNN，给 2–3× 惩罚 → ○ **~20–30 ms 纯 BPU**。叠上排队规律（p50 基本由"等一个固件 FC"决定、且对模型大小不敏感）→ **端到端 wall 延迟预计 ○ 75–110 ms，吞吐 ~10 Hz 量级**。

🔴 **前提：纯计算时间必须 < 固件 FC 周期（~78 ms）。** `stereonet` 那个 139 ms 的例子说明一旦超过就完全吃不到空隙、延迟直接翻倍到 209 ms。**所以 DINOv2 编出来后第一件事是量它的纯 BPU 时间，看有没有守住 ~70 ms 这条线。**

### 4.3 算子构成 —— 三个模型能否上 BPU

用 `onnx` 读取模型图统计算子分布（这是**代码事实 + 分析判断**，最终需 OpenExplorer 编译验证）：

| 模型 | 节点数 | 算子种类 | BPU 友好算子 | **BPU 不友好算子** |
|---|---|---|---|---|
| **SuperPoint** | 237 | 31 | Conv×12、MaxPool×8、Relu×10 | **GridSample×1**、TopK×1、ScatterND×4、Where×9、Range×12、ConstantOfShape×7、Mod×1 |
| **LightGlue** | 1598 | **43** | MatMul×96 | **Einsum×36**、**IsInf×40**、**IsNaN×20**、Where×80、And×44、Greater×21、Less×20、ArgMax×2、GatherElements×1 |
| **DINOv2-base** | 951 | **23** | MatMul×96、Softmax×12、ReduceMean×50、Erf×12、Conv×1 | Where×1（几乎没有控制流）|

| 模型 | 判断 | 理由 |
|---|---|---|
| **DINOv2** | 🟢 **算子最干净** | 23 种算子、标准 ViT、无 Einsum、无数值检查、几乎无控制流。三个里最适合上 BPU |
| **SuperPoint** | 🟡 **可切图部署** | backbone（Conv/MaxPool/Relu）上 BPU，后处理（TopK / GridSample / ScatterND / NMS）留 CPU。计算量绝大部分在 backbone，收益大，但后处理的 CPU 耗时未知，需拆分实测 |
| **LightGlue** | 🔴 **风险最高** | 36 个 Einsum + 60 个 IsInf/IsNaN + 大量 Where/And 掩码逻辑，典型的 BPU 不支持算子。即使能编译也会被切成很多段，BPU↔CPU 来回拷贝可能让性能倒退 |

⚠️ **判断能否上 BPU 的标准不是内存**（BPU 与 CPU 共用同一块 1307 MB DDR，没有独立显存），而是：① 算子能否被 `hb_mapper` 编译 ② 子图切分程度 ③ Bayes-e 主跑 int8，需量化+校准 ④ DDR 总量装得下（和 CPU 推理同一个约束）。

### 4.4 释放算力值多少

| 情景 | 重定位延迟 | 收益 |
|---|---|---|
| 现状（全 CPU，top_k=3 串行）| ⬤ 15.1 s | — |
| 只有 SuperPoint backbone 上 BPU（**仍用 LightGlue**）| ○ ~14.3 s | 🔴 **改善 5%，无意义**（LightGlue 那 8.6 s 没动）|
| 只有 DINOv2 上 BPU（**仍用 LightGlue**）| ○ ~10 s | 🔴 无意义，同上 |
| **DINOv2 上 BPU + LightGlue 换 BF 匹配**（方案 6）| ○ **~1.5 s** | 🟢 **快 10 倍，且检索质量已知** |

> **早期结论"BPU 的价值 100% 取决于 LightGlue 能否上"已被推翻。** 正确的结论是：**不要试图加速 LightGlue，而是不用它** —— cv2 BF 匹配 38.6 ms 就能替代它的 2870 ms（§ 5.5）。删掉 LightGlue 之后，BPU 的价值转移到 DINOv2 身上，而 DINOv2 恰恰是三个模型里最容易上 BPU 的。**这是整份文档最关键的一次判断修正。**

#### SuperPoint 线程扩展曲线 —— ⬤ **4 线程饱和**（2026-07-31 实测）

⚠️ **先纠正输入规格**（写 ORT 推理代码的人必看）：`sess.get_inputs()` 实测

```
IN image              [1, 1, 'height', 'width']  tensor(uint8)   ← uint8，不是 fp16！

模型名里的 `fp16` 指**权重**精度，输入是 **uint8**。漏掉 `keypoint_threshold` 会直接 `ValueError: Required inputs (['keypoint_threshold']) are missing`。

测试条件：`inter_op=1` · 关 arena 和 mem_pattern · 2 warmup + 5 计时 · **每档独立进程**（否则 `ru_maxrss` 单调累积拿不到分档峰值）· `keypoint_threshold=0.005` · **固件全程在跑（占 ~1.8 核）→ 真实共存环境**

| 线程数 | mean (ms) | p95 (ms) | 相对 1t 加速比 | 峰值 RSS |
|---:|---:|---:|---:|---:|
| 1 | 3902.4 | 4018.3 | 1.00× | 131.6 MB |
| 2 | 2031.4 | 2062.3 | 1.92× | 147.7 MB |

| 8 | 1125.6 | 1165.2 | 3.47× | 148.7 MB |

- 1→2→3 几乎线性（效率 96% / 97%）
- **4 线程后进入平台期**：4/5/6/8 全落在 1071–1150 ms（±4%，就是噪声），5t 和 8t 甚至比 4t 略差
- 比 LightGlue 晚一档饱和（LG 是 3 线程），但平台期高度类似
- **峰值 RSS 126–149 MB，与线程数无关** → 内存不是这里的约束变量

🔑 **对"关不关 VIO"的直接含义：收益比外推的小得多。**
原来的预算基于"6 线程 = 1010 ms"，实测 6 线程 = 1071 ms（基线是对的）；但**4 线程就已经拿到 3.52×**，把可用核从 4.5 提到 8 **几乎白给** —— SuperPoint 在这个分辨率上根本用不掉 4 核以上。
**关 VIO 腾出来的核不会让 SuperPoint 变快，只会让你能并行跑别的东西**（比如同时跑 BPU 路线的 CPU 侧前后处理）。**收益要从"并发度"而不是"单模型延迟"上算。**

### 5.2 DINOv2 内存四档 —— 换运行时 ≫ 换精度

```
arena=ON   load=195MB  peak=816MB  lat=5271ms
arena=OFF  load=185MB  peak=504MB  lat=5237ms   ← 省 312MB，延迟不变
```

设 `sess_options.enable_cpu_mem_arena=False` + `enable_mem_pattern=False` 即可。这两个开关是 ORT 的"用内存换速度"优化（arena 预申请大块内存且**不归还系统**；mem_pattern 预分配峰值大小的连续块），**在内存紧张的嵌入式设备上应该关掉**。实测延迟几乎不变 —— **省 312 MB 是纯赚**。同样适用于 SuperPoint / LightGlue。

| 配置 | 权重 | 峰值 RSS | 省了什么 | 检索质量影响 |
|---|---|---|---|---|
| ORT fp16 + arena on（原状）| 195 MB | ⬤ **816 MB** | — | 基准 |
| **ORT fp16 + 关 arena** | 185 MB | ⬤ **504 MB** | −312 MB：arena 预留 | **无损** |
| ORT **int8** + 关 arena | ○ 98 MB | ○ **~420 MB** | 再 −84 MB：**只压权重，activation 一分没省** | 轻微下降 |
| **hbDNN int8 on BPU** | ○ 86 MB | ○ **~150–200 MB** | 再 −220 MB：**ORT 的 activation 膨胀整个消失** | 待验 |
| dinov2-**small** fp16 + 关 arena | ○ ~49 MB | ○ **~180 MB** | 延迟也降到 ○ ~1300 ms | 中等下降（几个百分点）|

> **关键区分**：504 MB 里只有 185 MB 是权重，另外 319 MB 是 ORT 的 activation + 中间张量。所以 **ORT 里 int8 最多省 84 MB**；真正的大跳是**换运行时**（ORT → hbDNN，缓冲编译期定死）。**"int8 降内存"这句话在 ORT 语境下几乎不成立，只有配合上 BPU 才兑现。**
> ⚠️ hbDNN 那一档是估算（权重 86 MB + ViT-B 257 tokens 的 activation 工作集 ~50 MB），编出 `.bin` 后必须实测复核。

**OOM 实录**：早期一次直接被 OOM killer 杀死 ——
```

Out of memory: Killed process 1477 (python3) total-vm:1656976kB, anon-rss:931176kB
```
⚠️ 触发 oom-killer 的是 `insight_full` 的 `imu_pub` 线程 —— **DINOv2 的内存压力已经威胁到相机固件本身**。

### 5.4 LightGlue 多实例并行

重定位里 top_k 次 LightGlue **无数据依赖**（都只依赖 query 特征 + 各自的参考帧），可以真并行（ORT `run()` 释放 GIL）：

```
SuperPoint(query) ─┬─→ LightGlue(query, ref1) ─┐
                   │   LightGlue(query, ref2) ─┼─→ 合并 → PnP
检索 top-k ────────┴─→ LightGlue(query, ref3) ─┘
      串行                这 3 个可并行
```

| 配置 | 串行 3 次 | **并行 3 次** | 加速比 |
|---|---|---|---|
| 每实例 1 线程（占 3 核）| ⬤ 18201 ms | ⬤ **6606 ms** | 2.76× |
| 每实例 2 线程（占 6 核）| ⬤ 12027 ms | ⬤ **5399 ms** | 2.23× |

**为什么并行 3 个 2 线程实例（5399 ms）比单个 2 线程实例（3875 ms）慢 1.39 倍？** 6 个工作线程超过了可用核数（运动时只有 4.5 核空闲），加上内存带宽和 cache 争抢 —— **并行不是免费的**。

### 5.5 ⭐ 用传统匹配替代 LightGlue

**LightGlue 既是 CPU 上最慢的（2870 ms，占总耗时 57%），又是最难上 BPU 的（Einsum×36 + IsInf/IsNaN×60）。那就不用它** —— 保留 SuperPoint 的强描述子，改用传统 BF 匹配。

实测 **512×256 float32** 描述子的匹配耗时（就是 SuperPoint 的输出规格）：

| 匹配方式 | 延迟 | 备注 |
|---|---|---|
| numpy 余弦 + mutual-NN | ⬤ 264.8 ms | numpy 用未优化 BLAS，慢 |
| numpy 余弦 + Lowe ratio | ⬤ 259.5 ms | 同上 |
| **cv2 BFMatcher L2 + crossCheck** | ⬤ **38.6 ms** | ✅ 推荐（更严格）|
| **cv2 knnMatch k=2 + ratio test** | ⬤ **20.6 ms** | ✅ 更快 |
| *（对照）LightGlue* | *⬤ 2870 ms* | **慢 74–140 倍** |

> ⚠️ 匹配**速度**已实测，但这个组合的**recall 完全没有数据** —— 见 § 10.4 的数据空白。

### 5.6 🟢 DBoW3 检索层的部署代价（2026-08-03 PC 实测）

方案 1 / 3 的全局检索层 = `pydbow3` + 预训练 `ORBvoc.txt`。之前这层挂着两个未知数（能不能装、要多少内存），现在都有数了。

#### a) `pydbow3` 装不上的问题已解决 —— 不是"能不能"，是"用哪份代码"

上游 [`foxis/pyDBoW3`](https://github.com/foxis/pyDBoW3) **编不过 OpenCV 4.x**：它自带的 numpy↔`cv::Mat` 转换层里的 `NumpyAllocator` 继承 `cv::MatAllocator`，而 OpenCV 4 给基类加了新的纯虚函数，于是

```
error: cannot declare variable 'g_numpyAllocator' to be of abstract type 'NumpyAllocator'
```

⚠️ 另有一个次要坑：它的 CMakeLists 找 Boost 组件 `python-py310`，Ubuntu 22.04 提供的名字却是 `python310`（无 `-py`）。

**解法：不修那个停更的转换层，直接写 ~70 行 pybind11 薄壳**。我们只需要传稠密 `(N,32) uint8` ORB 描述子，用不着通用 Mat 转换器。接口与 `models_trt.py::DBoW3Engine` 期望的 pyDBoW3 API 源码兼容（`Vocabulary.load` / `Database.setVocabulary` / `add` / `query`，`QueryResult.Id`、`.Score` 大小写两种拼法都给）。

> 🟢 **对上板的意义**：这个 shim 只依赖 pybind11 + DBoW3 + `opencv_core`，**没有任何与 OpenCV 版本耦合的遗留代码**，aarch64 上同样编译即可 —— T-1 从"未知风险"降级成"照着 Dockerfile 再编一遍"。

#### b) ⬤ ORBvoc 的内存与延迟实测

| 步骤 | 耗时 | 常驻 RSS |
|---|---|---|
| `ORBvoc.txt`（145 MB 文本）载入 | ⬤ 8.2 s | ⬤ 437 MB |
| `Database.setVocabulary()` 之后 | — | ⬤ **629 MB** ← DBoW3 **把整棵词典又拷了一份** |
| **`del voc` 之后**（Database 自持副本，功能不受影响）| — | ⬤ **475 MB** |
| **改存 DBoW3 二进制格式**（`voc.save()` → 49 MB 文件）再载入 | ⬤ **0.8 s** | 同上 |
| 单次 `query`（1000 desc 查 300 帧库）| ⬤ **2.6 ms** | — |

词典规模 **971814 词**（文件头 `10 6 0 0` = k=10 / L=6 / L1-norm / TF-IDF）。

**两个几乎白捡的优化，一起用**：
1. **`setVocabulary()` 后立刻 `del` 掉 Python 侧的 `Vocabulary`** → 省 **154 MB**（629→475）
2. **预先转成 DBoW3 二进制词典**（145 MB 文本 → 49 MB）→ 载入 **8.2 s → 0.8 s**，还省 96 MB 磁盘

🔴 **但 X5 上仍然很紧**：475 MB（检索层）+ 212 MB（`insight_full` RSS）= **687 MB / 943 MB available，且无 swap**，还没算 ORB 提取器（43 MB）、Python+ROS 开销和地图数据本身。

→ **这条路要走通，几乎肯定得换小词典**：1M 词是给"整座城市"设计的，办公室场景用 k=10/L=4（1 万词）或 L=5（10 万词）就够。

> ✅ **已验证，而且比预期好得多**：自训练小词典不但省内存（541 → **118–159 MB**），**recall 还更高**。详见 § 10.2 末尾。本节的 475 MB 只适用于"直接用预训练 ORBvoc"这一种做法，**不要再拿它当方案 1 的内存基准**。

## 6. 六个算法总表

重定位是**三层流水线**（全局检索 → 局部特征 → 匹配），每层都有「学习式」和「经典」两种选择。SuperPoint 分辨率统一 **320×272**，描述子规格统一 **512×256 float32**。

### 6.1 总表

| 层 | 算法 | 类型 | **CPU 用时** | **峰值 RSS** | **地图/帧** | **BPU 可行性** |
|---|---|---|---|---|---|---|
| **① 全局检索**<br>几千帧里选 top-k | DINOv2-base (CLS) | 学习 | ⬤ **5190 ms** | ⬤ 816 MB → **504 MB** | 3 KB | 🟢 **算子最干净** |
| | DINOv2 patch VLAD | 学习 | ○ >5190 ms | ○ >816 MB | ○ ~16 KB | 🟢 同上，输出改吐 patch tokens（786 KB）|
| | SuperPoint BoW | 经典 | ○ ~5 ms | ○ ~5 MB | 2 KB | 不需要（cv2+numpy）|
| | DBoW3 + ORBvoc | 经典 | ○ ~5 ms | ○ **145 MB**（词典常驻）| ○ 1.5 KB | 不需要 |
| **② 局部特征**<br>提关键点+描述子 | SuperPoint @320×272 | 学习 | ⬤ **1010 ms** | ⬤ 145 MB | ⬤ **528 KB** | 🟡 **可切图** |
| | ORB (nfeat=1024) | 经典 | ⬤ **46.5 ms** | ⬤ ~10 MB | ⬤ **39 KB** | 不能（非神经网络）|
| **③ 匹配**<br>每次配对 | LightGlue | 学习 | ⬤ **2870 ms** | ⬤ 169 MB | — | 🔴 **最难** |
| | BF-L2 + crossCheck（SP 描述子）| 经典 | ⬤ **38.6 ms** | ⬤ ~5 MB | — | 不需要 |
| | BF-L2 knn + ratio（SP 描述子）| 经典 | ⬤ **20.6 ms** | ⬤ ~5 MB | — | 不需要 |
| | BF-Hamming（ORB 描述子）| 经典 | ⬤ **26.0 ms** | ⬤ ~5 MB | — | 不需要 |

**三层共用的后处理**（与选哪个算法无关）：`findFundamentalMat` RANSAC ⬤ **87.1 ms** · `solvePnPRansac` ⬤ **2.6 ms**

### 6.2 recall 与用时的错位

> **影响 recall 最大的那层用时可以很小；用时最大的那层对 recall 只是中等影响。这个错位是所有优化的依据。**

| 层 | 作用 | **对 recall 的影响** | **对用时的影响** |
|---|---|---|---|
| **① 全局检索** | 决定 top-k 里有没有正确帧 | 🔴 **决定性 —— 第一道门**，没命中后面全白搭 | 🟢 极小（BoW 5 ms）<br>🔴 或极大（DINO 5.19 s，占 34%）|
| **② 局部特征** | 描述子质量决定能匹配上多少点 | 🟡 中等 | 🟡 中（SP 1010 ms / ORB 46 ms，**22 倍差**）|
| **③ 匹配** | **第二道门**：需 ≥50 匹配点、≥80 landmark、PnP inliers ≥50（`map_node.py`）| 🟡 中等 | 🔴 **最大（LG 8610 ms = 总耗时 57%）** |
| top_k | 第一道门的宽度 | 🔴 直接决定（R@1 88.87% → R@10 99.25%）| 🔴 匹配层的乘数（top_k=3 就是 ×3）|

由此得出三条优化逻辑：

1. **检索层要保质量，但它本不该贵** —— 唯一贵的是 DINOv2 走 CPU。挪到 BPU（int8）就同时拿到「质量已知」和「几乎不花时间」。
2. **匹配层是用时的绝对大头（57%），但对 recall 只是中等影响** → **这才是最该动刀的地方**。LightGlue → BF-L2：8610 → 116 ms（**省 98.6%**），描述子仍是 SuperPoint 的。
3. **局部特征是唯一真正的速度-精度权衡点**（SP 强得多但贵 22 倍）。建议先留 SP，把 1010 ms 当可接受成本。

## 8. 时延预算（5 秒）

**已确定的预算：5 秒/次。** 同事实测 Jetson 版 tinynav 约 **3 s/次**，轮速机器人可放宽到 5 s。

| 项 | 数值 |
|---|---|
| 轮速里程计平地漂移 | 1–2% 距离 |
| IMU gyro yaw 漂移（消费级 MEMS）| ~0.2–0.8 °/min |
| 5 秒 @ 0.3 m/s 行程 | 1.5 m |
| **→ 位置漂移** | ○ **~3–7 cm** |
| **→ yaw 漂移（轮速+陀螺）** | 🟢 ○ **<0.5°** → 横向 1.3 cm |
| **→ yaw 漂移（纯轮速，omni 轮）** | 🔴 ○ **1–3°** → 横向 2.6–7.8 cm |

> `planning_node` 栅格分辨率 **0.1 m**，所以纯轮速的横向偏差已接近一格，加陀螺才有安全余量。里程计三个变体的对比见 [`README.md`](README.md)。

| 方案 | 6 核（关 VIO）| **4.5 核（VIO 开着）** | 5 s 预算 |
|---|---|---|---|
| 0 现状 main 全 CPU | ⬤ 15.1 s | ○ ~20 s | 🔴 超 4 倍 |
| 1 ORB 全经典 | ⬤ 0.39 s | ⬤ **0.38 s** | ✅ **13× 余量** |
| 2 BoW+SP+**LG**（top_k=1）| ⬤ 4.5 s | ○ ~6 s | 🔴 超 |
| **5a BoW+SP+BF** | ⬤ 1.40 s | ⬤ **1.50 s** | ✅ **3.3× 余量** |
| **6 DINO@BPU+SP+BF** | ○ 1.49 s | ○ **1.58 s** | ✅ **3.2× 余量** |

**两条结论**：

1. **关 VIO 从「前置条件」降级为「优化项」** —— 方案 1/5a/6 在 4.5 核下都塞得进 5 s，**不用等 LooperHub 权限就能开工**；拿到权限只是把余量从 2.8× 提到 4×。
2. **5 s 预算独立地判死了 LightGlue** —— 唯一超预算的就是带 LG 的方案。这与「用 BF 替代 LG」的结论一致，但是一条独立的理由。

🟢 **4.5 核那列已从外推改为实测**（SuperPoint 线程曲线见 § 5.1）。三个候选方案的余量都比原先估的更好：**方案 1 有 13×、5a 有 3.3×、6 有 3.2×**。

🔑 **而且「关 VIO」的收益要重新理解**：SuperPoint **4 线程就饱和**（3.52×），把可用核从 4.5 提到 6.6 对单模型延迟几乎没帮助（1110 → 1071 ms，只快 3.5%）；ORB 更是完全不扩展（1 核和 8 核都是 38 ms）。**所以关 VIO 的价值不在「让重定位更快」，而在「能并行跑别的东西」** —— 比如 BPU 路线的 CPU 侧前后处理，或给 `planning_node` 留余量。
⚠️ **CPU 独占仍是真实约束，但已大幅缓解**：方案 5a 在 5 s 周期里只忙 1.8 s（占空比 36%），`planning_node`（需 ~1 核持续跑 10–30 Hz 的 raycasting + ESDF + 轨迹打分）有足够空间；而现状 main 的 15.1 s 会把规划饿死整个周期。
⚠️ `map_node` **必须加纯定位模式** —— 现在 `keyframe_callback`（`map_node.py:332`）每个关键帧无条件跑 `keyframe_mapping()`（写盘存 depth/image + 重算 DINO/SP + 全量 Ceres pose graph），额外 391.8 ms/帧且随地图增长。

**两个重要推论**：

**① SuperPoint：GPU 8.4 ms vs X5 CPU 1010 ms = 120 倍差距。** 这是"为 GPU 设计的算法直接搬到嵌入式 CPU"的代价。

**② 原版重定位频率不是 10 Hz，而是约 2.5 Hz。** 关键帧**生成**阈值是 3 cm / 1° / 3 秒（`looper_bridge_node.py:235`），按 0.3 m/s 理论上 10 Hz；但关键帧**处理**（`mapping_loop`）平均要 392 ms，实际上限约 **2.5 Hz**。而且 `pose_graph_trajectory_publish`（332 ms，发布 18459 个 pose 的完整 Path）和 `solve_pose_graph` 都随地图规模增长 —— **大地图上会退化到几秒一次**。

> 这条可优化：导航时没必要每个关键帧都发布完整轨迹 Path。**PR #172（junlinp，gate pose graph trajectory publishing）正是修这个的**，可直接借用。

**三条结论**：

1. 🔑 **主导变量是描述子，不是检索算法。** 同样用 cv2 BoW：**SuperPoint 夜间 44.0%，ORB 夜间只有 9.9%**（4.4 倍）。选 BoW 还是 DBoW3 只影响速度和内存，选 ORB 还是 SuperPoint 才决定 recall。
2. 🟢 **白天：所有路线都够用**（86–96%）。经典路线（ORB + 自训练 DBoW3）**90.1%** 已经超过 main 现行的 DINOv2 patch VLAD 配置，而且零神经网络、快 4 倍、省 2 倍内存。
3. 🟡 **夜间：ORB 不行，但不是"物理上不可能"。** ORB 系最好 21.6%；**SuperPoint BoW 44.0%、DINOv2 VLAD-64 48.8%，是 ORB 的 2–2.5 倍。** 夜间瓶颈是"ORB 提不出特征点"（见下），换更强的局部特征能救回相当一部分。

⚠️ **两个口径保留意见**：
- **PR #210 的变换仍是自拟合的**（每个后端用自己的 Top-1 拟合 SE(2)，即本节开头指出的循环论证）。缓解证据：他三种方法拟合出的 yaw 高度一致（day −0.69…−0.97°，night 17.46…18.25°），说明偏差不大。但要严格对齐，应该用本项目的 `--transform-json` 重跑他那条线。
- **⚠️ main 现在默认的 VLAD 词典大小是 512，落在崩溃区**（#210 扫到 256 时夜间已只剩 10.7%）。所以 § 10.1 那份历史数据（night 31.21%）很可能是**一个调坏了的配置**。这意味着"经典反超学习式"这个说法最大的水分来源就在这里 —— **正确的说法是"经典超过了 main 当前的默认配置"，不是"超过了调好的 DINOv2"**。

#### 🔑 夜间为什么崩：不是描述子变差，是**没东西可描述**

| | ORB 特征点/帧 mean | median | p10 | 零特征帧 |
|---|---|---|---|---|
| day 地图 | ⬤ **916** | 1021 | 603 | 0 |
| night 地图 | ⬤ **333** | 270 | ⬤ **114** | ⬤ **3** |

夜间每帧 ORB 特征点掉到白天的 **36%**，最差的 10% 帧只有 114 个点，还有 3 帧一个点都提不出来。地图文件直接体现：`features.dat` night **55 MB** vs day **149 MB**。

→ **失败发生在特征提取环节，不在检索环节。** 这与上表完全吻合：换检索算法（BoW→DBoW3）救不了夜间，但**换更强的局部特征能救回一大半**（SuperPoint BoW 44.0% vs ORB BoW 9.9%），因为 SuperPoint 在低照度下仍能提出足够多、且可重复的点。DINOv2 走另一条路 —— 它不看关键点、直接吃整幅图像，所以完全绕开了这个瓶颈。

⚠️ **仍待确认**：夜间即使用 SuperPoint 也只有 44–49%，离可用还差不少。**双时段地图**（夜晚查询匹配夜晚关键帧，退化为同条件检索）和 **#212 的感知混淆剪枝**（作者实测 night 有 3.3% 的问题关键帧、day 0%）是两条正交的补救手段，都还没实测。补光是最后手段。

#### ⭐ 词典规模扫描：**自训练小词典反超 1M 词的预训练 ORBvoc**

§ 5.6 提出"1M 词太吃内存，能不能换小词典"。扫了一遍 `bow-cv2`（在 `map_gt` 自己的描述子上训练 kmeans 词典），R@K 全部用共享变换、0.5 m 阈值：

|---|---|---|---|---|---|
| 256 词 | 自训练 | 81.4% | 95.2% | 11.5% | 27.5% |
| 512 词 | 自训练 | 82.6% | 95.3% | 9.9% | 29.0% |
| 2048 词 | 自训练 | 85.4% | 97.5% | 13.3% | 35.8% |
| **8192 词** | **自训练** | ⬤ **89.5%** | ⬤ **98.4%** | 19.5% | ⬤ **42.3%** |
| *（对照）**971814 词** ORBvoc* | *预训练* | *88.4%* | *98.2%* | *17.6%* | *38.1%* |
| *（对照）DINOv2 patch VLAD* | *预训练* | *88.87%* | *99.25%* | ***31.21%*** | *39.89%* |

🟢 **8192 词的自训练词典在 4 项里赢了 3 项**，包括**夜间 R@10 42.3% 是全场最高**（超过 DINOv2 的 39.89%）—— 词表小了 **119 倍**，效果反而更好。原因不难理解：ORBvoc 是在通用大规模数据上训的，而自训练词典和目标场景**同分布**。

🔴 **但 `bow-cv2` 这个实现不能直接上板**：它做的是**暴力最近质心**（每帧 ~1000 个描述子 × 8192 个质心逐个算距离），PC 上就要 **0.15 s/帧**，X5 上会到秒级 —— 而 DBoW3 的层次树是**对数级下降**，query 只要 2.6 ms。

→ **正解是训练一个小的 DBoW3 层次词典**，同时拿到三样东西：层次树的对数级检索、小内存、领域匹配的 recall。为此给 shim 补了 `Vocabulary(k, levels)` + `create()`，基准脚本加了 `--descriptor dbow3-trained`。

| **自训练 99023 词（L=5）** | 88.8% | 97.8% | ⬤ **21.6%** | ⬤ **44.4%** |
| *（对照）预训练 ORBvoc 971814 词* | *88.4%* | *98.2%* | *17.6%* | *38.1%* |

**部署侧代价**（另起进程加载已存词典，非训练时的峰值）：

| 词典 | 文件 | 加载 | **词典常驻** | +1150 帧库 | **总计** | query |
|---|---|---|---|---|---|---|
| **自训练 10000 词（L=4）** | 0.6 MB | ⬤ 0.00 s | ⬤ **0.1 MB** | 74.4 MB | ⬤ **118 MB** | ⬤ 13.8 ms |

- 想要**白天最好** → `k=10, L=4`（1 万词）：Day R@1 **90.1%，全场最高**，118 MB
- 想要**夜间最好** → `k=10, L=5`（10 万词）：Night R@10 **44.4%，全场最高**（超过 DINOv2 的 39.89%），159 MB

⚠️ **两个代价要记住**：
1. **词典变成地图的一部分**——必须和地图一起建、一起分发；换场景要重训（训练一次 ~70 s / 1123 帧，PC 上离线做，不占板上时间）。
2. **训练时峰值 656–672 MB**，这在 PC 上无所谓，但**别想在 X5 上训词典**。

## 13. 上游分支盘点

### 13.1 三层各有哪些算法，以及它们的真实耦合关系

先把概念分清 —— 重定位是三层流水线，**每层可以独立换算法**：

| 层 | 在干什么 | 候选算法 |
|---|---|---|
| **局部特征** | 找关键点 + 给每个点算描述子，一张图出 ~1000 个 | **ORB**（32 字节二进制）· **SuperPoint**（256 维 float，要跑网络）|
| **全局检索** | 把一张图变成**一个**向量，在几千张地图帧里捞 top-k | **BoW / DBoW3**（把那 1000 个局部描述子汇总成直方图）· **DINOv2 / SigLIP**（不看关键点，整幅图喂进网络）|
| **匹配** | 查询帧与候选帧的关键点两两配对 → PnP | **BF-Hamming / BF-L2** · **LightGlue** |

#### BoW 与 DBoW3 是同一思想的两种实现

两者都是「视觉词袋」：用描述子聚类出**词典**（每个聚类中心 = 一个视觉单词），把一张图的描述子各自归到最近的单词，数出**直方图**，TF-IDF 加权归一化，相似度取余弦。区别只在数据结构：

| | 词典结构 | 查一个描述子属于哪个词 | 天生适合 |
|---|---|---|---|
| **cv2.kmeans BoW** | 扁平，N 个中心 | **暴力**，与 N 个中心逐个比 | float 描述子 |
| **DBoW3** | **k 叉层次树**（k^L 词）| **对数级**逐层下降，只比 k×L 次 | 二进制描述子（float 也支持）|

这解释了 § 10.2 里的反差：8192 词的扁平 BoW 每帧 0.15 s，而 971814 词的 DBoW3 只要 3.0 ms —— **词多 100 倍反而快 50 倍，全靠树**。

#### ⚠️ 唯一的真约束：词典必须用你之后要查询的那种描述子训练

不能拿 ORB 训的词典去归类 SuperPoint 描述子（维度、度量、分布都不同）。**除此之外没有别的约束** —— 常见的两个误解都要纠正：

- **「DBoW3 必须配 ORB」是错的。** DBoW3 源码 `DescManip.cpp` 对 `CV_8U`（Hamming）和 `CV_32F`（L2）都有分支 → **DBoW3 + SuperPoint 完全可行**。只是**预训练的 `ORBvoc.txt` 是 ORB 专用**，换 SuperPoint 就得自己训词典（§ 10.2 已打通这条路）。
- **「BoW 必须配 SuperPoint」也是错的。** § 10.2 里的 `bow-cv2` 就是喂 ORB 的，跑得通，只是 recall 低。

#### 那为什么实践上总是"全局和局部用同一种"？—— 省算力，不是算法要求

**局部描述子只提取一次，两处复用**：

```
方案 1：  图 ──ORB(38ms)──→ 1000 个 ORB 描述子 ──┬─→ DBoW3 直方图 → 全局检索
                                                 └─→ BF-Hamming   → 局部匹配
          神经网络 0 个，特征只提一次

方案 5a： 图 ──SuperPoint(1010ms)──→ 1000 个 SP 描述子 ──┬─→ BoW 直方图 → 全局检索
                                                         └─→ BF-L2      → 局部匹配
          神经网络 1 个，特征只提一次

方案 6：  图 ──DINOv2(整幅图)──→ 1 个全局向量 ──────────────→ 全局检索
          图 ──SuperPoint──→ 1000 个 SP 描述子 ───────────────→ 局部匹配
          神经网络 2 个 ← DINOv2 不产生关键点，局部必须另跑一个网络

main：    DINOv2 patch VLAD + SuperPoint + LightGlue = 神经网络 3 个
```

🔑 **所以 BoW/DBoW3 的真正优势是"搭便车"**：局部匹配反正要算描述子，全局检索白拿（实测 DBoW3 query 4.8 ms）。而 DINOv2/SigLIP 是**另一个网络另跑一遍**，全局检索成本从"几毫秒"变成"一整次推理"。反过来「全局 DINOv2 + 局部 ORB」在算法上也成立，只是既然已付了一次 ViT 推理，局部再用弱的 ORB 不划算。
