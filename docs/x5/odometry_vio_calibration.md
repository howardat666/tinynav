# 轮速里程计标定到 VIO：方法、结果、三个坑

> 2026-09-01，圆盘底盘。目标**不是物理真值，而是和 VIO 一致** —— 规划器/地图/目标点全在
> VIO 的米制里（尺度来自出厂标定的 0.1002 m 立体基线），让轮子对齐 VIO 等于让整个栈自洽。
> 工具：`tool/x5_board/diffcar_calib_vio.py`（`spin` 用 VIO 当真值，`dist` 见下面的警告）。

## 1. 结果：距离和转角都到 ±0.6%

最终固件值：`WHEEL_CIRC = 0.2173`（**没动**）+ `ppr = 1536.4 / 1536.8`（`n` 命令改，不用重烧）
+ `WHEEL_BASE = 0.2035`，`CFG_REV` 全程没动。等效轮周长 = 0.2173 × 1468.6/1536.4 = **0.2077 m**
（等效轮径 66.1 mm）。

里程计小是对称圆自己抵消误差，**不代表更准**；52 mm 才是车真的没回到原点。

## 2. 🔴 拟合完的两个数在物理上讲不通，这是刻意的取舍

等效轮径 **66.1 mm** 比实测轮子（约 65）大 1.7%；有效轮距 **0.2035** 比物理轮距 207 mm
**小 1.7%** —— 而接地是面不是线、原地转有打滑，物理上有效轮距只能**更大**。这是 VIO
平移/旋转尺度不完全自洽的指纹（`diffcar_esp32/src/main.cpp:46` 记着上一次按 VIO 定绝对距离
偏了 5.9%）。

**但对这台车这是对的**：没有任何消费者需要物理米。⚠️ 哪天要物理真值：卷尺量 ≥2 m，
`k = 实测/里程计x`，然后 **`ppr × k` 和 `WHEEL_BASE × k` 必须同比例一起改**
（`main.cpp:44` 的耦合：`B_有效` 与 `C` 成正比）。

## 3. 三个坑

### 🔴 `Vio.path`（逐帧累加路径）不能当距离基准

VIO 约 100 Hz，亚毫米抖动累加 500 帧就能虚增约 10%。用它当基准会报出"里程计短 10%"这个
不存在的结论。**距离用弦长 `straight_m`；弧长由 `弦长 × θ / (2 sin(θ/2))` 还原。**
同一段左弧：累加路径给 0.898，弦长还原给 **1.004**（与转角的 1.003 一致）。

### 🔴 打滑跟转速有关，必须在最终会用到的转速下标，而且要迭代

固件按 `setTargets(v ∓ w·B/2)` 发轮速，所以 **B 假设值错 ⇒ 实际转速也错**：
`B=0.3234` 下发 `w=0.8` 实际转出 1.18 rad/s，量出轮距 0.2189；改到 0.2189 后重测
（真的 0.8 rad/s）变成 0.2130。**要迭代到 B 收敛**（第三轮残差 −0.3%，进入噪声）。

### 🔴 `/dev/ttyS3` 只能一个持有者 —— 这是第三次犯

板子重启后 `board-app` 自动起来，`diffcar_control` 以 19 Hz 发 `p`，和标定脚本双向对撞，
轮子跑出 0.537/1.410 的鬼数据（两股 `u` 指令交替）。**跑任何串口脚本前：**

```bash
systemctl stop board-app
bash /userdata/x5/tinynav/tool/x5_board/app_start.sh stop
pkill -f "[d]iffcar_control.py"
# 验证：for p in /proc/[0-9]*; do ls -l $p/fd 2>/dev/null | grep -q ttyS3 && echo 还有人; done
```

## 4. 顺带量到的偏航偏置

**命令直行时车固定左偏 0.030 ~ 0.040 rad/m（1.9°/m），三次测量同号。** 里程计(0.0131) 和
VIO(0.0144) 一致 ⇒ 是真实物理偏航，不是测量误差。换算：

```
s_r − s_l = 0.0144 × 0.2035 = 2.93 mm  /  0.486 m 行程  =  0.60% 左右不对称
```

这也解释了左右弧线的距离比值差 4.4%（1.0281 vs 0.9842）。

**候选原因与判据**：电池偏左造成的载荷差算下来只有需要量的 1/20（10% 载荷差 → 约 0.03%
有效滚动半径差，需要 0.6%），所以**更可能是轮径制造差**（0.6% × 66 mm = 0.4 mm）。
**20 秒能判**：直行前进和后退各一次比较偏航符号 —— 同号 ⇒ 外力（脚轮侧向力/地面坡），
反号 ⇒ 几何不对称。

**建议先不动**：导航靠 VIO 闭环、每周期重规划，1.9°/m 不影响；纯航位推算 3 m 才偏 7 cm；
而且若根因是脚轮侧向力，改 `ppr` 不对称治不了它还会让里程计不自洽。想试是
`n 1536.4 1527.6` + `w`（右轮 ppr 降 0.6%），可回退。

## 5. 怎么复现

```bash
# 必须先释放串口，见第 3 节
python3 /userdata/x5/tinynav/tool/x5_board/diffcar_calib_vio.py spin 2   # 轮距，VIO 当真值 ✅
python3 /root/car/calib.py dist 2.0                                     # 轮周长，要卷尺 ⚠️
```
⚠️ `spin` 默认 5 圈 = 39 s 连续旋转，**改成 2 圈**：实测长时间快速原地旋转会让 VIO 丢跟踪
（21.6 s 那次位姿跳 0.97 m），而 2 圈的角度信号已经足够。

跑起来直接 `TypeError: 'NoneType' object is not subscriptable`。

同一个坑 `diffcar_spin_closure.py` 也踩了，**它已经改成 VIO 可选**（VIO 只是旁证，
真正的基准是图像闭合）。`diffcar_calib_vio.py` 没改 —— 它整套方法就建立在 VIO 上。

⚠️ 板上跑任何 ROS 脚本都要先 `. /userdata/x5/env.sh`，否则 `No module named rclpy`。

## 2. 用图像闭合替代 VIO：原理与实测

`tool/x5_board/diffcar_spin_closure.py`。**原地自转整整 360° 后相机回到完全相同的位姿，
所以那一帧和起始帧逐像素相同、视差恰好为零** —— 这是唯一一个不受近景视差污染的角度
基准，而且是物理事实，不依赖任何标定。

```
1. 0.5 rad/s 恒速原地自转（不用 0.15~0.30：地毯静摩擦主导，兑现率只有 57~81%）
2. 累计里程计自己报的角度，同时抓 infra1 帧
3. 多转 25°，从里程计 320° 开始记帧（窗口要覆盖标度 0.89~1.07）
4. 每帧算水平边缘剖面：取 120~420 行，abs(diff(band, axis=1)).sum(axis=0)
5. 和起始帧互相关，扫 ±60 px 取峰值，抛物线拟合到亚像素
6. 只留相关系数 > 0.60（离起点 90~180° 时画面是另一片景，自然低）
7. 位移过零那一刻就是真 360°，线性插值读出里程计当时报的角度
```

实测（2026-09-02，落地、有电 11.14~11.33 V）：

```
逆时针(左): 里程计 +364.42° / 真 360° = 1.0123
顺时针(右): 里程计 -372.64° / 真 360° = 1.0351
角度标度 = 1.0237      有效轮距 0.3234 × 1.0237 = 0.3311 m
```

## 3. 🔴 从导航日志反推的 7% 是高估，别用那个方法

我曾用「相邻两次重定位的 Δyaw_odom 和 Δyaw_map 各自积分成净转角再比」算出
**+6.6% / +7.6%**（R² 只有 0.20~0.68），而直接测只有 **+2.4%**。三个原因：

1. **基准自己有误差** —— `yaw_map` 是 PnP 出来的，且地图的位姿图不是全局一致的；
2. **基准不独立** —— 两者一起喂给同一个 `map->odom` 拟合，地图侧的系统性误差被算到里程计头上；
3. **运动方式不同** —— 转圈测纯原地自转，导航跑弧线，内外轮滑移完全不同。
   所以那 7% 里**可能有一部分是弧线特有的真实误差**，现有数据分不开。

对账：`2.4% × 260° 净转角 = 6.2°`，而实测地图帧漂移 25° → **里程计只能解释四分之一**，
剩下 19° 在地图侧或弧线滑移。

🔑 **教训：拿地图当基准反推里程计误差会高估。**

## 4. 左右不对称 2.3%，单改轮距修不掉

```
对称部分（均值）   = 1.0237  → 有效轮距 0.3234 → 0.3311 m
反对称部分（半差） = ±1.14%  → 左右轮标度不同
```

轮距误差**必然对称**，所以那 2.3% 的方向差只能来自左右轮的脉冲/圈或轮径。
⚠️ 而且它**不是轮速不匹配** —— `diffcar_kff_closedloop.py` 的注释里记着：左轮同 PWM
比右轮快 4.3%，但**闭环 PID 已经把两轮抹平**（悬空实测 6257 计数差 1 个）。
PID 拉平的是**计数**；如果一边 ppr 标错，等计数 ≠ 等距离 → **车在画弧而里程计以为在走直线**。

**不对称意味着直着开也会累积偏航**，对导航的影响比原地转大。

### 可验伪的预测（下一步该做的测量）

W = 0.3311 m、ε = 1.14%、走 L = 3 m：

```
朝向偏转 = ε·L/W     = 5.9°
横向偏移 = ε·L²/(2W) = 0.155 m
```

**走 3 米直线，如果车偏出去约 15 cm 而里程计报 theta≈0、左右计数基本相等，就确认
ε≈1.1%。** 偏得远小于这个数，说明那 ±1.14% 是转圈的方向性滑移（脚轮甩头之类），
不是 ppr 误差，不用管。

命令（会走 3 米，全程用深度图实时刹车；需要卷尺）：

```bash
. /userdata/x5/env.sh
python3 /userdata/x5/tinynav/tool/x5_board/diffcar_drive_measured.py 3.0 0.20
```

跑完量两个数：① 起点胶带 → 车体后缘的实际距离（定死轮周长）；② 车尾横向偏离参照直线
多少（定死左右轮不对称）。工具会打印 `固件里程计 x = ... (计数 左N 右N, theta=±N 度)`。
⚠️ 它输出里的 `VIO 全程弦长` 是坏值，忽略。

## 5. 优先级

**中等，排在延迟和倒车后面。** 理由：`map->odom` 每 1.5 s 重锚一次，2.4% 在两次重定位
之间只攒出约 1.2°，可忽略；它**只在重定位掉线时才放大**，而那时该修的是掉线。
对称那 2.4% 要烧固件（`WHEEL_BASE` 是固件常量），不对称那部分要先做上面那个直线测量。
