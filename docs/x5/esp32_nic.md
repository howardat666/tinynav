## ✅ 2026-09-16：丢包根因定案（ZLP）+ 开机对时修复 + 配置全部纳入版本管理

### 一、持续丢包的真凶：NTB 长度撞上 64 的整数倍

**机制**：全速（full-speed）批量端点一包 64 字节。NTB（NCM Transfer Block，一次 USB 传输里打包
的若干以太网帧）长度正好是 64 的整数倍时，主机既收不到短包、TinyUSB 又不发零长包
（Linux 侧 `dmesg` 明写 `CDC NCM (NO ZLP)`），那次 URB 就不结束 —— **下一个 NTB 被追加进同一个
URB，而 `cdc_ncm` 只解析 `wBlockLength` 以内的内容，后面那整个 NTB 连同它的帧被当尾部填充丢掉**。

🔴 **两端计数都显示"发成功 / 收完成"**，所以任何计数器都查不出来。帧长 4 字节对齐后每 16 个长度
命中一次 = 6.25%，和长期实测的 8~13% 丢包率对得上。

**修法**：`ncm_start_tx()` 里发现长度是 64 的倍数就补 4 字节把它错开（NTB 允许尾部填充，
`wBlockLength` 含它）。

**对照实验**（同一 RSSI −44 dBm、同一信道 ch=6，回退到修复前的固件再跑一遍）：

| ping 载荷 | NTB 长度 | 是 64 的倍数 | 修复前丢包 | 修复后 |
|---|---|---|---|---|
| 62 B | 256 | ★ 是 | **45.3%** | **0%** |
| 126 B | 320 | ★ 是 | **47.3%** | **0%** |
| 100 B | 296 | 否 | 8.0% | 0.33% |
| 56 B | 252 | 否 | 8.7% | **0%** |

剩下的约 1.77% 常态丢包是空口侧的（2.4 GHz 拥塞），不是这条 bug。

### 二、NTB 死锁：是 TinyUSB 的既有缺陷，不是我们引入的

老版本代码里 `if (transferring) return;` + 不检查 `usbd_edpt_xfer()` 返回值 + 无条件
`transferring = true` 三件**逐字存在**，上游 0.20.0 重写后仍然有（对应 issue #3436）。
表现是整段中断（34%/55%/82%/100% 的突发），而不是连续卡顿。

**三处修复**（都在 `ncm_device.c`）：

| 修复 | 说明 |
|---|---|
| 检查 `usbd_edpt_xfer()` 返回值 | 失败时保留本 NTB 并 `return`，不再把 `transferring` 焊死成真 |
| 超时就地恢复（500 ms） | ⚠️ **判据必须是超时，不能用 `usbd_edpt_busy()`** —— 卡死时端点**就是** busy，基于它的判据一次都没触发过。常态最长 35 ms，500 ms 是 14 倍余量 |
| `SET_INTERFACE` 切 alt 时重置发送侧 | 主机 `ifconfig down/up` 会走 alt=0 → alt=1，alt=0 时在途传输的完成回调永远不来 |

另外 TinyUSB 假设单线程，而我们从专用桥接任务里调它 —— 已补互斥锁。
⚠️ `ncm_tx_recover_if_lost()` **必须节流**（10 ms）：`loop()` 每秒跑 2~3 万圈，裸调等于每秒上万次
和 usbd 任务抢锁。

验证：`Nk` 命令人为注入死锁，29 次全部就地恢复，链路不断，整机看门狗一次没触发。

### 三、WiFi 一直钉在弱 AP 上

Arduino 默认 `WIFI_FAST_SCAN`：**扫到第一个同名 AP 就连，完全不看信号**。现场 DEEP-RD 有好几个
AP，实测长期钉在 ch=1 的 −56 dBm 上，而 ch=6 那个是 −44（差 12 dB）。改 `WIFI_ALL_CHANNEL_SCAN`
配合 `WIFI_CONNECT_AP_BY_SIGNAL` 后，吞吐 1.15~1.59 → **1.96 / 2.62 / 2.61 Mbit/s**。

### 四、开机对时挂了一个月，还顺带吃掉 48 秒开机时间

拔掉 USB 网卡换成 ESP32 网桥后，`board_autotime.sh` 里**写死的 `IFACE=wlx80ea07cb5d4a` 指向一块
已经不存在的网卡**，每次开机等满 `WAIT_NET=60` 秒、`exit 0` 退出 —— systemd 显示
`Finished successfully`，完全看不出坏了。实测板上时钟比真实时间**慢 34 小时**。

**代价是双份的**：`board-app.service` 是 `After=board-autotime`，那 60 秒白等直接把整个开机推后。

**第二个 bug 藏在后面**：即使网卡名改对，对时照样失败 —— 相机固件自带的
`/etc/init.d/looper/ip_config.sh` 无条件执行 `route add default gw 169.254.10.2`，给 usb0 加一条
**metric 0** 的默认路由；host 模式下 gadget 侧没有载波，这条路由是黑洞。
判据：`ping 223.5.5.5` 100% 丢包，但 `ping -I enxa4cb8fd549dc 223.5.5.5` 0% 丢包 26 ms。
⚠️ 原脚本的 `route -n | grep -q $IFACE` **发现不了**它 —— 两条默认路由并存时 grep 命中，
但实际出网走 metric 最小的那条。

**已修**（`tool/x5_board/board_autotime.sh`）：网卡改成探测 `en*`/`wl*`（排除 usb0，它有 IP 也
出不了网）；无条件 `ip route del default dev usb0`。

**冷启动实测**：

| | 修复前 | 修复后 |
|---|---|---|
| 开机总时长 | 83.0 s（内核 1.3 + 用户态 81.7） | **51.1 s**（内核 1.2 + 用户态 49.9） |
| `board-autotime` | 61.1 s（全部白等，对时失败） | 29.6 s（对时成功） |
| 板上时钟误差 | **−34 小时** | 与 PC 秒级一致 |

剩下那 29.6 秒基本压不动：等网卡拿到 IP **17 s**（ESP32 上电 → USB 枚举 → 连 WiFi → DHCP 的
串行链，ESP32 枚举单独实测就要 13.6 s）+ ntpdate ~7 s（开机早期重试；稳定状态实测 DNS 0.37 s
+ 对时 0.19 s）+ `is_time_sync` 跳 0→1 的 6 s（两个 `sleep 3`，相机固件靠这个重算时钟偏移）。

⚠️ 唯一还能砍的是让 `board-app` 不再 `After=board-autotime`（能提前约 30 s），但那样 app 会在
错误时钟下启动、然后被 step 近 200 秒，ROS 定时器和日志都会被这一跳打乱。**不建议动。**

📌 **可复用的判据**：任何"等网络"的脚本都不要写死网卡名 —— 换网络方案、换板子、换 USB 口都会让它
变，而超时退出的失败形态是完全静默的。查开机慢直接看 `systemd-analyze blame`。

### 六、USB 角色切换：四次实测，测出一个自激 bug

⚠️ **前提**：ESP32 的电只能来自 Looper 的 VBUS（C-to-C 直连），所以 Looper 一切到 device 就等于
给它断电。**接着 COM 线测出来的数都不作数** —— 那时它有外部供电，插上就能枚举。

| 场景 | 用时 | 说明 |
|---|---|---|
| host → device（C 口改接电脑） | **32.5 s** | 4.1 s 确认断开 + 26.3 s 枚举窗口 + 2.1 s 切换 |
| device → host（接回 ESP32，**有 COM 供电**） | 12.3 s | ESP32 全程没断电，参考价值有限 |
| 热插拔第 1 次（无 COM，真断电） | **18.4 s** | 枚举 14.3 s，与历史 13.6 s 吻合 |
| 热插拔第 2 次（同上） | 🔴 **158 s** | 见下 |

#### 🔴 第二次热插拔劣化 9 倍：两个 bug 叠在一起

```
[up 539.08s] host 检查失败 1/2   USB设备=0            ← 拔
[up 569.58s] host 26s 放弃: 设备已消失 472s > T_BOOT=25s — 转 device   ← 🔴
[up 581.82s] 试 host  →  [up 608.18s] 26s 放弃（消失 511s）→ device
[up 620.40s] 试 host  →  [up 646.77s] 26s 放弃（消失 549s）→ device
[up 658.96s] 连续 3 轮两侧都不通，放慢节奏继续轮询
[up 689.01s] 试 host  →  [up 697.23s] 稳定在 host ✅
```

**bug ①：`设备已消失 472s` 是假数。** `SEEN_AT`（最后一次看到 USB 设备的时刻）只在"正在轮询
角色"的循环里刷新，**一进稳定态就不再更新**。这次稳定态待了 440 秒，于是第二次拔线时它还停在
第一次热插拔的时刻。→ 已修：`settle()` 的监控循环里也刷新。

**bug ②：`T_BOOT` 一个参数身兼两职，而两职要的时长相反。**

| 它扮演的角色 | 需要 |
|---|---|
| 等 ESP32 重新枚举的耐心 | **更长** |
| 判定"对面其实是电脑"的门限 | **更短**，否则插到电脑要干等 |

实测：ESP32 正常上电到枚举 13.6 s，但**断电仅 12 s 后再上电，26 s 都起不来**（连续三轮全失败）；
直到断电 42 s 那轮才 8 s 枚举成功 —— 短暂断电会把它卡在一个恢复更慢的状态。于是 25 s 的窗口
等不到它 → 转 device 又断它的电 → **自激**。

→ 已修：拆成 `host_patience()`。**从没见过设备**（开机接的就是电脑）仍用 `T_BOOT=25s`；
**刚才还在**（是热插拔）用 `T_REPLUG`，且每失败一轮 +15 s，封顶 90 s。

**耐心定在 60 s（45 s 那版余量只剩 2.4 秒）**：上板实测 ESP32 在第 42.6 s 回来，而耐心 45 s。
⚠️ 它要覆盖的是「**人拿着线停留多久** + 枚举 13.6 s」，前者不可控。

**⚠️ 长耐心的代价，以及一个反直觉的取舍**：代价落在「拔了 ESP32 去接电脑」上，而「拔掉电脑
再插回电脑」要付两次（实测 52.9 s，其中 46 s 在等一个永远不会来的 ESP32）。
**别用「断开后优先重试上次的角色」来解** —— 那会 `set_role device` 掐掉刚接上的 ESP32 的电，
在「调试完接回去」这条更常见的路径上反而多花 14 s，净亏。正解是**按上次成功的角色挑耐心**
（`LAST_OK`）：一旦稳定在 device 过，说明对面上一次就是电脑，退回短的 `T_BOOT`。接回 ESP32
完全不受影响 —— 它 13.6 s 就枚举出来，25 s 窗口内 `host_ok` 早已成功。实测 62 s → **28 s**。

**新逻辑上板后的各场景实测**：

| 场景 | 用时 | 备注 |
|---|---|---|
| 开机 → 网络就绪 | 25.1 s | |
| 热插拔 ESP32（无 COM 供电） | 46.7 s | 其中 **29 s 是人停留的时间**，全程没转 device |
| 热插拔 ESP32（有 COM 供电） | 30.6 s | ESP32 不断电，只需重新枚举 |
| 拔 ESP32 → 接电脑 | 52.9 s | 长耐心的代价 |
| 拔电脑 → 接回 ESP32 | **16.4 s** | 这才是系统的纯响应时间 |

🔑 **46.7 s 和 16.4 s 的差别不在系统，在人手上**：前者 daemon 在 host 模式空等你把线插回来，
后者线已经插好了、一切到 host 就供电。报数字时别把人的停留时间算成系统延迟。

## ✅ 2026-09-14 夜：C-to-C 直连跑通，供电转接头可以去掉

**接线从「Looper C 口 → 外部供电转接头 → A-to-C 线 → ESP32」简化成一根 C-to-C 直连线。**
实测枚举成功、网桥自动起、吞吐无退化。

### 为什么原来要那个转接头

不是为了供电，是为了**绕过 VBUS 检测**。两件事之前一直被混在一起：

| | 是什么 | 引脚能不能解决 |
|---|---|---|
| 供电 | ESP32 芯片要有电 | ✅ `5V` 引脚（走板载 LDO）或 `3V3` 引脚 |
| VBUS | USB 线里第 5 根线，是「对面 host 在不在」的**信号** | ❌ 它来自线缆对端，本地电源给不了 |

ESP32 的 USB 外设默认**必须检到 VBUS 才起会话、才上拉 D+**。所以哪怕用 5V 引脚把它喂饱，
对端不供 VBUS 它也不枚举。而 X5 **没有 typec 子系统**（`/sys/class/typec` 不存在），
没有 CC 检测硬件，按 USB-C 规范就不会主动开 5V —— A 口转接头没有 CC 这套协商，
所以反而一直能用。

### 解法：在 ESP32 侧 override 掉 VBUS 检测

`main.cpp` 的 `USB.begin()` 之后把 `GOTGCTL` 的三组 session-valid 强制置 1：

```c
USB0.gotgctl |= USB_VBVALIDOVEN | USB_VBVALIDOVVAL |
                USB_AVALIDOVEN  | USB_AVALIDOVVAL  |
                USB_BVALIDOVEN  | USB_BVALIDOVVAL;
```

⚠️ **必须在 `USB.begin()` 之后**——`begin` 会重置 OTG 核，写在前面会被冲掉。

### 实测结果

| 项 | 换线前（转接头） | 换线后（C-to-C） |
|---|---|---|
| 枚举 | 成功 | 🟢 成功，`已被枚举=1 桥接=on 链路=1` |
| `GOTGCTL` | — | `0x000d00fc`（低 6 位 override 全置） |
| 下行吞吐 | 2.00 Mbit/s | 🟢 **2.09 Mbit/s**（2.46/1.86/1.95，无退化） |
| RSSI | −70 dBm | −57 dBm（位置变了，不是改动的功劳） |
| ping 丢包 | 0% | 0% |
| 板上接口错误 | — | rx drop 209 / tx drop 17（很低） |

### 🔴 判真实 VBUS 只能用 `Nv`，别读普通状态行

override 一开，`检到VBUS` 和 `GOTGCTL` 的只读位 `BSESVLD`/`ASESVLD` **全都被驱动成 1**，
读出来恒真，分不出对面到底供不供电。`Nv` 命令会临时撤掉 override 读一次真值再恢复。

⚠️ **当前 `Nv` 读到的 `B会话=1` 还不能证明 Looper 在供电** —— ESP32 同时还插着 PC 的
CH343 口，而 DevKitC-1 板上两个 USB 口的 VBUS 大概率并到同一条 5V 轨。
**干净的判据是拔掉 PC、只留 C-to-C，看网络还通不通。**

### 产品形态还差一步

现在 ESP32 靠 PC 的 CH343 口供电，产品里没有 PC。要么从底板取 5V 接 `5V` 引脚，
要么确认 Looper 的 C 口真的供电。⚠️ 拔掉 PC 之后就没有串口带外通路了，
所以要先确认 C-to-C 本身是通的再拔。

## 📊 2026-09-14 傍晚：分方向实测，瓶颈定位在 USB 桥接段

### 三组数字（口径已对齐，都是同一天、同一个 WiFi 环境）

| 路径 | 吞吐 | 相对损失 |
|---|---|---|
| **ESP32 自己发 WiFi**（UDP blast，不过 USB） | **8.60 Mbit/s**（rssi −39，3842 包成功 / 54 失败） | — |
| **过桥下行** Looper→USB→ESP32→WiFi→PC | **1.79 Mbit/s**（HTTP 有效 1.52） | **4.8 倍** |
| **过桥上行** PC→WiFi→ESP32→USB→Looper | **0.78 Mbit/s**（TCP 有效 0.56） | **11 倍** |

🔴 **「WiFi 环境变差」的结论作废。** 同一天重测 ESP32 独占发送仍是 8.60 Mbit/s，和最早那次的 6.84 同量级甚至更高。**WiFi 不是瓶颈，桥接这条路才是。**

### 分方向的计数证据

两个方向的丢包原先**共用同一个 `ncm_drop_tx`**，混在一个数里根本分不清谁在丢 —— 在拆开之前，所有关于"发送丢包"的分析都不可信。拆开后：

| 方向 | 速率 | ESP32 转发 | 关键计数增量 |
|---|---|---|---|
| 下行 | 1.52 Mbit/s | 1.79 | `USB→WiFi 丢 33 帧 = 1.3%`；`can_xmit 拒绝 全 0` |
| 上行 | 0.56 Mbit/s | 0.78 | 🔴 `NTB容量满 +174832 次`；`丢发送 37` |

**UDP 阶梯限速**（绕开 TCP 重传）：上行 1 Mbit/s 档只到达 **74.5%**，之后链路完全断流 —— 上行的物理上限就在 0.6 附近。

### 两个方向的瓶颈机制不同

**下行（USB→WiFi）—— ESP32 的转发是同步串行的，没有流水线：**

```c
bool tud_network_recv_cb(const uint8_t *src, uint16_t size) {
  ...
  esp_wifi_internal_tx(WIFI_IF_STA, (void*)src, size);   // 同步，在 usbd 回调里直接发
  tud_network_recv_renew();                               // 发完才准备收下一帧
}
```

收一帧 → 发一帧 → 才收下一帧，**每帧的 USB 接收和 WiFi 发送延迟串行累加**。而 blast 是连续发、无 USB 等待，这正是 8.60 → 1.79 那 4.8 倍的来源。

⚠️ **丢包率低不等于不是瓶颈。** 这个方向只丢 1.3%，我一度据此判定它"干净"—— 错的：串行延迟才是瓶颈，丢包率根本量不到它。

**上行（WiFi→USB）—— 卡在 Linux 那头取数据：**

`NTB容量满` 涨 17.5 万次，含义是 ESP32 把 NTB 装满却发不出去，一直在等 Looper 来取 IN 端点；ESP32 自己只丢 37 帧，**不是发不动，是没人来取**。同一个 `cdc_ncm` 驱动**发数据很快（下行 1.79 没问题）、取数据很慢**，收发不对称。Linux 侧参数：`rx_max=3200 tx_max=3200 tx_timer_usecs=400`，`rx_dropped` 占 7.8%。

### 已被数据否决的假设（别再走回头路）

## 🔴 2026-09-14 下午：四个根因与全部自愈机制

### 一、USB 死活起不来的真凶：`cdc_ncm` 开机没加载

dmesg 里有 `new full-speed USB device number 2` 却**没有** `New USB device found, idVendor=...`，看着像枚举失败 —— 实际是 host 侧的 `cdc_ncm` 驱动**根本没装上**。`lsmod` 只有 device 侧的 `usb_f_ncm`，而 `systemd-modules-load` 报 SUCCESS。手动 `modprobe` 一次就全好了，枚举和绑定一次过。

⇒ 和线材、转接头、USB-C 的 CC 电阻**全都无关**，之前那几轮硬件排查方向是错的。`modprobe` 现在写死在轮询脚本开头。

### 二、角色协商：一个口三选一，只能软件轮询

**Looper 只有一个可用 USB 口**（`35100000`，UDC 也是它），PC / ESP32 / USB WiFi 网卡**三选一**。X5 的 C 口没有 CC 检测电路，判不出对面是主机还是设备，只能「试一下看通不通」。

`/usr/local/bin/usb_role_daemon.sh`（`usb-role.service`）替掉了只切一次就回不来的 `net_rescue.sh`：

| 当前 | 条件 | 转移 |
|---|---|---|
| 试 host | 60 秒内 **ping 通网关** | 稳定在 host |
| 试 host | 16 秒没枚举到任何设备 | 提前转 device |
| 试 device | 30 秒内 UDC 变 `configured` | 稳定在 device |
| 稳定态 | 每 30 秒复查，**连错两次**才动 | 回到试 host |
| 连续 3 轮两侧都不通 | — | 只放慢节奏继续轮询 |

🔴 **四个判据我全写错过，每个都静默生效、都能锁死板子**：

| 判据 | 错在哪 | 后果 |
|---|---|---|
| `[0-9]-[0-9]*` 找枚举设备 | root hub 自己的接口叫 `1-0:1.0`，被匹配上 ⇒ 恒真 | 提前退出永不触发 |
| 只读 `net/usb*/carrier` | 接口 DOWN 时读出**空串**不是 0 ⇒ 恒假 | 永远 settle 不住，每 90 秒切断一次连接 |
| 只看 `ip route show default` | 「接口还在、链路已死」时恒真 | 卡在走不通的 host 上出不来 |
| 退避「停在 device 待援 300 秒」 | **device 模式不供 VBUS** | 线接着 ESP32 时对面 USB 压根起不来，自锁 9 分钟 |

⚠️ 还有一个：`settle` 返回时判据早已变假，**拿它结算成功/失败等于成功过也照样累计失败**，必须用单独标志位。

### 三、桥接一压流量就卡死（已加自愈）

传约 1 MB 之后 `tud_network_can_xmit()` 永远返回假，**丢包 100% 而 `链路` 仍显示正常** —— 主机不再来取 IN 端点，`transferring` 就一直挂着（TinyUSB 0.16 的 NCM 已知问题）。排除了优先级反转：`usbd` 任务是 24，桥接任务才 5。

**自愈**：转发任务里记 `last_ok`，连续 5 秒发不出去就 `tud_disconnect()` + 200 ms + `tud_connect()`，逼主机重新枚举。次数计入 `发送卡死自愈` 报到状态行。

### 四、串口杂散字节让车自己跑起来（安全问题）

ESP32 用**同一个解析器**处理调试终端和 ttyS3 来的命令，而 `f`/`b`/`l`/`r`/`d`/**`t`**/`j` 直接驱动电机 —— `t` 是引脚自检，末尾 PWM 给 50% 转 3 秒。原先只有 `X` 和 `U` 做了来源检查。

**已加白名单**：串口来源只放行 `u c s p e q z K U y`，其余丢弃并计数。判据是状态报告里 `串口拒收命令` 的**增量**。

🔴 **干扰源是充电器**：插着 25 秒拒收 4 次、累计 61 次；拔掉后 20 秒 **0 次**，RSSI 同时从 −68 跳到 −48 dBm。和舵机总线那条同源。

### 五、ESP32 侧的状态机（已烧录）

**不变式：桥接开着 ⟺ USB 链路 up 且 WiFi 已连接。**

| 规则 | 条件 | 动作 |
|---|---|---|
| R1 | WiFi 断开（每 10 秒查） | 桥接开着先退桥（内含断开重连），否则 `WiFi.reconnect()` |
| R2 | 桥接开 且 链路 down | 立刻退桥，把自己的 IP 要回来 |
| R3 | 桥接开 且 链路 up 但 120 秒零帧 | 退桥 + **冷却 60 秒**（没有它就是开桥/退桥自激循环） |
| R4 | 桥接关 且 自启开 且 链路 up 且 WiFi 已连接 且 过冷却 | 开桥（唯一入口） |

### 六、远程可判的状态量（不用再让人看灯）

状态命令 `N` 现在带：

```
USB 设备侧: 检到VBUS=0 已被枚举=0 挂起=0 发送卡死自愈=0 次
上位机: 灯=青慢闪(Looper说PC不可达) | 距上次 ttyS3 数据 0s | Looper报PC可达=0 | 累计 静默0次/PC不可达241次
串口拒收命令: 0 次 (最近一个 '-')
```

- **`检到VBUS`** 一刀切开「ESP32 的 USB 没启动」和「主机没供电/没在做主机」—— 只看 `链路=`/`主机已开=` 分不开，两种情况下都是 0
- **`距上次 ttyS3 数据`** 判 Looper 死活，比 ping 快
- 新增命令 **`Nc`** = USB 断开重连，不用整机复位就能逼主机重新枚举

### 三轮优化的效果

| 指标 | 第一版 | 现在 | 对照：原 8188GU 网卡 |
|---|---|---|---|
| 🔑 **控制环最大周期** | **2002 ms**（标称 50） | **51 ms** | — |
| TCP 端到端 | 0.85 Mbit/s | **1.42 Mbit/s** | 1.60 Mbit/s |
| UDP 端到端 | 0.51 Mbit/s | **2.63 Mbit/s** | — |
| ESP32 内部丢弃 | 队列 4059 / 发送 18702 | **队列 0 / 发送 385** | — |

**三处改动，按贡献排序：**

1. 🔑 **控制环挪进独立的高优先级 FreeRTOS 任务**（CPU1，优先级 10，1 kHz 节拍）。
   原来它跑在 Arduino 的 `loop()` 里 —— 那是全系统优先级最低的任务，WiFi/USB/网桥一忙就被挤掉。实测转发大流量时控制周期被拉到 **2002 ms**，车真跑起来等于失控。挪出来之后满负载下仍然精确 51 ms。
   ⚠️ 实时段内不许有串口输出（会阻塞），三处 `printf` 改成标志位交给 `loop` 打印。

2. 🔴 **桥接期间 ESP32 必须交出自己的 IP**（`esp_netif_dhcpc_stop` + 清空 IP，`ip=0.0.0.0`）。
   二层桥接下转发出去的帧**源 MAC 是 STA 的、源 IP 是主机的**。如果 ESP32 自己还占着另一个 IP，AP 就看到「一个 MAC 两个 IP」，带防 IP 欺骗的企业 AP 会整批丢包 —— 实测主机发 3540 包只有 399 到达（丢 88.7%），而 ESP32 自己发同样速率**零丢包**，两者唯一差别就是源 IP。改完丢包率降到 48%，UDP 吞吐涨 4.7 倍。

3. **转发等发送口时先忙等（`taskYIELD`）再睡**，队列 16→32。
   `vTaskDelay(1)` 是一个完整 tick，每帧都付 1 ms 的话 TCP 的 ACK 会被拖慢；而且**帧之间一睡，NCM 就没法把多个帧打进同一个 NTB**。TCP 从 1.14 → 1.42。

### 还差什么

TCP 比原网卡低 11%（1.42 vs 1.60），剩下的差距在**空口**：UDP 测出 48% 丢包，而 ESP32 内部几乎不丢（队列 0 / 发送 385）。这个网络本身就很差 —— 网关自己的 RTT 都有 157 ms、扫得到 31 个 AP。**不是实现问题，继续优化转发代码收益有限。**

## 一、为什么做：成本，不是驱动

- X5 芯片**本身没有 WiFi 射频**，必须外挂

| 环节 | 实测 | 备注 |

| **现状：X5 的 USB 网卡 8188GU** | **1.60 Mbit/s** | 发方向（板→PC），这是现在的瓶颈 |

### 🟢 能开回彩色预览

| | 加 NCM 前 | 加 NCM 后 | 芯片有 |
|---|---|---|---|

| 指标 | 实测 |

## 四、固件怎么做的（Arduino 下做 NCM 的完整配方）

```
X5 ──USB(NCM 网卡)──> ESP32 ──WiFi──> 路由器
       以太网帧原样搬运，中间不拆包
```

**五个关键点，每个都踩过坑：**

1. **Arduino 的 TinyUSB 预编译库里没有 NCM**（`nm` 查符号数 = 0，只编了 CDC/MSC/HID）。
   → 从 TinyUSB 官方仓库取 `ncm_device.c` + `net_device.h`（MIT，版本对齐 SDK 头文件的 **0.16.0**）放进 `src/tinyusb_net/`，还要把 `ncm.h` 从 SDK 复制过去（`net_device.h` 按同目录找它）。
   🟢 描述符宏 `TUD_CDC_NCM_DESCRIPTOR` 在 SDK 的 `usbd.h` 里**是有的**，只有类驱动实现被裁了。

2. **用 weak 符号挂进协议栈**：`usbd_app_driver_get_cb()` 在库里是 weak（`nm` 显示小写 `w`），应用可覆盖，返回自己组的 `usbd_class_driver_t`（`.init=netd_init, .reset=netd_reset, .open=netd_open, ...`）。
   构建标志：`-DCFG_TUD_NCM=1 -DCFG_TUD_NET_MTU=1514 -Isrc/tinyusb_net`。

3. 🔴 **`ARDUINO_USB_MODE` 必须改成 0**。=1 走的是硬件 USB-Serial-JTAG，**做不了自定义 USB 类**。改完原生 USB 口归 TinyUSB 管；烧录仍走左边 CH343 口和 OTA，不受影响。

4. 🔴 **CDC 必须关掉**（`ARDUINO_USB_CDC_ON_BOOT=0`）。CDC 和 NCM 各要 2 个 IN 端点，加起来超过 S3 的 TX FIFO，**症状是主机报 `can't set config #1, error -32`**（描述符本身完全正确，是配置阶段 STALL）。
   ⚠️ 连带影响：CDC 关掉后 Arduino 不再定义 `Serial0` 这个名字（`Serial` 本身就是 UART0），代码里要加 `static HardwareSerial &Serial0 = Serial;`，并且 `io` 类不能再把两者的 `available()` 相加（会读成两倍）。

5. 🔴 **`USB.begin()` 要自己调**。core 的 `main.cpp:66` 把它藏在 `ARDUINO_USB_ON_BOOT` 开关后面，而那个宏还依赖 CDC 的 include。CDC 关掉后必须在 `setup()` 里自己 `#include "USB.h"` 并调用，且**必须在 `ncm_usb_register()` 之后**（`tinyusb_enable_interface` 一旦看到 `tinyusb_is_initialized` 就直接拒绝）。

**桥接逻辑**照搬 ESP-IDF 官方 `tusb_ncm` 示例：不过 `esp_netif`，直接在以太网帧层对接 ——
- USB→WiFi：`tud_network_recv_cb()` → `esp_wifi_internal_tx(WIFI_IF_STA, ...)`
- WiFi→USB：`esp_wifi_internal_reg_rxcb()` → 队列 → `tud_network_xmit()`

🟢 这三个符号在 Arduino 预编译库里都有（`libnet80211.a` / `libpp.a`），只是头文件没暴露，自己写原型即可 —— **所以不用切 ESP-IDF，现有 1000 多行电机控制代码一行没动**。

🔑 **NCM 网卡的 MAC 必须取 WiFi STA 的 MAC**。二层桥接下如果两边各用各的 MAC，就成了 802.11 的四地址（WDS）场景，普通路由器根本不转发。

⚠️ `esp_wifi_internal_reg_rxcb` 注册之后 **ESP32 自己的 lwIP 就收不到包了** —— 它只做网桥，没有自己的 IP。这是设计，不是 bug。

## 七、踩过的坑（别重蹈）

🔴 **别用「发送端的失败计数」当射频质量的判据。** 第一版压测循环 `while(...){ 发包 }` 一直占着 CPU 不让出，而 ESP32 的发包是异步的（真正搬包的是后台 WiFi 任务），被我饿死了。量出来 **0.20 Mbit/s、90% 失败**，我据此下了「射频有问题、要换天线/加供电」的错误结论。加一句 `delay(1)` 让出 CPU，数字立刻变成 **6.84 Mbit/s、零丢包**。
→ 正确判据是**接收端实际收到多少**，而且要先确认发送端真把包交出去了。

🔴 **别在电脑上测桥接吞吐。** ESP32 桥接出去的就是电脑已经在的那个局域网，一配 IP 就会有两个接口在同一子网，ARP 和路由必然打架（实测直接把电脑网搞断了）。X5 上不存在这个问题（拔了网卡只剩一个接口）。要在电脑上测得让 ESP32 连一个**不同网段**的网络（比如手机热点）。

⚠️ **Python 批量改代码时 `str.replace(..., 1)` 要配 assert。** 有一次锚点 `g_ledState = LED_OK;` 在 `drive()` 里先出现，初始化代码被静默插进了错误的函数，症状是「注册返回值一直是初始值」，查了一轮才发现。

⚠️ **电池电压要盯着。** 中途 X5 掉线一次，而 ESP32 还在线 —— ESP32 报的「塌前最低电压」一路从 11.59V 掉到 9.86V（低压保护阈值 9.60V）。Looper 是 12V 输入，电池放空就起不来，而 3.3V 的 ESP32 还撑得住。**这个组合（X5 掉线 + ESP32 在线）基本就是电池的指纹。**
