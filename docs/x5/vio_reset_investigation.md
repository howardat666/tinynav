# 固件 VIO 重启：九格消去实验（2026-09-02）

## 现象与后果

固件日志里成对出现：

```
W key_frame_state_estimator.cc:773  Image data is lost for a long time, vio will be stopped.
[insight_full] VIO restarted successfully after tracking lost
```

`insight_full` **进程不重启**（`etimes` 连续），所以我们这边任何进程级监控都看不见。
但 VIO 原点归零，后果有两个：

1. **地图位姿瞬移** → 落进 POI 的 0.4 m 到达半径 → 宣布到达、导航结束。
   实测 3.08 s 挪了 2.85 m = 0.92 m/s，是 `max_vx` 0.25 的 3.7 倍，而车其实还在 2.75 m 外。
2. **障碍栅格按世界坐标索引，世界一挪整张图作废** → `blocked=0/110`、`fwd_ok=90/90`、
   `front_clearance=>1.20m` → 规划器发出 `vx=0.250` **满速冲进一张空白地图**。

## 九格消去实验

判据：固件 journal 中两条消息的**增量**。工具 `tool/x5_board/perf_monitor.py`
（同时采 load / 温度 / BPU ratio / 各话题的消息戳与墙钟间隔 / 各进程瞬时 CPU）。

| # | 条件 | load | 温度 | insight_full | 丢图/重启 |
|---|---|---|---|---|---|
| 阶梯 0→6 | nav开无目标 · 静止 · CPU 0→6 | 10.9→**20.5** | 80→86 | — | **0/0** |
| ① | nav关 · 静止 · 无 | 8.2 | 84 | 177% | 0/0 |
| ② | nav关 · **转动** · 无 | 10.0 | 85 | **274%** | 0/0 |
| ③ | nav关 · 静止 · CPU6 | 16.1 | 88 | 168% | 0/0 |
| ④ | nav关 · **转动** · CPU6 | 19.1 | 89 | **161%** | 0/0 |
| ⑤ | **nav开** · 静止 · 无 | 13.8 | 88 | 211% | 0/0 |
| **⑥** | **nav开** · **转动** · 无 | 18.0 | 88.7 | **192%** | 🔴 **+3/+1** |
| ⑦ | nav关 · 转动 · **内存压到 415MB** | — | — | 277% | 0/0 |
| ⑧ | nav关 · 转动 · **大消息 DDS**（BPU 打到 100%） | 13.3 | 88 | 263% | 0/0 |
| ⑨ | nav关 · **抖动**转动 · 无 | 13.4 | 88 | 282% | 0/0 |

🔑 **CPU 够不够彻底出局**：④ 只拿到 **161%** 却 0 失效，⑥ 拿到 **192%** 反而失效。
内存、BPU、DDS 大消息、匀速/抖动转动，单独都复现不出来。
**必要条件是「nav 开（map_node + cmd_vel_control 在跑）」且「车在动」**，
但具体是这两者的哪一点，尚未切出来。

⚠️ **统计功效不足**：失效是低频事件（55 s 里 +1 次），同条件的 baseline 跑出过 +2 和 0
两种结果。上表右列应读作「**没复现出来**」而不是「已排除」。要真排除某个变量，
每格需要跑十几分钟而不是 55 秒。

## 调度优先级 A/B —— 三种方案都没好处

相同压力（3 个 nice −5 进程）、相同 45 s、车都在慢速原地转：

| 方案 | load | 温度 | 丢图 | VIO重启 | planning cycle p50/p90 | stamp_lag |
|---|---|---|---|---|---|---|
| baseline（现状） | 18.97 | 89.2 | **+0** | **+0** | 0.24 / 0.75 | 0.53 |
| camfirst（相机 nice −15） | 19.79 | 89.6 | **+18** | **+3** | 0.25 / 0.74 | 0.53 |
| affinity（相机绑 0-2 核 / 我们 3-7 核） | 19.29 | 89.7 | **+11** | **+3** | 0.26 / 0.77 | 0.53 |

提相机优先级和核绑定都没帮上忙，而我们自己的环延迟三者几乎一样 —— **两边都没赚到**。
（baseline 另一次跑出过 +7/+2，所以方案间差异在方差之内；能确定的只有「改了没好处」。）

⚠️ `nice` 和 `chrt` 是两回事：前者只改 CFS 权重，后者是实时调度会绝对抢占。
本节测的全是 `nice`。

## insight_full 的线程拆解

| 线程 | 静止 CPU |
|---|---|
| `vio_frontend` ×2 | **84.5%** |
| `vio_backend` / `vio_stereo` / `vio_imu` | 9.6 / 3.2 / 2.5 |
| **VIO 小计** | **≈ 100%（1 核）** |
| `rgb_pub` + `rgb_cap` + `jpg_encoder` | **14.3%** ← 彩色流，导航不用 |
| 其余 | ≈ 58% |
| **整进程：静止 177% / 转动 274%** | 动起来多吃一个核 |

`insight_full` 有 **14 个线程带实时优先级**（`imu_cap` 是 99），VIO 内核本来就受保护 ——
这解释了为什么普通进程加压到 load 20.5 也压不垮它。

## 已加的三道守卫（不解决根因，但让它不再致命）

| 位置 | 内容 |
|---|---|
| `tool/looper_bridge_node.py` | VIO 重置检测改按**物理极限**判位移。原判据 `contiguous = dt < 0.12` 要求相邻两帧，而本节点位姿队列 `depth=1`、回调间隔中位数 450 ms，条件几乎永不成立 —— 6 次真实重置报了 **0** 次 |
| `tinynav/core/map_node.py` | 到达判定加瞬移守卫：`moved > 0.25×dt + 1.2` 就不判到达。验算：拦下 2.85 m/3.08 s，放行正常接近与 1.1 m 的重定位修正 |
| `tinynav/core/planning_node.py` | 位姿瞬移 → 清空障碍图 + `TINYNAV_BLIND_AFTER_JUMP_S`（默认 1.2 s）内不许前进 |
