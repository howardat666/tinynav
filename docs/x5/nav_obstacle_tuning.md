# 避障几何、z 带与性能 —— 2026-08-11 的实测与结论

本文记录 LeKiwi + Looper（单 X5）导航栈在 2026-08-10~11 两轮实机测试后的一次集中排查。
所有数字都是板上或同一份地图上实测的，**推测和测量分开标注**。

被推翻的旧结论单独列在最后一节，因为它们已经写进过对话和 commit message，值得留一份纠错记录。

---

## 0. 一句话结论

导航「明明离障碍物很远却卡住」的机制**不是地面被误判成墙**（这一条已被实测推翻），而是
**碰撞检测用外接正方形代替圆盘（外伸多 41%）+ 十字膨胀（方向相关 4.1~10 cm）+ 体素量化（±14 cm）
三层各向异性余量叠加**，等效避障半径随方位角在 0.11~0.45 m 之间变化四倍。

配套的第二个问题是 **z 带按 VIO 的坐标原点定的，顶部看到世界 0.58 m** —— 而 LeKiwi 只有 0.25 m 高。

---

## 1. 术语与坐标约定

| 术语 | 含义 |
|---|---|
| **ESDF**（欧氏符号距离场） | 每个自由格到最近障碍格的欧氏距离。本仓库里是 `distance_transform_edt(~obstacle_mask) * resolution`，**格心到格心** |
| **z 带**（z band） | `build_obstacle_map` 把 3D 占据栅格投影成 2D 障碍图时，参与投影的那一段高度区间，由 `robot_z_bottom` / `robot_z_top` 定义，**相对相机** |
| **z_span** | 同一 (x,y) 列上，带内最高与最低占据层之间的高度差 |
| **layer / 层** | 局部栅格的一个 z 切片，厚 `resolution` = 0.1 m |
| **datum** | 世界坐标 z 的原点。VIO 从相机起算（相机 z≈0）；轮速里程计现在从地面起算（相机 z=0.18） |
| **REP-103** | ROS 的机体坐标约定：+x 前、+y 左、+z 上 |
| **光学约定**（optical） | 相机坐标：+x 右、+y 下、+z 前。**整个导航栈用这个** |

两套并存的**分辨率**，互不相干：

| | 局部避障栅格 | 全局地图栅格 |
|---|---|---|
| 位置 | `planning_node.py:281` `self.resolution = 0.1` | 地图文件 `occupancy_meta[3] = 0.1` |
| 尺寸 | `grid_shape = (100,100,10)` → 10×10×1 m | 办公室图 134×182×23 → 13×18×2.3 m |
| 生存期 | 每帧 `×0.99` 衰减，半衰期约 14 s | 永久，存盘 |
| 跟随 | **跟着机器人滚，三个轴都滚**（`roll_occupancy_grid`） | 固定在世界里 |
| 消费者 | 障碍图 → ESDF → 轨迹碰撞打分（5 Hz） | 全局 A\* 路径搜索（切 POI 时一次） |

## 2. 碰撞几何：三层各向异性余量

### 2.1 采样点用的是外接正方形，不是圆

`RobotConfig.half_size` 对 `shape == 'circle'` 返回 `(radius, radius)`，
`score_trajectories_by_ESDF` 据此取 **中心 + 4 个角**：

```
        实际底盘（圆 r=0.15）        碰撞检测用的（外接方）
                                    ●─────────────●  ← 角离心 0.2121 m
            ╭───╮                   │   ╭───╮     │
           │  ●  │  r=0.15          │  │  ●  │    │
            ╰───╯                   │   ╰───╯     │
                                    ●─────────────●
                   离心距离：0.15  →  0.2121 m，多出 41%
```

角随朝向旋转，**所以圆盘原地旋转会得到不同的碰撞结论** —— 纯几何幻影。
实测那次 23 秒死锁的日志里 `esdf_at_robot=0.22~0.28 m`，角在 0.2121 m，正好卡在边界，
14 条原地旋转候选只活下来 1~2 条。

### 2.2 膨胀是十字形，效果随方位角变

`dilation_cells = 1` + `scipy.ndimage.binary_dilation` 默认结构元（4 连通十字）：

| 障碍格相对位置 | 未膨胀 ESDF | 膨胀后 | 被削掉 |
|---|---|---|---|
| 正方向邻格 (2,0) | 0.200 | 0.100 | **0.100 m** |
| 对角邻格 (1,1) | 0.141 | 0.100 | **0.041 m** |

**同一个物体，正前方比斜前方多吃 6 cm 的余量。**

**实测（板上，lekiwi 在真实地板，25 s / 88 帧）**：未膨胀 42.2 格 → planning 实际报 96 格 = **×2.3**。

### 2.3 体素量化：±0.141 m，双侧

障碍点 → 体素用 `floor`，**不是四舍五入到格心**：

```python
end_voxel_x = int(np.floor((pw_x - origin_x) / resolution))   # planning_kernels.py:52
x_img       = int((check_xs[k] - origin[0]) / resolution)     # planning_kernels.py:215
```

障碍点和查询点各自在自己格子里任意位置，而 ESDF 量的是格心到格心。
二维半对角 = `0.1×√2/2 = 0.0707 m`，两侧独立：

> **ESDF 读数 `d` → 真实距离 ∈ `[d − 0.141, d + 0.141]`**（最坏）；**1σ ≈ 0.041 m**

### 2.4 三层叠起来

| 层 | 数值 | 性质 |
|---|---|---|
| 圆盘真实半径 | 0.15（轮子接地点）/ 0.20（最大外伸） | 物理 |
| 碰撞采样点离心 | **0.2121 m** | 41% 是幻影 |
| 膨胀 | 0.041 ~ 0.100 m | **方向相关** |
| 体素量化 | ±0.141 m | 双侧 floor |
| `safety_radius = 0.1` | **软惩罚**，不是硬禁 | 见 2.5 |
| 硬碰撞判据 | 采样点**落进**障碍格（`min_dist < 1e-3`） | 唯一的 inf |

> **等效避障半径 = 0.11 ~ 0.45 m，随方位角变四倍，无法用一个数表达。**
> 日志里 `front_clearance=0.10m` 时，真实物体可能在车心外 0.15~0.45 m。

### 2.5 `safety_radius` 现在是软的，但数值上是决定性的

```python
if   min_dist < 1e-3:            inf                        # 硬碰撞
elif min_dist > safety_radius:   0.0                         # 不罚
else:                            decay / (min_dist + 1e-3)   # 软惩罚
```

`d = 0.1` 时 `score ≈ 9.9 × decay`，进代价函数是 `×100000` ≈ **50 万**，
而目标项 `100 × dist` 通常只有 **200**。所以名义上软、实际上压倒性。

## 3. 建议的新碰撞结构：r / s / c

### 3.1 圆形机器人根本不需要采样

ESDF 的定义就是「这一格到最近障碍格的距离」，半径 `r` 的圆盘碰撞条件**精确地**就是 `ESDF(圆心) < r`。
采样是近似，这个是精确。

```python
d = ESDF[圆心格]
if   d < r + s:          inf                          # 硬禁
elif d > r + s + c:      0.0                          # 不罚
else:                    decay / (d - (r+s) + 1e-3)   # 居中偏好
```

内层循环从 5 次查表降到 1 次（106 条 × 31 步：16430 → 3286 次）。方形（go2）保留 4 角采样，按 `shape` 分支。

### 3.2 三个参数，各管一件事

```python
collision_radius = 0.20    # r：车身真实最大外伸（0.15 是轮子接地点，不是外壳）
safety_radius    = 0.10    # s：量化 + 深度噪声 + 位姿误差的余量 → 硬阈值 0.30
comfort_margin   = 0.10    # c：软惩罚带宽 → 软上界 0.40
dilation_cells   = 0       # 余量全部交给 r + s，各向同性、连续
```

| | 值 | 含义 | 改它的后果 |
|---|---|---|---|
| `r` | 0.20 | **物理事实**，量出来的 | 不该调 |
| `s` | 0.10 | **对传感器和栅格有多少信心** | 调大 → 更安全，走廊要求更宽 |
| `c` | 0.10 | **路径品质** | 调大 → 更爱走中间；不影响安全 |

`c` 的实际价值：门只有 0.80 m 时所有候选都落在惩罚带里，这时它**挑最宽的挤过去**而不是全部判死然后冻住。
没有 `c` 就只有「过」和「不过」两态。

`r` 取 0.18 还是 0.20 **无所谓** —— 0.02 m 是 1/5 个体素，远低于 ±0.141 m 的量化不确定度。

### 3.3 保守 / 平衡 / 激进（`r = 0.20`）

| 方案 | `s` | 硬阈值 | **一定不撞的间隙** | 典型(1σ)间隙 | 最大浪费站位 | **一定能过的走廊宽** |
|---|---|---|---|---|---|---|
| 激进 | 0.05 | 0.25 | **−0.09 m** | +0.01 | 0.19 m | **0.78 m** |
| **平衡** ⭐ | 0.10 | 0.30 | −0.04 m | +0.06 | 0.24 m | **0.88 m** |
| 保守 | 0.15 | 0.35 | **+0.01 m** | +0.11 | 0.29 m | **0.98 m** |

**保守方案过不了办公室的门**（门洞 0.8~0.9 m，它要 0.98 m）。所以取平衡。

在 0.1 分辨率下**必须**在「最坏会擦到」和「过不了门」之间选一个。分辨率是唯一能同时满足两者的杠杆（见 §6）。

### 3.4 圆盘原地旋转应免于碰撞打分

圆盘原地旋转，扫掠体积和它现在占的地方完全相同。所以「原地旋转会碰撞」这个判定：

- 若为假 → 是外接方角的幻影
- 若为真 → 它说的是「你现在就在障碍物里」，是对**现状**的陈述，而且**完全不可行动**

两种情况下都不该用来否决旋转：

```python
if self.robot.shape == 'circle' and self._is_turn_in_place(param):
    score = 0.0
```

副作用是好的：真被顶到墙上时机器人会转身而不是冻住。

### 3.5 UI 改圆形不需要改前后端

前端 `planning_painter.dart:167` 用 `path.close()` 画**闭合多边形**，点数任意；
后端 `node_manager._on_footprint` 的 else 分支原样收下任意点数。
所以只改 `publish_footprint`，圆形底盘发 16 个圆周点即可。

⚠️ `_on_footprint` 有个 `if n >= 84 and n % 21 == 0` 分支（RViz 轮廓插值遗留），点数别撞上它。16 安全。

## 4. z 带：问题在顶部，不在底部

### 4.1 层格是固定的，因为栅格三个轴都跟着机器人滚

```python
new_center = robot_pos                                    # planning_node.py:789
new_origin = new_center - grid_shape * resolution / 2     # 三个轴都减
```

所以 `z_rel` 永远落在 `{−0.45, −0.35, …, +0.45}` 这个格上（栅格只滚整格）。

**推论：把 datum 从 0.18 平移到 0，`robot_z` 和 `origin[2]` 同时平移，`z_rel` 一个字节都不变。**
datum 改动对 z 带是**严格的空操作**。

### 4.2 go2 和 lekiwi 的真正差别

| | 相机 z | 地面 z_rel | 地面所在层 | 带内在它下面的层 | 带覆盖的**世界**高度 | 机器人高 |
|---|---|---|---|---|---|---|
| **go2** | ≈ 0 | −0.35 | −0.35（**带的最底层**） | **0 层** | −0.05 ~ +0.75 | ~0.40 m ✅ |
| **lekiwi 现状** | 0.18 | −0.18 | −0.15 | 2 层（−0.25, −0.35） | −0.22 ~ **+0.58** | ~0.25 m ❌ |

go2 的 datum 恰好把地面顶在带的最底边。**但实测显示底部那两层是空的**，所以对 lekiwi 也无害。

> **问题一直是顶部：一个 0.25 m 高的机器人在看 0.58 m 高的东西。**

### 4.3 实测：真实地板，25 s / 88 帧

层分布（`z_rel` 相对相机，世界 z = z_rel + 0.18）：

```
层  z_rel   世界 z 区间        体素/帧   内容
 2  -0.25  [-0.12, -0.02]        0      空
 3  -0.15  [-0.02, +0.08]       82      ← 地面
 4  -0.05  [+0.08, +0.18]       67
 5  +0.05  [+0.18, +0.28]       76      ← 机器人顶
 6  +0.15  [+0.28, +0.38]       52
 7  +0.25  [+0.38, +0.48]       65      ↓ 机器人从下面过去
 8  +0.35  [+0.48, +0.58]       45
 9  +0.45  [+0.58, +0.68]       55
```

方案对比（每帧平均障碍格数；`min_wall_span_m` 只在 0.1 的整数倍上有意义）：

| 方案 | band | 层 | span=0 | span=0.1 | **span=0.2** |
|---|---|---|---|---|---|
| **A 现状** | [−0.40,+0.40] | 8 | 251.4 | 59.7 | **42.2** |
| B（带=机器人扫掠高） | [−0.28,+0.10] | 4 | 197.3 | 27.9 | **0.6** ⚠️ |
| R | [−0.20,+0.10] | 3 | 197.3 | 27.9 | 0.6 |
| **R2 推荐** | **[−0.20,+0.20]** | **4** | 217.1 | 44.3 | **20.9** ⭐ |
| X（排掉地面层） | [−0.10,+0.10] | 2 | 122.2 | 21.6 | 0.0 |
| X2 | [−0.10,+0.20] | 3 | 142.1 | 38.4 | 20.2 |

### 4.4 两个关键判读

**① 地面根本没被误判。** X2（把地面整层排除）vs A = 20.2 vs 42.2 —— 但那是带高度不同造成的。
直接对照：早前一组 C `[−0.10,+0.40]` vs A `[−0.40,+0.40]` = 39.5 vs 39.9，**地面只贡献 1%~6%**。
原因：地面只占**一层**（层 3 有 82 个体素，层 2 有 0 个）→ `z_span = 0` → `min_wall_span_m = 0.2` 正确滤掉。

**② 把带收窄到机器人扫掠高度会把障碍物删光。** `42.2 → 0.6`。
带只剩 4 层（0.38 m）却要求 z 跨 0.2 m = **要求物体占满 4 层里的 3 层**，真实地板上几乎没有物体能做到。

> **张力**：带 = 「我关心哪个高度」应该等于机器人扫掠高度；
> span = 「这是地面还是墙」需要垂直跨度来区分。**带越窄，span 越难满足。**

### 4.5 推荐

```python
robot_z_bottom  = -0.20    # 底部无所谓（下面两层是空的），-0.20 比 -0.28 保险
robot_z_top     = +0.20    # 世界 +0.38，机器人顶 0.28 之上留一层
min_wall_span_m =  0.2     # ⚠️ 暂不动，见 §5
dilation_cells  =  0
```

**障碍格 96（现状，已膨胀）→ 20.9（无膨胀）**，79% 的下降每一份都能溯源：

| 减掉的部分 | 从哪来 | 为什么安全 |
|---|---|---|
| 96 → 42.2 | 去掉膨胀（×2.3） | 换成 `r + s = 0.30` 的 ESDF 判据，各向同性、连续，严格更好 |
| 42.2 → 20.9 | 顶部 +0.40 → +0.20（世界 0.58 → 0.38） | 删掉的是只存在于世界 0.38 m 以上的东西 —— 桌面、货架边沿。机器人 0.25 m 高，从下面过去 |
| 地面贡献 | 20.9 里只占约 3% | 地面只占一层，span 正确滤掉 |

## 5. `min_wall_span_m` 是整条流水线里唯一的噪声过滤器

```python
occupancy_grid[end_voxel] += 0.2          # planning_kernels.py:82，命中一次 +0.2
np.clip(self.occupancy_grid, -0.2, 0.2)   # planning_node.py:799，上限就是 0.2
# build_obstacle_map: occ_threshold = 0.1
```

**上限 0.2 = 单次命中量。命中 1 次和命中 100 次的格子数值完全一样。**
累积证据被 clip 抹平，`occ_threshold` 区分不出命中次数。加上 `×0.99` 衰减（半衰期 14 s）：

> **一个坏像素就能造出一个障碍体素，并存活约 14 秒。**

所以 `min_wall_span_m = 0.2` 不只在滤地面，它在滤噪声，**而且是唯一在滤的**。
降到 0.1（27.9~44.3 格）会同时放进噪声 —— 这是它不能顺手改的原因。

想让 10 cm 的门槛可见，正确顺序是**先修噪声过滤**：

```python
np.clip(self.occupancy_grid, -0.2, 1.0, out=...)   # 上限抬到 1.0
occ_threshold = 0.9                                 # 需要 5 次命中
```

**然后** `min_wall_span_m` 才能安全降到 0.1。分两步，不要一次做完。

### 5.1 待验证：轮速位姿没有 roll/pitch，底盘倾斜会让地面在栅格里倾斜

```python
quaternion = quaternion_multiply(yaw_to_quaternion(theta), QUAT_BASE_CAMERA)
position   = [..., ..., float(offset[2])]     # z 是常数
```

`base_pose_to_camera_pose`（`omni3_kinematics.py:356`）产生的是**纯平面位姿：只有 yaw，z 恒定，无 roll/pitch**。
所以底盘物理上一倾斜，深度点会被当作没倾斜来投影 —— **地面在栅格里表现为倾斜的平面**。

量级：地面点在水平距离 `R` 处，俯仰误差 `θ` 使其垂直位移 ≈ `R·θ`。
`R = 2 m, θ = 2°` → 0.07 m；`θ = 5°` → 0.17 m —— **足以跨 1~2 层，从而伪造出 z_span**。

**这是「远场地面伪障碍」的候选机制，目前未验证** —— §4.3 的实测是静止在平地上做的，没有倾斜。
验证方法：**导航行进中**跑同一个探针，比较层分布与静止时的差异。

## 6. 局部分辨率 0.1 → 0.05：实测 ×5.66，已 mark 不做

板上实测（一帧真实深度 640×544、34.8 万有效像素，同一帧同一位姿，中位数）：

| | 射线投影 | 障碍图 | ESDF | 轨迹打分 | **合计** |
|---|---|---|---|---|---|
| **res = 0.10**（现网） | 5.0 ms | 5.6 ms | 2.3 ms | 1.2 ms | **14.1 ms** |
| **res = 0.05** | 19.0 ms | **52.8 ms** | 6.9 ms | 1.2 ms | **79.8 ms** |
| 倍数 | ×3.8 | **×9.4** | ×3.0 | ×1.0 | **×5.66** |

**代价不是延迟，是 CPU。** 规划周期实测 230 ms（≈4.3 Hz），深度输入 5 Hz = 200 ms/帧，
所以 230 ms 里计算只占 14 ms，剩下是等。加 66 ms 后计算 80 ms，仍在 200 ms 预算内 ——
**规划频率大概不会掉**，但：

```
每周期多 65.7 ms × 5 Hz = 每秒多 328 ms = +33% 一个核
planning_node 51% CPU → 约 84%
```

而满负载下 `/wheel/camera_pose` 已经从 42.3 Hz 掉到 23.3 Hz（−45%），整条链在抢 CPU。

**收益**（为什么值得记着）：量化项正比于格边长，`±0.141 → ±0.071`：

| | res 0.1 | **res 0.05** |
|---|---|---|
| 「最坏也不碰」需要的硬阈值 | 0.341 m | **0.271 m** |
| 对应的**一定能过的走廊宽** | **0.96 m** ❌ | **0.68 m** ✅ |

**瓶颈是 `build_obstacle_map`（×9.4）**，它对整个 z 带做了几个全栅格 `np.where` + `max/min`，全是临时数组。
真要上 0.05 先优化它，×5.66 不是下限。

都是 junlinp 加的；`0933d0d`（本仓库）只是把它们搬进独立文件。

## 8. 逃生舱与代价函数

### 8.1 代价函数里 ω 只作为惩罚，从不作为收益

```python
cost = score×100000 + 100×dist + 40×|Δvx| + 10×|Δω| + gate_penalty
                      ↑ 只看轨迹终点的 xy 位置
```

原地旋转的终点 = 起点 → `dist` 不变 → **转身收益 0**，同时 `10×|Δω|` 还要收钱。

目标在正后方 1.913 m、车静止时：

| 候选 | dist | 40×\|Δvx\| | 10×\|Δω\| | **总代价** |
|---|---|---|---|---|
| **站着不动** (0, 0) | 191.3 | 0 | 0 | **191.3** ← 最小 |
| 原地旋转 (0, 1.047) | 191.3（不变） | 0 | 10.47 | **201.8** |

**关键细节**：`last_param` 是上一周期选的。一旦转起来，`|Δω| = 0`，继续转最便宜。
**所以死锁是启动问题** —— 逃生舱的作用是强行踢出第一脚。

### 8.2 优先级链是四层，逃生舱在第三层

```
① 碰撞过滤   scores[i] == inf     → 从 admissible 剔除
② 门控       gate_penalty == 1e9  → 从 admissible 剔除
③ 逃生舱     escape_reason 非空 且 turns 非空 → 无视排序，强制指定一条原地旋转
④ 代价排序   argsort(costs)[0]
```

`if escape_reason and turns:` —— **`turns` 空时逃生舱静默失效**。
那次 23 秒死锁的日志是 `escape=blocked turns=1`：触发了，但没牌可打（§2.1）。

**所以「碰撞过滤 > 逃生舱」**，这是 §3.4 存在的理由。

### 8.3 `_escape_reason` 是顺序短路，`blocked` 优先级最高且不看距离

```python
if front_blocked:                  return "blocked"      # ① 不检查距离
if stand_dist <= 0.5:              return ""             # ②
if heading_err_abs > radians(80):  return "heading"      # ③
if best_gain < 0.05:               return "no-progress"  # ④
```

`blocked` 时**距离多近都转** —— 贴着障碍物不能因为离目标近就放弃转身。

### 8.4 `front_clearance` / `front_blocked`

`_clearance_along` 从车头前脸沿朝向每 10 cm 走一步、最远 0.5 m，横向同时查 3 条线（左边缘/中线/右边缘）。
`front_blocked = front_clearance <= 0.30`（`planning_node.py:984` 硬编码）为真时，
`_motion_gate_penalty` 把所有前进和弧线判 1e9，只放行原地旋转。

- 探到 0.5 m 都没碰到 → 返回 `1.50`，日志打成 `>0.50m`（**这是"没找到"标记，不是距离**）
- 前方通 + POI 在正后方 → 倒车门是 `0.0 if (front_blocked and allow_reverse) else 1e9` → **倒车被禁** →
  `_escape_reason` 返回 `"heading"` → 原地掉头。实机已验证（146°→0°，6 s）

### 8.5 main 的 force_turn 为什么不能照搬

main 在**控制器**里做（`cmd_vel_control.py`，PR #152）：

```python
heading_err = atan2(p[1], p[0])                       # 前瞻点在车体系里的方位角
if (not is_backward_segment) and abs(heading_err) > deg2rad(80):
    vx = 0.0; vyaw = clip(heading_err, ±max_angular)  # 硬停 + 原地转
elif vx > 0.0 and abs(heading_err) > 0.45:            # ~26°
    vx = 0.0; vyaw = clip(1.6 * heading_err, ±0.6)
```

不能移植的原因：
1. 我们的控制器被重写成**时间参数化 Samson 反步跟踪器**，`is_backward_segment` / `raw_vx` / `step_idx` 全部 grep 命中 0
2. **更要紧**：死锁时规划器发的是 **31 个重合点**的退化轨迹，`atan2(0,0)` 算不出 `heading_err`，控制器**根本不知道目标在后面**
3. `v_ref = w_ref = 0` 时反步增益 `k = 0`，控制器连转的能力都没有

所以借的是 **80° 阈值和「先转再走」的思路**，落点放在规划器 —— 那里能直接看到目标位姿。

main 的倒车门是硬互斥：`should_reverse = front_clearance <= 0.30`，
**触发条件是前方受阻而不是目标在后**，所以它结构上不可能倒车去后面的 POI。

## 10. `T_from_map_to_odom` 为什么要用 SE3 优化而不是直接用重定位的 T

`map_node.compute_transform_from_map_to_odom`（`:1240`）。

**单次重定位给的 T 就是这个优化里的一次观测**：

```python
观测 = camera_in_odom_world @ se3_inv(camera_in_map_world)   # map_node.py:1254
```

优化器不做别的，它在**融合很多个这样的 T**。原因是单次的噪声太大 —— 本仓库自己的实测注释
（`map_node.py:888`）：

> relocalization alone moved the reported position **0.15 m** while the wheels stood still

**轮子一动不动，单次重定位报的位置能跳 15 cm。** 而这个位置直接喂给 POI 到达判定（半径 0.4 m）
和全局路径搜索 —— 15 cm 抖动会让到达判定反复翻转、每次重定位都重规划一条不同的路。

| 优化解决什么 | 怎么做 |
|---|---|
| 降噪 | 最多 100 次观测的加权最小二乘，误差按 ~1/√N 下降 |
| 按可信度加权 | 权重 = `relocalization_pose_weights`（那次重定位的协方差），匹配好的说话更响 |
| 不跳变 | 热启动：上次的解当这次的初值 |
| 跟踪漂移 | 滑动窗口只留最近 100 个（`[-100:]`），旧观测自动淡出 |

**为什么必须在 SE3 流形上**：旋转矩阵不能逐元素平均（结果不正交、行列式不为 1），
四元数逐元素平均也不行（要归一化，且有双覆盖符号问题）。
正确做法是把误差写成 `log(T_估计⁻¹ · T_观测)`（切空间 6 维向量），在切空间做最小二乘，再 `exp` 回流形。
`pose_graph_solve` 是 C++ 绑定（`tinynav.tinynav_cpp_bind`，Ceres 风格）。

结构是两节点位姿图，只有一个自由节点，所以它其实是**加权的 SE3 均值**，不是真正的图优化：

```
节点 0 = T_from_map_to_odom   ← 自由
节点 1 = 单位阵               ← 固定（constant_pose_index_dict = {1: True}）
边     = 最近 100 次重定位各一条，权重 = 协方差 × [10,10,10]
```

### 10.1 起步阶段确实会跳 —— 而且没有跨次热启动

| 阶段 | 状态 |
|---|---|
| 首次重定位成功前 | `T_from_map_to_odom is None` → `try_publish_nav_path` 直接返回（`:1287`），**完全没有导航路径** |
| 第 1 次成功后 | 只有 1 个约束 → 解**就是**那一次的单次 T，**15 cm 噪声全部保留** |
| N 次后 | 约 `15/√N` cm：4 次→7.5 cm，16 次→3.8 cm，100 次→1.5 cm |

重定位成功率实测 0.5 次/秒量级，所以：

> **约 30 秒后才降到 4 cm；填满 100 的窗口要约 3 分钟。**

🔴 **而且 `relocalization_poses.npy` 只保存、从不加载** —— `map_node.py:1219-1220` 写盘，
但 `:351-368` 的加载列表里没有它。所以**每次启动窗口都是空的，这个收敛过程每次都要重走一遍**。

**可改进项（未做）**：启动时加载 `relocalization_poses.npy` 把窗口预填。
要注意的是里程计 datum 每次启动都重置（从 0 开始），所以存的 `camera_in_odom_world` 跨次无效 ——
需要存的是**观测**（`T_from_map_to_odom` 本身）而不是两个位姿，或者干脆只把上次的解当初值。

## 11. 同步丢帧：不是同步问题

上一轮报告 `/slam/depth` 只有 3.35 Hz（原始 depth 5 Hz），一度归因于
`ApproximateTimeSynchronizer` 的 `sync_queue_size=3` 太小。**实验推翻了。**

探针（`tool/x5_board/sync_loss_probe.py`，第四观察者，只读）：

| 指标 | 值 |
|---|---|
| STAMP INFEASIBLE | **0%** |
| depth 与 infra1 时间戳距离 | **0.0 ms**（逐字节相同） |
| depth 与 pose 时间戳距离 | 14 ms p50 / 26 ms p95 |
| depth 比自己的时间戳晚到 | 215 ms p50 / 329 ms p95 |

A/B（`/slam/depth` 保留率）：

| 配置 | `/slam/depth` | 原始 depth | 保留率 |
|---|---|---|---|
| VIO 位姿（精确同步）queue=3 | 5.088 Hz | 4.979 | **100%** |
| VIO 位姿 queue=10 | 5.099 Hz | 4.979 | **100%** |
| 轮速位姿（近似同步）queue=3 | 4.999 Hz | 4.976 | **100%** |
| 轮速位姿 queue=10 / 20 | 4.935 / 4.977 | 4.976 | 99% / **100%** |
| **满负载 app** | **5.129 Hz** | 5.058 | **100%** |

**`sync_queue_size` 对丢帧毫无影响，同步机制也毫无影响。** 3.35 Hz 是 load 9.17 时
（`map_node` + `cmd_vel_control` 也在跑）的一次瞬态 CPU 饿死。

探针为什么"支持"了错误结论：它是个**轻载观察者**，测的是自己进程里的到达顺序，
而 bridge 那个 101% CPU 的进程里回调调度完全不同。**把观察者的时序当成了被观察者的时序。**

最灵敏的「全链路饿死」指标是 **`/wheel/camera_pose`**：单独跑 42.3 Hz，满负载 23.3 Hz（**−45%**）。
它的工作量恒定（50 Hz 读舵机），速率下降只能由抢不到时间片解释。

## 15. 局部视图的画布原点：箭头画在相机上，圆圈画在控制中心

局部视图里除了画布原点，**其余每一层都是绕控制中心的世界坐标** ——
footprint、trajectory、occupied voxels、global path。而画布原点来自 `/slam/odometry_visual`，
那是**相机**的位姿，在 LeKiwi 上位于中心前方 60 mm、左侧 50 mm。

```
planning_painter.dart:57   _drawRobotArrow(canvas, Offset(cx, cy), pose.yaw)   ← 箭头钉在画布中心 = 相机
planning_painter.dart:161  cx + (footprint[i].x - pose.x) * scaleX             ← 圆圈绕控制中心
                                                                                 → 差 78 mm
```

所以箭头被画在自己 footprint 圆圈中心外 78 mm 处，在 0.20 m 半径上看就是**明显偏左**；
轨迹起点也显得不在机器人身上。`operate_tab` 长按设目标用的是同一个 `odom_pose`，
所以**点下去的位置也偏 78 mm**。

修法：只在构造 planning 快照时把位姿平移到控制中心（`node_manager._to_control_centre`）。
`current_pose` 和 pose callbacks **保持相机位姿** —— 地图是用相机位姿建的、POI 也记在相机位姿里，
动它们会让每个已记录的 POI 偏 78 mm。

**前端零改动**：所有层都是 `x - pose.x`，一起平移即可；长按目标自动跟随。

用的就是 planning 的 `camera_to_robot_center` 和 `cmd_vel_control` 的 `robot_pos`，
三处现在按构造一致。对 `base_pose_to_camera_pose` 在三个朝向上往返验证，误差 **0.000 mm**。

实测（`/ws/planning` 一帧）：

```
canvas origin (odom_pose) vs footprint centroid = 0.0 mm     改前 78 mm
trajectory[0] vs canvas origin                  = 0.0 mm     改前 78 mm
footprint 16 点，半径 min=0.200 max=0.200
```

⚠️ **对导航避障零影响** —— 整条导航链本来就一致地用控制中心：

| 位置 | 用的是 |
|---|---|
| `generate_trajectory_library_3d(init_p=...)` | `camera_to_robot_center(T)` |
| `score_trajectories_by_ESDF` 的 ESDF 查询 | 轨迹点 = 控制中心 |
| `_clearance_along(center, ...)` | `camera_to_robot_center(T)` |
| `cmd_vel_control` `:441` | `self.position - self.rotation @ self._cam_offset_3d` |

**只有显示端用的是相机。** go2 的 `camera_y = 0`，所以它只有 0.2 m 的纵向偏移、没有横向偏移 ——
这就是为什么在 go2 上看起来「在正中心」。

## 16. 轨迹 seed：预测喂预测，已按 main 删除（2026-08-12）

规划的起始位姿本来不是测量值，而是**上一周期自己发出的轨迹**上采的一个点（seed），用来补偿
0.37 s 的感知延迟。放行判据只有一条 —— 预测与实测的 **xy 距离**小于阈值。

### 两个后果

**位置**：预测喂给下一次预测，测量值只在超阈值时才插得进来，是一个没有反馈的开环积分器。
8-12 实测行驶期间呈干净的锯齿波，发散速率中位数 **0.103 m/s**（车速的 53%，主因是车跟不上
指令的角速度），`seed_err` 中位数 **0.29 m**、最大 0.52 m —— 超过 0.20 m 的碰撞包络，也就是
碰撞打分跑在一个车并不在的位姿上。

**朝向**：判据里没有朝向项，而**原地转向的位置差恒等于 0**，所以那道闸门永远拦不住它。只要
指令发出没被执行（暂停、舵机丢包、转速低于死区），朝向就纯开环发散，实测约 **55°/s**，且
`-25° / -83° / -134°` 的序列在两次重置后逐字重现 —— 确定性重放的指纹。

### 为什么直接删掉，而不是补一个朝向判据

| | main | 本分支（改前） |
|---|---|---|
| 规划起点 | `init_p = camera_to_robot_center(T)`，直接用测量 | seed |
| 延迟补偿 | 只在控制器：`lookahead_steps = 1` | 规划器 + 控制器，**两遍** |

`grep latency\|predict\|lookahead\|extrapolat` 在 main 的 `planning_node.py` 上 **0 命中**。seed 来自
junlinp 的 `01bc430`（2026-06-02），**从未合进 main**。同一天同一人写的离线回放工具
`tool/planning_bag_viser.py` 里**有** 15° 的朝向闸门（`seed_fallback_rotation_rad`），线上节点漏了。

而我们的控制器比 main 的更强：`cmd_vel_control` 用 `query_t = now + 0.15` 在轨迹的时间轴上二分
查找，是完整的时间参数化跟踪。**延迟已经在下游补过一遍，规划器里那层是重复的**，而且是全链路
唯一引入累积误差的一层。

改后轨迹起点锚在采集时刻（now − 0.37 s），控制器索引到第 0.52 s 的点（改前是第 0.32 s）；轨迹
长 3.0 s / 31 点，两者都远未到期。误差上界从「锯齿到 0.5 m」变成 **7 cm 且不累积**。净 −72 行。

### 顺带修掉的两处

- `cmd_vel_control` 的 `received stale` 是**警告不是拒绝**，但它和 accepted/ignored 那行**共用
  同一个 1 Hz 限流器**，每周期都触发的警告把 accepted 挤没了 —— 这就是 `nav_health` 报
  `0 fresh / 54 stale` 的来源，读起来像「路径全被丢了」，实际一条没丢。已拆成两个限流器，警告
  阈值提到 1.0 s（远超感知延迟，远小于 3 s 轨迹跨度）。
- `nav_health.sh` 那行改成 `accepted / ignored / expired / lag-warnings`。

## 20. 前视探针：点采样根本不可能无缝，已改成投影（2026-08-12）

现象由用户报出：正前方放一个水杯，面板 `clearance 0.30 m at robot` 正确，
`front obst` 却是 `clear`。加密采样后仍然复现。

### 原实现（与 upstream main 逐字相同，来自 #124）

`_clearance_along` 沿朝向走 6 步，每步横向取 3 个点，共采 **18 个格子**：

```python
for w in (-hw, 0.0, hw):      # LeKiwi hw=0.20 m；main 的 GO2 hw=0.15 m
```

两级漏检，第二级是致命的：

**① 横向线距 > 分辨率。**LeKiwi 三条线间距 0.20 m，栅格 0.10 m。车心在
`(49, 50)`，车身横跨 y 列 `48..52`，探针只落在 `48/50/52` —— **`49` 和 `51`
两列从来没被查过**，即中线左右各 0.10 m。GO2 同理（0.15 m 间距 > 0.10 m）。
正面摆位实测 **40 处漏检**。

**② 采样格随车旋转，栅格不转。**把横向改成一条线一列（5 条）后，正面 0 漏检，
但斜向仍然漏 —— 沿旋转方向走一格的步长，在轴对齐栅格上会斜着跳过格子：

| 朝向 | 走廊内格子 | 漏检 | 最近的漏检（车壳外） |
|---|---|---|---|
| 0° / 90° | 20 | 0 | — |
| 30° | 20 | 3 | **0.03 m** |
| 45° | 24 | 3 | 0.07 m |
| 55° | 21 | 4 | 0.15 m |

**加密采样只能把缝变窄，不能消除。**

### 为什么不只是显示问题

`front_clearance` 驱动 `front_blocked` 门，而它是 `_escape_reason` 的第一个判据：

1. `front_blocked = False` → `_escape_reason` 返回 `""` → **原地转向逃逸不触发**
2. 轨迹打分用 ESDF（`hard_clearance = 0.30 m`，从车心），障碍在 0.32 m 处，
   任何前进一格的轨迹都跌破阈值 → 全判碰撞
3. 日志写 `gate=forward only` 而所有前进轨迹在碰撞 → **车既不前进也不转向**

"莫名停住"的一条独立成因，与第 15 节的规划延迟、第 18 节的路径折叠都不同。

### 修法：投影，不采样

把窗口内每个障碍格投影到朝向轴上，取走廊内 `along` 的最小值：

```python
along   = dx * fx + dy * fy
lateral = dx * -fy + dy * fx
in_corridor = (np.abs(lateral) <= hw + 0.5 * self.resolution) & (along >= fl)
```

`+ 0.5 * resolution` 的松量：`lateral` 量到格心，格心刚在走廊外的格子仍与走廊
重叠，而旧代码的 ±hw 采样点会落进这种格子 —— 加上它才是等宽平移，不会悄悄把走廊
收窄，`front_blocked_m` 的调参含义不变。

**全朝向 0 漏检。**

### 为什么要开窗口 —— 代价确实变了

采样是 O(步数×线数)，与杂乱程度无关；投影是 O(障碍格数)。板上实测（单次调用）：

| 障碍格数 | 采样 | 投影全图 | 投影+窗口 | 对采样 |
|---|---|---|---|---|
| 0 | 200 µs | 121 µs | **52 µs** | 0.26× |
| 60（典型办公室） | 189 µs | 435 µs | **357 µs** | 1.89× |
| 600 | 189 µs | 653 µs | **436 µs** | 2.30× |
| 10000（全满） | 17.5 µs | 3471 µs | **536 µs** | 30.6× |

走廊最远只到车心外 `fl + max_dist = 0.70 m`，先切一个约 15×15 的窗口再投影，
最坏情况就从 3.5 ms 封到 0.54 ms。`_clearance_along` 每周期最多调 16 次
（1 次前向走廊 + 最多 15 个逃逸转向候选），所以典型代价约 5.7 ms / 250 ms 周期，
比原来多 2.7 ms。**这是原实现选点采样唯一说得通的理由，而开窗口之后它不再成立。**

## 21. 墙上的洞是取样稀疏，不是膨胀不够（2026-08-26）

`self.step = 10` 表示深度图**每 10 个像素取一条射线** —— 640×544 里只有 1% 的像素
被投射。板上拿一帧真深度离线重跑，以 `step=2` 为参考真值：

| step | 射线数 | 板上稳定用时 | 0–1 m 召回 | 1–2 m | 2–3 m | 3–4 m |
|---|---|---|---|---|---|---|
| 10（原值） | 3456 | 4.3 ms | 94.2% | **55.9%** | **42.0%** | 55.3% |
| 8 | 5440 | 6.1 ms | 96.5% | 66.7% | 54.0% | 57.9% |
| **5（现值）** | 13824 | **14.0 ms** | 98.8% | **72.1%** | **68.0%** | 63.2% |
| 3 | 38553 | 37.6 ms | 97.7% | 81.1% | 80.0% | 71.1% |
| 2 | 87040 | 81.5 ms | — | — | — | — |

叠上「一格要连续两帧才越阈值」：单帧召回 55% 意味着两帧联合只有约 30%，格子很可能
**永远**不越阈值。这就是「墙上一堆洞 / 漏检」的机制。

🔴 **膨胀和取样步长是同一个洞的两种补法，代价完全不同。** 膨胀每格要多 0.1 m/侧的
过道净宽（十字元素，对角只 0.041 m），窄过道正好最缺这 0.2 m；step 5 付的是
10 ms / 250 ms ≈ 4% 的 CPU，一分净宽都不付。**填洞要动 step，不要动膨胀。**

⚠️ 这翻转了 §「两个候选机制已被闭环仿真证伪」里对 `step=10` 的结论：那个仿真用理想
深度 + 大块规则几何，墙面每条射线都命中，看不出稀疏。真实场景里斜墙、杂物、细物件让
step 直接体现为**洞的密度**（不是探测距离）。**验取样密度必须用真深度帧。**

## 22. 办公椅脚轮：z 跨度判据结构上看不见它（2026-08-26 / 27）

星形底盘的腿离地 **4~8 cm**，而体素是 0.1 m —— 腿和地面落在**同一层**，
`z_span = (最高层 − 最低层) × 0.1 = 0`。`min_wall_span_m` 调成 0.2、0.1 甚至 0 都一样，
**它永远进不了障碍图**。这不是门限问题，是表示能力问题。

而且体素层边界在**世界 z 的 0.1 整数倍**上（栅格重定心只按整格滚），地面的世界 z =
相机 z − 0.178，**相机 z 是 VIO 给的、会漂** —— 所以「地面落在层内哪个位置」是随机
且缓慢变化的。相位差的时候地面自己就横跨两层，此时 `span=0.1` 会把地面当障碍。
**这就是矮障碍时灵时不灵的原因，也是 `min_wall_span_m` 留在 0.2 的原因。**

### 修法：独立的离地高度通路

`low_obstacle_hits`（`planning_kernels.py`）统计每个 xy 格里**离地 5~25 cm** 的深度点数，
结果 OR 进障碍图，绕开 z 量化。地面有多干净（只取确定是空地的格，不预裁剪）：

| 距离 | p50 | p90 | p99 | max |
|---|---|---|---|---|
| 0.3–1.0 m | +0.2 cm | +0.5 cm | **+1.2 cm** | +14 cm |
| 1.0–2.0 m | −0.0 cm | +1.0 cm | **+2.6 cm** | +6.7 cm |
| 2.0–3.0 m | **+4.5 cm** | +7.3 cm | +8.4 cm | +8.4 cm |

2 m 之外那 +4.5 cm 是**系统性**的（相机俯仰或深度偏置），不是噪声 —— 所以
`TINYNAV_LOW_OBS_RANGE_M = 1.5`。门限扫描（1.5 m 内 71 个空地格）：

| 门限 | ≥1 点 | ≥3 点 | ≥5 点 | ≥8 点 | 空地误报 |
|---|---|---|---|---|---|
| 4 cm | 49 | 34 | 32 | 26 | **0 / 0 / 0 / 0** |
| 5 cm | 46 | 33 | 31 | 26 | **0 / 0 / 0 / 0** |
| 8 cm | 43 | 31 | 28 | 23 | **0 / 0 / 0 / 0** |

### 「点」是深度像素，不是体素 —— 所以最少点数不能是定值

格子是 0.1 m，点是 `step=5` 抽样后的**深度像素**，所以一个格子收到多少点按 1/d² 掉：

| 距离 | 满格正对相机 | **4 cm 宽的椅子腿** |
|---|---|---|
| 0.5 m | 153 点 | 约 24 点 |
| 1.0 m | 38 点 | 约 6 点 |
| 1.2 m | 27 点 | **约 4.3 点** |
| 1.5 m | 17 点 | **约 2.7 点** |

🔴 **`min_pts=5` 等于在 1.1 m 之外把椅子腿整个丢掉**（2026-08-27 实测：那一帧
0.75–1.25 m 的触发格有 36–42% 不足 5 点，这解释了「避障好一点但还是撞椅子脚」）。
**已改成 2**：空地那边不需要 5 的余量（上表全零误报），而「连续两帧才算」本身已经把
单点飞点滤掉。

### 「厘米级」只在高度这一维成立

门限 5 cm、地面噪声 1.2–2.6 cm，高度判别确实是厘米级的；**但平面上仍然是 0.1 m 的
格子**，一个脚轮占 1 格，位置精度没变。这条判据买到的是「以前完全看不见的东西现在
看得见」，不是「定位更准了」。

### 占据栅格清得有多快（常被记错）

上限是 **0.2 不是 1**（`clip(±0.2)`），每帧贡献也夹在 `±0.1`，判据是 `> 0.1` 严格大于：

| 情形 | 算式 | 多久不再是障碍 |
|---|---|---|
| 射线穿过它（看到那儿空了） | 0.2×0.99 − 0.1 = 0.098 | **1 帧** |
| 没人再看它（走出视野） | 0.2×0.99ⁿ ≤ 0.1 | 69 个周期 ≈ **16 s** |

「帧」是**规划周期（深度帧，约 4.3 Hz）**，不是关键帧（约 0.67 Hz）。按关键帧算会把
16 s 高估成 100 s 以上。

# 2026-09-02 更新：z 带定案 + 「顶着障碍走」的解释

## 1. z 带参数已定案：`zbot=-0.11` / `span=0.05` / 矮障碍层关

前面那一节的「虚空障碍」根因是**栅格 z 相位**：`planning_node.__init__` 里
`origin = grid_shape * resolution / -2 + grid_offset`，**不含位姿项**，而
`roll_occupancy_grid` 按整格 roll，所以 origin 永远钉在同一个格阵上。相机 z=0.124 时
`origin[2]` 落到 −0.10，层中心是 −0.075 / −0.025 / +0.025 —— **一条层边界正好压在地面上**，
地面被劈成两层、再加向下的噪声就是三层，`z_span = 2×0.05 = 0.10 m` **正好等于旧门限**。

修法不是抬门限，是**先把地面移出波段**：

| `zbot`（离地） | `span` | 空地误报（4 个 z 相位） | 椅脚「矮」检出（4 相位） |
|---|---|---|---|
| −0.076 | 0.05 | 🔴 91/81/59/60 | 46/74/36/30 |
| −0.076 | 0.10 | 🔴 23/0/0/0 | 13/29/13/10 |
| −0.076 | 0.15 | ✅ 0 0 0 0 | 4/8/0/0 |
| −0.076 | 0.20 | ✅ 0 0 0 0 | **0/0/0/0（全瞎）** |
| **−0.11（离地 +0.014）** | **0.05** | **✅ 0 0 0 0** | **25/15/9/7** |
| −0.11 | 0.10 | ✅ 0 | 5/1/0/0 |
| −0.11 | 0.15 / 0.20 | ✅ 0 | 0/0/0/0（全瞎） |

🔑 **`span=0.05` 之所以安全，完全是因为 `zbot` 先把地面切出去了**：波段下界在世界
+0.014 m，地面只落在 +0.025 这一层 → 跨 1 层 → `z_span = 0`，门限调到 0 它也过不了。
`span=0.05` 只要求「比地面那一层高出一层」≈ 5 cm 以上的真实结构。

⚠️ **依赖地面在每个格里只占一层**：实测格内高度跨度 p90 = 0.015 m ✅。
但 `zbot=-0.14` 只差一个相位（+0.013）地面就占两层、误报 23 格 —— **所以必须扫相位**。

**矮障碍层（`TINYNAV_LOW_OBS`）已默认关**：仿真里它贡献 0 格（z 跨度单独就抓到椅腿），
板上贡献 185/243 格（76%）—— 硬件上加的全是噪声。它的判据下限 0.05 m 比误差预算还小
（俯仰固定偏置 1.38° 在自己 1.5 m 量程上就是 0.036 m）。

**离线复现工具**：`tool/x5_board/capture_depth_scene.py` 抓深度序列到 npz，
`tool/x5_board/replay_obstacle_map.py` 导入**真实**的 `run_raycasting_loopy` /
`build_obstacle_map` / `roll_occupancy_grid` 重放并扫参数。
⚠️ 它必须复现板上的 z 相位（origin 初始化**不加位姿**、按整格 roll），否则得到的是
「层中心压地面」这个更干净的相位，虚空障碍复现不出来 —— 这个坑我踩了两次。

## 2. 🔴「直接顶着障碍物走」：5 cm 是设计值，门限没失效

启动行的几何：`circle r=0.1175m hull=0.122m safety_r=0.05m hard/soft=0.17/0.27m`。

**更正上一节的一句话**：门限**不是** `front_clearance >= vx × reaction_time_s`。实现是

```
forward_ok[i] = prefix_clear[i] >= _prefix_gate_m()
_prefix_gate_m() = robot.hard_clearance = 0.17 m     ← 恒定值，不随速度变
prefix_clear[i]  = 这条轨迹前 2.0 s 那一段上，圆盘中心的最小 ESDF
```

速度是通过「前 2 秒扫过多远」进来的，门限本身恒是 0.17 m。而门限查**圆盘中心**、
半径已经算在门限里，所以：

```
允许的车壳到障碍格距离 = 0.17 − 0.1175 = 0.052 m
栅格 0.05 m 半格量化   = ±0.025 m      → 实际 2.5 ~ 7.5 cm
```

现场实测那 18 秒 `front_clearance` 从 0.39 一路降到 **0.07 / 0.03 m**，全程 `fwd_ok>0`
—— **一次都没违反门限**。`front_clearance` 是从**车壳面**量的（`_clearance_along`），
所以 0.07 就真的是车壳离障碍 7 cm；而 `esdf_at_robot` 是从**中心**量的，同一时刻 0.21。
⚠️ **这两个数基准不同，不能互相校验。**

### 抬 `safety_r` 的代价（过道净宽 = 2 × (0.1175 + safety_r)）

| `safety_r` | 车壳留空 | 需要过道净宽 | 后果 |
|---|---|---|---|
| **0.05（现在）** | 5.2 cm | **0.335 m** | 看着贴墙，窄缝过得去 |
| 0.08 | 8 cm | 0.395 m | 0.40 m 过道擦边 |
| 0.10 | 10 cm | 0.435 m | **0.40 m 过道过不去** |

⚠️ **0.10 等于把一个已修的 bug 用参数重新引入**：`_prefix_clearance` 原来按外接方形取
四角，等效就是 0.435 m 净宽，实测 0.40 m 过道被判成堵、90 条前进轨迹只放行 6 条
（改成查中心后 30 条）。**抬之前必须先量场地最窄处。**

## 3. 楔住时的行为（真车已验）

fwd_ok  71/90 → 43 → 37 → 28 → 21 → 5 → 0/90

## 4. 🔴 位姿是严格平面的，仰起来地板会整片变障碍（未修）

`wheel_odometry_node` / 固件位姿 `z = 0.0`、四元数只有偏航，**roll/pitch 恒为 0**。
车骑上东西真的仰起来时位姿说自己是平的，射线投影把地面整片抬起来。而 `zbot=-0.11`
只在地面上方 **0.014 m**：

```
仰 1° → 0.80 m 外的地面进波段      仰 2° → 0.40 m      仰 3° → 0.27 m
```

单纯斜面每格仍是 1 层，但车**摇**的时候同一格被写进两个高度，栅格 16 s 的记忆叠成
2 层 → 跨度 0.05 → 障碍。这解释了 `blocked` 在 96 和 9 之间整片翻、以及事故后
12~16 秒的持续时间。

**能修但还没修**：`/camera/camera/imu` 的加速度计直接给重力方向 = 俯仰/横滚，不用积分。

# 2026-09-04：射线投射拆成 hit/carve，z 相位定案，判决图 + 调参工具

## 1. 🔴 密集刻空在删掉真实障碍

`run_raycasting_loopy` 用**同一个 `step`** 同时控制两件事：沿射线刻空闲（每个体素 `-0.05`）和标命中（终点体素 `+0.2`）。一条 2 m 的射线要写约 40 个体素，其中只有 1 个是命中 —— **97% 的算力在刻空**。

而两件事需要的取样密度完全相反：
- **命中要密**：稀了漏矮东西和远处地面
- **刻空不需要密**：相邻射线刻的几乎是同一批体素，纯重复劳动

拆开之后（`tinynav/core/raycast_split.py`，两遍循环各一个 step）实测，板上真录数据 `data/obstacle_scenes/`：

| 配置 hit/carve | PC ms/帧 | 椅子那侧障碍格 | 5–10cm 波段 | 空地录像 <1m 假障碍 | 地面层覆盖 1~1.5m |
|---|---|---|---|---|---|
| 3/3（原状） | 5.1 | 94 | 56 | 0 | 3% |
| **3/8（已上板）** | 1.5 | **208** | **85** | 0 | 8% |
| 4/8 | 1.2 | 177 | — | 0 | 8% |
| 5/10 | 0.8 | 173 | 70 | 0 | 6% |
| 6/12 | 0.6 | 158 | 62 | 0 | 7% |

🔑 **`3/8` 的命中密度和 3/3 一样，召回却翻倍 —— 增益全部来自"少刻空"。** 相机只有 12.4 cm 高，看远处地面几乎是平的，掠射线横穿近处地面所在的那一层，把地面自己的回波抹掉。

| 层 k | 世界 z | 离地 |
|---|---|---|
| 1 | −0.050 ~ **0.000** | −5 ~ 0 cm |
| 2 | **0.000** ~ 0.050 | 0 ~ 5 cm |
| 3 | 0.050 ~ 0.100 | 5 ~ 10 cm |

一条 7 cm 椅子腿（跨度门限 0.10）：地面落 k=2 → 占据 {2,3} → 跨度 **0.05，被否**；地面落 k=1 → 占据 {1,2,3} → 跨度 **0.10，认了**。**认不认由 ±1 mm 噪声决定，而且每个格子各自随机。**

`0.1625` → `origin_z = −0.0875`，地面落在 k=1 正中间（两边各留 12.5 mm）→ 恒定落 k=1，**最小可见高度从「50 mm 但不稳」变成「63 mm 稳定」**。

⚠️ **改的是 `/userdata/x5/env.sh` 不是 `app_start.sh`**：service 跑的是 `tinynav/tool/x5_board/app_start.sh`，那份里写着 `RAYCAST_STEP:-5` / `CAMERA_HEIGHT_M:-0.18`，而实际生效是 3 和 0.124 —— 因为 `env.sh` 在它之前 source，`${VAR:-默认}` 让 env.sh 赢。**改错文件白改一轮。**

### 两项改动各自贡献多少（受控 A/B，同一段录像 250 帧）

| 配置 | 障碍格 | 矮物被否 | 最小可见 |
|---|---|---|---|
| 基线 `0.15 / 3-3` | 151 | 151 | 50 mm（不稳） |
| 只改 z 相位 `0.1625 / 3-3` | 169 (+12%) | 248 | **63 mm 稳定** |
| 只改 carve `0.15 / 3-8` | **325 (+115%)** | 200 | 50 mm |
| **两项都改（现役）** | **358 (+137%)** | 376 | 63 mm |

**障碍格涨 2.4 倍，其中 87% 来自 carve，z 相位只占 12%。** 代价：全局路线与实时障碍图的冲突从 22% 涨到 **55%**（`ROUTE-UNPINNED`），见 `planning_cost.md`。

## 3. z 跨度判据：只看 max 和 min，中间空洞完全不管

```python
occ_high = np.where(band_occ, z_idx, -1).max(axis=2)
occ_low  = np.where(band_occ, z_idx, n_z).min(axis=2)
z_span   = (occ_high - occ_low) * resolution     # 只有这两个数进来
obstacle = has_occ & (z_span >= config.min_wall_span_m)
```

`min_wall_span_m = 0.10` + `res = 0.05` → **`hi − lo ≥ 2`**，即"最高层和最低层序号差 ≥ 2 = 横跨 3 层，但只需 2 层真被占据"。`{1, 3}` 就够，第 2 层空着也算。

板上真数据：**99 个障碍格里 68 个（69%）的占据层是不连续的**，跨度 ≥4 层的**全部**不连续（跨 7 层只占 4 层）。这是刻意宽松 —— 地面回波 + 高处一个点就能凑出跨度，墙和桌腿正是这么被认出来的。空地录像近场假障碍实测 0，所以现在没造成问题。

波段（diffcar，相机系 `[−0.16, +0.40]`，相机高 0.124）= **离地 −0.036 ~ +0.524 m**，参与的层是 k=1..11 共 11 层。

## 4. 判决图（`/planning/height_color`）

替换了原来的离地高度配色。它答的是「**这块地方被 z 跨度判据判成什么、没判成障碍的话卡在哪一步**」。

| 颜色 | 名字 | 判据 |
|---|---|---|
| 近黑 | 无效 | `depth <= 0` |
| 灰 | 栅格外 | 投影出的 (i,j) 在车周 ±2 m 框外 |
| 🔵 蓝 | 波段外 | **本像素自己的 z** 在离地 −0.036~+0.524 之外 → 不参与判断 |
| 🔴 红 | 障碍 | 该列有占据 **且** 跨度 ≥ 0.10 m |
| 🟣 洋红 | 矮物被否 | 该列有占据、跨度不够，但最高占据层离地 > `verdict_low_h`(0.03) |
| 🟡 黄 | 只有地面 | 同上但最高占据层离地 ≤ 0.03 |
| 🟢 绿 | 栅格不认（还在攒） | 该列波段内无占据，本像素那个体素累加值 0~门限 |
| ⬛ 暗青 | 栅格不认（被刻空） | 同上但累加值**为负** = 栅格主动认定它空 |

赋值顺序后覆盖前：波段外 → 绿/暗青 → 黄 → 洋红 → 红（**红优先级最高**）。

### 🔴 修掉的两个 bug

**(1) 波段外的像素继承了它那一列的判决。** 原代码里"波段外"只在该列没占据时才涂得上，于是桌面/椅背（离地 >0.52 m，本来不参与判断）继承了它那一列（只有地面）的黄色。实测 **1145 个像素（离地中位 0.61 m）被涂错 = 69% 的波段外像素**。修法：先整片涂"波段外"，后面每条按格子的赋值都必须带 `judged = inside & px_in_band`。

**(2) 绿色原来叫「空（真空）」—— 那个名字是错的。** 有像素就说明这一帧真有回波，`judged` 又保证回波落在波段内，所以"该列没占据"只能意味着**栅格不认本帧的观测**。图里根本不存在"确认是空"这一类。按体素累加值分两档后实测：**1.5~2 m 的地面像素 87% 是"被刻空"**，只有 1% 是"还在攒"。这直接把 §1 那个掠射线问题画出来了。

### 平涂读不出来，必须薄涂在红外底图上

第一版是大块纯色平涂，**没有任何实物轮廓，对不上现实里哪个东西被判成了什么**。现在：红外图当底 + 逐类薄涂强度（`_VERDICT_ALPHA`，要看的两类涂 0.72/0.92，其余压到 0.16~0.35）+ 底部 8 格色标条。"矮物被否"从橙改成**洋红** —— 红和橙在薄涂下分不开，而"障碍 vs 被否"正是要看的那一组对比。

⚠️ **代价**：红外底图要多订阅一个 20 Hz 的 640×544 话题，板上实测**一个什么都不做的裸订阅者 = 13.9% 一个核**，而判决图只用其中 1 Hz 一帧。`TINYNAV_VERDICT_BASE=depth` 退回深度当亮度（免费，但只有轮廓没纹理）。没有更便宜的红外源：`keyframe_image` 只有 0.66 Hz，运动时底图会比判决图旧 1.5 s。

**导航档 vs 调参档**：

| | STRIDE | HZ | VERDICT_BASE | 每周期摊到的代价 |
|---|---|---|---|---|
| 导航 | 4 | 1.0 | infra | ~5 ms |
| 停车调参 | 2 | 2.0 | infra | ~26 ms |

板上逐段实测（stride=2 共 64 ms）：`classify_verdict` 34.9 + `tint_verdict` 17.8 + 投影 9.4 + 底图 0.9 + 出消息 0.9。stride=4 降到 23.9 ms。

## 6. 🚫 试过但失败的路：逐体素 gather

想法是不再让每条射线走一条线往算出来的地址写（scatter），而是让每个体素把自己投到深度图查一次（gather）—— 没有 scatter、没有写冲突、没有分支，且形状规则。**实测两个维度都更差，已放弃**：

| 配置 | PC ms/帧 | 障碍格 | 与现状 IoU | 现状有它没有 |
|---|---|---|---|---|
| scatter 3/3 | 5.1 | 99 | 100% | 0 |
| gather ε=.025 | **8.7** | 19 | 17% | **82** |
| gather ε=.05 | **8.3** | 48 | 36% | **60** |
| gather ε=.10 +minpool3 | 29.5 | 171 | 40% | 22 |

- **速度**：numpy 里 89,600 个体素要过十几个临时数组 + 一次花式索引 gather，比 numba 里 120 万次**顺序**写还贵
- **精度**：判据 `|z − D| ≤ ε` 里 z 是体素中心在相机系的深度。对**掠射面**根本不成立 —— 体素中心比地面高 2.5 cm，它那条视线要走远得多才碰到地面，`z − D` 是个大负数 → 被判成空，把地面自己抹掉。地面层覆盖从 25%/12% 崩到 2%/3%
- ε 拉到 0.10 能救回覆盖，但那时是"±10 cm 内一律算占据"= **把 z 分辨率丢一半**，而 z 分辨率正是跨度判据的全部依据
- 要做对得让 ε 随入射角放大 → 那是真正的 TSDF（带表面法向的加权融合），另一套东西
