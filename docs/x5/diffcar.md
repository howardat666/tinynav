# 差速小车（ESP32-S3 + TB6612）接入 tinynav

> **结论：不是新分支，是第四个 platform。** LeKiwi 的耦合比看起来浅 —— 规划器本来就是
> 非完整约束的，全向只存在于控制器层。

## 1. 为什么不新建分支

调查（2026-08-18）查到三件事，决定了这个判断：

| 事实 | 依据 | 后果 |
|---|---|---|
| **规划器已经是单车模型** | `generate_predefined_trajectory_vocabularies` 产生 `(vx, omega)`；`planning_node.py` 里没有 `vy` 横移分量 | 规划侧**零改动** |
| **平台抽象已存在** | `tinynav/platforms/` 下已有 `lekiwi_control` / `unitree_control` / `simulator_control`，用 `TINYNAV_ACTUATOR` 选 | 加一个文件即可 |
| **几何已抽出共享模块** | `robot_config.py` 有 `GO2` / `B2` / `LEKIWI` 三份 `RobotConfig` | 加一份配置即可 |

LeKiwi 的全向运动学集中在 `platforms/omni3_kinematics.py`，差速车根本不 import 它
（只借用其中与底盘无关的 `base_pose_to_camera_pose`）。新建分支会把这套已经做好的抽象白白分叉。

### 🔑 相机横向偏移 = 5 cm,来自三目而不是安装偏心

Looper 是**三目**:中间那颗(color)与车居中,左右两颗红外各偏 5 cm。而**整个导航栈跑的是
`infra1`** —— 用 `camera_info` 的 `P` 矩阵定死了哪一目在左:

| 话题 | `P[0,3]` | 结论 |
|---|---|---|
| `infra1` | **0.0000** | **左目,是校正立体对的参考相机** |
| `infra2` | −31.0093 (fx 309.49) | 右目,基线 **0.1002 m** |

所以 `infra1` 在车中轴线**偏左 50 mm** → `camera_y = +0.05`
(`RobotConfig` 的 `camera_y` 定义为车体系**向左**偏移)。

🔴 **由此查出一个符号 bug**:`node_manager` 把 `-_ROBOT.camera_y` 传给执行器,而
`base_pose_to_camera_pose` 要的 `offset_xyz` 正是 `[前, 左, 上]` —— 两边本来就一致,不该取负。
`camera_y` 一直是 0 所以从没暴露;现在是 0.05,**符号反了会让每个障碍物偏 100 mm**。已修。

### 🔴 前进后退反了、左右转正常 —— 只有一种接线状态能同时成立

差速运动学下逐个排除:

| 假设 | 前进 | 转向 | 符合? |
|---|---|---|---|
| 两电机极性都反 | 反 ✓ | **也反** ✗ | ❌ |
| 左右两路互换 | **正常** ✗ | 反 ✗ | ❌ |
| **极性都反 + 左右互换** | 反 ✓ | 正常 ✓ | ✅ |

而这正是**把驱动组绕竖轴转 180°**的结果 —— 前后和左右同时翻转,两个翻转在偏航上抵消。
用 `m 100 0` / `m 0 100` 单独驱动一路验证过,和推断一致:**B 路(原 `g_wl` 槽)带物理右轮,
A 路带物理左轮,两路的正向 PWM 都把车往后推。**

🔑 **同一个符号错误的另一面:里程计的 `x` 是反的,`theta` 是对的。** 编码器符号是 `j` 按
"固件正向 PWM"标定的,而固件正向物理上是后退。⚠️ **改装前用 `/wheel/camera_pose` 建的图,
前进方向都是反的**(检索不受影响,几何受影响)。

**修法(已改进固件源码)**:把两个 `Wheel` 初始化里的硬件字段(引脚/通道/PCNT 单元)和标定值
(ppr/kff/截距)**整组对调**,两个 `invert` 都改成 `false`。这样 `g_wl` 才真是物理左轮、正向
PWM 真是物理前进,里程计一起对。
⚠️ **不要只在 `diffcar_control` 里把 `v` 取负** —— 那样车能走对但里程计的 x 还是反的,而且
`teleop.py` / `calib.py` 直连固件,一个也修不到。

### 固件常量:轮距差 2.91 倍,双向出错

```cpp
constexpr float WHEEL_CIRC = 0.070f * PI;  // 0.2199 m   旧: 0.065f*PI = 0.2042
constexpr float WHEEL_BASE = 0.320f;       //            旧: 0.110
```

`WHEEL_BASE` 同时进 `setTargets(v - w*L/2, v + w*L/2)` 和里程计 `dth = (dSr-dSl)/L`,所以旧值:

- `u <v> <w>` 的偏航指令**只实现 1/2.91**(转得太慢)
- 里程计的 `theta` **放大 2.91 倍**(报得太多)

🔑 之前看到的 `theta=22.6度` 实际只有约 **7.8 度**。**"原地转角度不足"是常量错,不是脚轮拖曳。**

### 烧完固件必须重标,顺序固定

`ppr / kff / 截距 / 编码器符号` 存在 NVS 里,**键是按槽位(`"l"`/`"r"`)而不是物理电机**,
硬件对调后会张冠李戴:

```
1. ./ota.sh 192.168.19.218   PC 上编译 -> 传到 Looper -> 经 ttyS3 灌进去，不用插 USB
2. j                         编码器方向自动标定(轮子架空)，跑完闭环才解锁
3. calib.py dist 2.0         卷尺反推真实轮周长 -> n <左> <右> -> w
4. calib.py spin 10          数实际圈数反推真实轮距 -> 改 WHEEL_BASE 重新 ota.sh
5. calib.py sweep            落地重标 kff/截距(顺带自动打开掉压补偿)
```

### 🔑 状态灯:两个链路指示,以及为什么不能复用现成的"失联"

2026-08-21 板子掉线过一次,当时**灯没告诉任何人** —— 只能靠 ssh 连不上才发现。加了两个状态:

| 颜色 | 含义 | 谁发现的 |
|---|---|---|
| **橙慢闪 700ms** | 上位机静默:Looper 挂了 / 串口断了 / app 没跑 | **ESP32 自己**(UART1 5 s 无字节),零外部依赖 |
| **青慢闪 700ms** | Looper 活着,但它报告 **PC 连不上** | Looper 探测后用 `K <0\|1>` 报进来 |

优先级:黄(标定)、红快闪(堵转)、紫闪(低压)压过它们 —— 那三个会烧东西;
**橙压过红慢闪**(「上位机没了」比「没收到运动指令」信息更具体)。

🔴 **不能拿现成的红慢闪当这个用。** 它的含义是「2 s 无**运动**指令」,没人开车时本来就该亮,
跟 Looper 死活无关。必须是新判据。

**顺带修掉红慢闪自己的一个误报。** `s` 不会亮红(它把 `g_closed` 和 `pwm` 都清零,失联保护
的条件不成立),但 **`c 0` / `u 0 0` 是闭环顶住零速**,`g_closed` 仍为真 → 2 s 后失联保护触发
→ 红慢闪。可红慢闪的语义应该是「**我正在动的时候上位机不说话了,我被迫停车**」;上位机主动
叫停之后失联,车本来就停着,报紧急停车是误报。现在只在 `target` 或 `pwm` 非零时才点红
(取值必须在 `stopAll()` **之前**,它会把两者都清掉),其余交给 5 s 的静默检测点橙灯。
实测:`c 0`+静默 → 绿;`c 0.05`+静默 → 红慢闪;继续静默 → 橙慢闪。

🔴 **ESP32 没有任何网络,它 ping 不了东西**,只能被告知。而告知它的只能是**串口持有者** ——
`/dev/ttyS3` 只允许一个持有者,旁边再起守护进程写不进去(OTA 就栽在这上面)。所以心跳做在
`diffcar_control` 里。app 没跑时没人写串口,由 ESP32 自己的静默检测点橙灯,语义正好自洽。

🔴 **板上没有 `ping`**(busybox 精简掉了),`subprocess.call(["ping",...])` 抛 `FileNotFoundError`
**把探测线程静默打死**,而节点照常运行、灯照常报绿 —— 比不做更糟。改成纯 Python 原始套接字
ICMP(板上是 root)。⚠️ 网关 `192.168.19.1` 不回 ICMP,别拿它当探测目标。

**探测阈值是量出来的,不是拍的。** 板上 180 次 1 Hz ICMP:1.0 s 超时下"丢" **17.2%**,
而 **p95 RTT 839 ms、max 991 ms** —— 大部分"丢包"其实只是慢。真实连续丢包段**最长 2**
(3 分钟里出现 7 次)。所以超时取 **2.5 s**、连续 **3 次**才判定不可达(2 次必然误报,实测过)。
恢复不去抖:**误报"一切正常"比晚报警更糟**。改完 80 秒零误报。
⚠️ 顺带记住这条链路有多差:**p95 RTT 839 ms**。

🔑 **`?` 会把灯的当前状态和链路事件计数一起报出来**:
`灯=橙慢闪(上位机静默)` / `链路事件: 上位机静默 1 次(最近 23s前) PC不可达 1 次(...)`。
**掉线永远是过后才被发现的**,当时没人盯着灯 —— 跟启动计数一个道理,必须能事后查。
(注意 `UART1 静默 Ns` 那一栏永远是 0:`?` 本身就刷新了它。看计数,别看那个。)

### 2026-08-21 空载标定实测(悬空)

烧完新固件后先在悬空状态做完所有不需要地面的项。**落地标定的对照基线就是这一组。**

`j` 两轮都是真量出来的(不是"没转"的默认值),这点必须看逐轮打印才能确认:

```
左轮: 正转计数 -3842 → 符号定为 -1
右轮: 正转计数 +3688 → 符号定为 +1
```

`m 120 0` → 计数 `(3986, 0)`、`m 0 120` → `(0, 3854)`:另一轮恰好 0,**没有串线**。

**PWM→速度扫描(`o 0 240 20`,标定电压 10.79 V)**

| PWM | 20 | 40 | 60 | 80 | 100 | 120 | 140 | 160 | 180 | 200 |
|---|---|---|---|---|---|---|---|---|---|---|
| 左均 m/s | .079 | .186 | .290 | .394 | .496 | .597 | .697 | .795 | .894 | .992 |
| 右均 m/s | .076 | .178 | .278 | .377 | .474 | .570 | .666 | .764 | .860 | .957 |

最小二乘(取 0.15<v<0.95,与 `calib.py` 同口径):**左 kff=197.8 截距=2.45、右 kff=205.7
截距=2.86,R²=0.99988,最大残差 0.75 PWM**。已 `x 197.8 205.7` / `i 2 3` / `w`。

🔑 **左轮同 PWM 比右轮快 4.3%,全量程一致**(1.037~1.047)。原来两个 kff 几乎相等
(197.5/199.9),等于前馈系统性地多推左轮、少推右轮 4%,每次都要 PID 去补。改成分轮匹配后:

| | 修 kff 前 | 修 kff 后 |
|---|---|---|
| 直线 3 s 两轮计数差 | 9 / 2202 = **0.41%** | **1 / 6257 = 0.016%** |
| `c 0.30` 稳态误差 | — | **±0.3%**,2 s 收敛,超调 +7.3% 后单调衰减 |
| `c 0.128`(原地转轮速) | — | **±0.8%**,0.8 s 收敛 |
| 航向漂移 | — | 0.937 m 上 0.1°(0.107°/m) |

`kp=200 / ki=400` 不动:超调 0.5 s 内衰完,而**落地后惯量和摩擦都变,拿空载动力学调 PID 是错的**。

🔴 **我预测错了一次,记下来免得再犯。** 我推断「轮径涨 7.7% → 上报的 m/s 大 7.7% → kff 应该
小 7.7%,落在 183~186」。实测左轮 197.8,与原存的 197.5 只差 0.2%。这个推断依赖一个假设:
原来那 197.5 是**用旧轮周长拟合出来的**。数据否掉了这个假设 —— 它不是。
**参数的来历不能靠猜,拿不到出处就直接量。**

⚠️ **落地必须重做的是 `截距`。** 空载拟合出来只有 2~3 PWM(PWM 20 就转得起来),
带载的静摩擦门槛会高得多,而截距直接决定低速段能不能动 —— 原地转只用 PWM 28。

⚠️ **`kff` 和掉压补偿基准是一对,必须一起重标。** 这次基准记成了 10.81 V(当时的电池电压),
落地重扫会重新记录。单独改一个会让另一个的补偿系数失效。

🔴 **待查(不影响控制路径):`o` 扫到 PWM ≥ 220 就不再往 UART1 输出**,但电机继续转、固件没
重启(启动次数不变、`?` 照答)、`o 0 40 20` 完全正常且重复性到 ±0.001。只在诊断路径上,
而且**车的工作区间全在下面**(固件上限 0.8 m/s = PWM 160,导航 `max_vx=0.3` = PWM 62,
原地转 = PWM 28),所以没继续查。真要查就从 `Console::write` 的 `toUart` 和 `Serial1` 的
TX 缓冲入手。

### ✅ 2026-08-21 卷尺定标:两个机械常量定死了

| 常量 | 最终值 | 反推的物理量 | 对物理测量的偏差 |
|---|---|---|---|
| `WHEEL_CIRC` | **0.2173** | 轮径 **69.2 mm** | 比标称 70 小 **1.2%**(轮胎压扁) |
| `WHEEL_BASE` | **0.3234** | 有效轮距 | 比物理轮距 320 mm 大 **1.1%**(接地是面不是线 + 原地转打滑) |
| `kff` 左/右 | **190.7 / 194.1** | — | 按 k 反比缩放(单位是 PWM/(m/s)) |
| 截距 左/右 | 14 / 11 | — | 不变(PWM 偏置,与周长无关) |

做法:开 **2.1560 m**(里程计读数),卷尺实测 **2.290 m** → **k = 1.0622**(固件**少报** 5.85%)。
`WHEEL_CIRC ×= k`;`WHEEL_BASE ×= k`(旋转标定定的是 **C/B 比值**,C 一动 B 必须同比例跟上);
`kff /= k`(m/s 的刻度变大了,PWM/(m/s) 就同比例变小)。

🔑 **一致性检验:两个常量都落在物理测量的 1% 以内,而且偏差方向都对。** 轮胎会压扁 → 周长偏小;
接地是面不是线、原地转有打滑 → 有效轮距偏大。这是整条标定链自洽的最强证据。

### 🔴 VIO 不能用来定绝对距离,那一版粗标是错的(作废)

我先前按 VIO 把 `WHEEL_CIRC` 从 0.2199 改到 **0.2046**(轮径 65.1 mm),依据是"轮/VIO = 1.075
在 0.2~0.6 m/s 四个速度上恒定 ±0.5%"。**卷尺证明它错了 5.9%** —— 真值 0.2173,而改装前那个
标称的 0.2199 其实**只差 1.2%**,我是往错的方向改了一大步。

**当时就有一个信号被我忽略了**:那一版推出的有效轮距 0.3045 **比物理轮距 320 mm 还小 4.8%**,
而接地打滑只可能让有效轮距**变大**。我标注了"反常"却没深究 —— **物理上讲不通的中间结果,
就是该停下来的地方。**

| 参考 | 能不能定绝对距离 |
|---|---|
| **卷尺** | ✅ 唯一可信,2 m 上约 ±0.5% |
| **VIO 平移** | 🔴 **不行**,少报约 6%;而且静止后会在 `TRACKING_STATIC` 里滞留数秒吞掉开头的运动 |
| **VIO 旋转** | ✅ 可用 —— **角度无量纲,不受尺度偏置影响**;三次测量 ±0.35%,而且推出的 B 方向正确 |
| **深度(地面平面)** | ✅ 尺度对(垂距 0.1736 vs 尺量 0.18,rms 0.4~0.9 mm),但**平移方向条件太差**(侧墙 n_z=0.065) |
| **地面俯视图互相关** | 🔴 抛光水泥地**没有纹理**,NCC 峰是平的,给出的是伪结果 |

⚠️ 另外我用"闭环跟踪偏高 1~3%"去推测周长偏大,**这个推理本身就无效**:目标和实测**都是固件
自己的单位**,周长在两边会约掉,那个偏差推不出周长的任何信息。

### 2026-08-21 落地标定:带载前馈(已完成)

**电源先量再判断,别外推。** 我原来按"带载塌 1.4 V"(来自一次疑似接触故障的日志)定了
"静置 ≥11.4 V 才能标定"的门槛。**实测推翻了它** —— 静置 10.72 V 时:

| 速度 | 区间最低 | 塌压 | 离闭锁 9.60V |
|---|---|---|---|
| 0.10 | 10.70 | 0.02 | +1.10 |
| 0.20 | 10.61 | 0.11 | +1.01 |
| **0.30**(`max_vx`) | **10.52** | **0.20** | **+0.92** |

**用闭环步进而不是开环 `o` 扫描**(开环两轮差 4.3% → 7.7°/米偏航 → 撞墙)。
稳态 PWM 就是 kff 该拟合的量,靠固件 `e` 里新加的 `PWM=` 读。

⚠️ **第一次(保持 1.6 s / 取样 0.6 s)不够用**:相邻点算出的斜率在 100~298 之间乱跳,
R²=0.994、残差 2.5 PWM(空载那次是 0.99988 / 0.75),而且左轮 kff 报到 238.9。
改成 **保持 2.6 s / 取样 1.3 s**(每点 16 个样本)后才稳。**环还在收敛就取样 = 白测。**

| 拟合 | 左 kff | 左截距 | 右 kff | 右截距 | 最大残差 |
|---|---|---|---|---|---|
| 全量 7 点 | 215.9 | 11.25 | 206.7 | 10.48 | 2.16 / 1.60 |
| **剔掉最低两点(取用)** | **202.6** | **14** | **206.2** | **11** | **1.38 / 1.59** |

🔑 **右轮三轮测下来 204.7 / 206.7 / 206.2 —— 稳;左轮从 238.9 漂到 202.6,漂的全是低速点。**
所以左轮是**静摩擦不稳**(可能轻微刮擦),不是增益不同。取剔掉拐点那组的理由有三条:
残差更小、跨轮次一致、而且对最低那点的预测也更准(18.97 vs 实测 20.6;全量拟合只给 16.2)。
**这样两轮 kff 只差 1.8%,差异全落在截距(14 vs 11)** —— 物理上就是"增益一样,左轮更黏"。

⚠️ **截距从空载的 2~3 涨到 11~14**,正是预料中的带载静摩擦。原地转只用 PWM 约 36,
**截距占了三分之一** —— 空载值拿到地上会让低速段推不动。

所以先不动。

### 🔑 `dist` / `spin` 的真值可以用 VIO 代替人

`tool/x5_board/diffcar_calib_vio.py`(板上跑)把卷尺和数圈数换成 Looper 的 VIO ——
它的米制标度来自出厂标定的 **0.1002 m 立体基线**,是独立于轮速的参考,而且不需要人在现场:

```sh
python3 /userdata/x5/tinynav/tool/x5_board/diffcar_calib_vio.py dist 2.0
python3 /userdata/x5/tinynav/tool/x5_board/diffcar_calib_vio.py spin 5
```

- `dist`:VIO 首末位移当真值 → `k = VIO/固件` → **新 ppr = 旧/k**。`ppr` 和轮周长在里程计里
  只以比值出现,所以调 `ppr` 等价于调轮周长,但**不用重烧固件**。
- `spin`:**逐帧累加旋转向量**,不能取首末四元数(转过 180° 就绕回去了);固件那边也用两轮
  计数差重算而不是读 `theta`(同样会绕回)。→ `轮距_真 = 轮距_固件 × θ_固件/θ_VIO`。
  转速取 **0.8 rad/s = 导航的 `max_yaw`**:有效轮距要吸收原地转的打滑,而打滑跟转速有关。
- 会在 VIO 位姿单帧跳变 > 0.15 m(重定位)或电压 < 9.9 V 时**中止而不是给一个错数**。

**顺序不能换:** `kff` 的单位是 PWM/(m/s),而 m/s 由 `计数/ppr*轮周长` 算出来 —— `dist` 会改
`ppr`,所以 **`sweep` 必须在 `dist` 之后**。`spin` 反推轮距也用到 `ppr` 和轮周长,同理在
`dist` 之后。轮距只进偏航和 `theta`,不影响单轮 m/s,所以第 4 步重烧不会作废第 3 步。

🔴 **第 4 步改 `WHEEL_BASE` 重烧时,千万别顺手动 `CFG_REV`** —— 接线没变,一动它 NVS 里刚标
好的 `ppr` / `kff` / `截距` / 编码器符号全被丢掉,闭环重新锁上,前三步白做。`CFG_REV` 只在
**改接线或改 `invert`** 时加一。

⚠️ 轮周长别直接填 π×70mm:轮胎压扁让实际周长偏小。轮距也别直接填 0.32:轮胎接地是一个面
不是线,实际轮距会略大。**卷尺和圈数反推出来的才是能用的值。**

### 🔴 `invert` 一改，NVS 里的编码器符号就是反的 —— 会正反馈飙车

`controlWheel` 的 PID 用带 `encSign` 的读数。`invert` 从 `true` 改成 `false` 后同一个正向
PWM 的物理转向反了,编码器相对「指令正方向」的符号也跟着反,而 NVS 里存的还是旧符号 →
**负反馈变正反馈,PWM 一路顶到 255 往错方向狂转**,而堵转保护判的是「转不动」,抓不到这个。

所以固件里加了一道版本联锁:`CFG_REV`(接线一改就加一)一起存进 NVS,不匹配时**丢掉存的每轮
参数并锁住闭环** —— `c` / `u` 直接拒绝并打印提示,`?` 里也会显示。跑一次 `j` 就地解锁,
敲 `w` 让它跨重启生效。**开环的 `m` / `f` / `b` 不受影响**(它们不看反馈)。

🔑 换接线/改 `invert` 的时候记得把 `CFG_REV` 加一,否则这道保护不会触发。

## 2026-08-24 地毯实测:转向符号、绝对轮距、低速兑现率

全部走 ROS 话题(`/cmd_vel` + `/wheel/odometry` + `/camera/camera/vio_100hz`),**不碰串口**,
所以 app 可以照常跑,不会和 `diffcar_control` 抢 `/dev/ttyS3`。

### 转向符号:槽位是对的(结案)

之前担心的是「固件的左右轮槽位可能还是反的」—— 那样转向和路径跟踪会整体镜像。用三个
互相独立的角度参照测原地自转(`diffcar_spin_sign_check.py`):

| 指令 | 图像水平位移 | 轮速里程计 | VIO |
|---|---|---|---|
| `angular.z = +0.40`(逆时针/左) | **+316 px = 左 58.5°** | **+52.6°** | **+52.6°** |
| `angular.z = -0.40`(顺时针/右) | **-297 px = 右 55.0°** | **-51.3°** | **-49.9°** |

🔑 **图像位移是方向上的铁证**:相机向左转,画面内容必然向右移,这条只用到 `fx`,和轮距、
轮周长、VIO 尺度全都无关。三者同号 → 槽位正确,`theta` 正 = 逆时针 = 左。

⚠️ **VIO 位姿的偏航落在 `z` 轴上,不是相机光学约定的 `y`**。原地转 52.6° 实测旋转向量是
`[+0.24 +0.25 +52.59]` 度 —— 所以 `/camera/camera/vio_100hz` 的 `z` 是竖直向上、正为逆时针,
水平面是 `xy`。按光学约定(x 右 y 下 z 前)去取 `y` 会拿到一个恒为零的数。

### 有效轮距:用 360° 闭合绝对标定

近景杂乱的房间里没法用图像量转角 —— 相机偏离旋转中心 71 mm,原地转时它自己在画圆,1 m
处的视差就有 5°。**但转满一圈之后相机回到完全相同的位姿,那一刻视差恰好为零。**

`diffcar_spin_closure.py` 就吃这一点:转过 360° 一点,沿途记下每帧的水平轮廓和当时的里程计
读数,事后找「相对起始帧位移过零」的那一帧,读出里程计当时报的角度。

```
逆时针: 图像闭合(真 360°)时里程计报 +363.50°  ->  标度 1.0097
顺时针: 图像闭合(真 360°)时里程计报 -366.45°  ->  标度 1.0179
```

闭合点两侧相关系数 0.91~0.92,过零区间只有 1~2 帧宽,精度约 ±0.3°。

**里程计角度标度 = 1.0138(高报 1.4%),有效轮距应为 0.3234 × 1.0138 = 0.3279 m。**

和瓷砖上用 VIO 测的 1.0226 方向一致、量级相当 —— 两种独立方法、两个地面都说轮距偏小 1~2%。
**但先不改**:1.4% 折到 90° 转弯上只有 1.3°,比两个方向之间的离散(0.8%)大不了多少,而轮距是
编译期常量、要重烧固件。等下次有别的改动要烧时一起带上。

### 🔴 地毯上低速转向指令兑现不了

口径是「3 秒内实际转过的总角度 ÷ 应转角度」,不用瞬时速率(低速段闭环 3 秒都没稳定,
瞬时速率会给出 >100% 的假象)。

| 指令 rad/s | 3 秒应转 | 实际 | **兑现率** | 起转延迟 |
|---|---|---|---|---|
| 0.15 | 25.8° | 14.3° | **55%** | 0.22 s |
| 0.20 | 34.4° | 23.8° | **69%** | 0.14 s |
| 0.30 | 51.6° | 41.8° | **81%** | 0.11 s |
| **0.40** | 68.8° | 63.6° | **92%** | 0.06 s |
| 0.60 | 103.1° | 97.1° | 94% | 0.07 s |
| 0.80 | 137.5° | 127.3° | 93% | 0.09 s |

🔑 **判据:亏损在编码器上就能看到,不是轮子打滑。**上表「实际」是从编码器算的,而图像和
VIO 都跟它吻合 —— 车身跟得上轮子,是**轮子本身没转够**,即闭环跟不上低轮速。0.15 rad/s 对应
的轮速只有 0.024 m/s,按瓷砖拟合的前馈只给约 19 PWM,地毯的破静摩擦远不止,于是全靠积分器
(`ki=400`)慢慢卷,卷够了轮子一跳、积分又卸掉 —— 粘滑运动,平均速度低于目标。

**规划器大约每 1.2 s 重发一次轨迹,所以 <0.4 rad/s 的转向命令等于白发。**修法是重测地毯上的
前馈 `x`/`i`,那两个存在 NVS 里,**不用重烧固件**。

### ⚠️ VIO 在 0.8 rad/s 自相矛盾,而 `max_yaw` 正好是 0.8

```
指令 -0.80: VIO 瞬时速率 -2.107 rad/s，但 VIO 自己的总角度 -128.5° / 3 s = -0.748 rad/s
```

瞬时速率要求最后 1.5 s 转 162°,而全程只转了 128° —— **VIO 自己的数据前后矛盾**,只能是它在
这一档跳变/丢帧。0.60 已经开始有征兆(0.643 vs 0.574),0.40 及以下完全正常。

导航位姿就来自 VIO,所以 `max_yaw = 0.8` 等于把机器人放在它自己位姿源开始退化的区间里。
**建议降到 0.6**;顺带也降低电流(见 `board_bringup.md` 的掉线分析)。

### 「里程计说右偏、卷尺量到左偏」怎么会同时成立

2026-08-21 的三趟直线里固件报 `theta = -1.30°`(顺时针=右),操作者量到的是**左**偏 3.5 cm,
量级对到 1 毫米。当时我把「量级对上」当成符号也对的证据 —— **那是错的推理**。

符号测试验证的是「计数差 → 物理方向」这个映射(它是对的),但直线行驶时:

```
左轮有效周长比右轮小 0.49%（70 mm 轮上直径差 0.34 mm）
  闭环把两轮"编码器速度"抹平   ->  左轮计数反而多 0.24%
  固件用同一个周长换算          ->  报 dSl > dSr  ->  说"右偏 1.30°"
  但左轮每个计数走的地面更短    ->  真实左边走得少  ->  车实际左偏 2.31°/3.03 m = 3.5 cm
```

🔴 **也就是说轮式里程计的航向误差是真实航向变化的两倍、而且反号。**当前导航用 VIO 闭环
(`pose_topic:=/camera/camera/vio_image`),每周期重新纠偏,所以不影响;但**切到轮式里程计导航
的那个变体时,车会朝错误方向纠偏**。

判据和修法都不用重烧固件:`diffcar_straight_curvature.py` 跑「前进+后退」若干趟,取带符号的
每米曲率 κ = Δθ/Δx:

| 观察 | 结论 |
|---|---|
| 前进和后退的 κ **同号** | 左右轮有效半径不一样(反向时 Δθ 和 Δx 一起变号) |
| 前进和后退的 κ **变号** | 外部侧向力(路面横坡 / 脚轮拖拽) |
| **VIO 的 κ 和里程计的 κ 反号** | 确认半径差,而且两者之差直接给出失配百分比 |

失配用 `ppr` 补:`ppr` 分左右存在 NVS 里,把小的那侧调大对应百分比,**里程计航向归零、而且
PID 会把那侧多转一点让车自己走直** —— 一处改动修两件事。

## 2. 几何怎么进规划器

几何数字见上面的「实测几何」表 —— **这里不重复,以免又出现两份互相矛盾的数字**(2026-08-21
之前这一节写的是旧车的 240×120 mm / 轮距 110 mm,改装后每一格都错了)。

`control_x` 取**驱动轴**而不是车体中心:差速底盘上驱动轴是唯一横向速度为零的点,轨迹推演
必须以它为准。于是 `footprint_from_control()` 给出:

```
front_len = 0.14 - 0.04 = 0.100 m       rear_len = 0.14 + 0.04 = 0.180 m
half_w    = 0.175 m                     cam_offset_3d = [-0.05, 0, 0.05]
```

矩形而不是圆形:以驱动轴为心、能装下 350 mm 宽车体的圆要 0.25 m 半径,是真实半宽 0.175 的
1.4 倍,会拒绝掉本来能过的门洞。

### 🔑 改装把两个避障参数的理由抽掉了

|参数|旧值|新值|为什么|
|---|---|---|---|
|`front_blocked_m`|0.2|**0.3**(即默认值)|0.2 当初的理由是「110 mm 轮距原地转几乎不占地方」。**原地转的后角扫掠半径从 0.078 m 涨到 0.251 m**,而 `front_blocked_m` 是从车身边缘算的 → 0.2 只保证轴心外 0.30 m,只剩 0.049 m 余量,闸门一开原地转就先被碰撞检查否掉,白走一趟逃逸分支|
|`max_vx`|0.5|**0.3**|**这是反应时间的限制,不是底盘的限制。** 规划器重发周期实测 p50 1.17 s,0.5 m/s 意味着新看到的障碍物出现前车已经承诺走 0.58 m —— 约等于闸门距离的 3 倍。0.3 让一个周期落在 0.35 m,和闸门同量级。**落地量过闭环延迟后再往上调**|

⚠️ **原地转的碰撞检查是靠"矩形"这个身份拿到的。** `_score_trajectories` 只在 `is_circle`
的底盘上豁免原地转的碰撞打分(圆形转来转去扫的还是自己那块地,判了也没用),矩形走的是正常
路径,**整条旋转轨迹逐位姿做足迹检查**,所以后角扫掠是被看着的。别顺手把 `shape` 改成 circle。

### ⚠️ 矮障碍物检测不到，这是已知局限，不要用 `min_wall_span_m` 去"修"

`build_obstacle_map` 判定障碍物的方式是「占据体素在 z 上的跨度 ≥ `min_wall_span_m`（0.2 m）」——
**这同时就是地面剔除机制**（平地跨度约 0，自然不算障碍物），而不是靠 z 下界。

于是 **21 cm 高的车面对不到 20 cm 的障碍物（门槛、地插、书本）是检测不到的**，而这些恰恰能拦住它。
这是真实局限，但**不能靠调低 `min_wall_span_m` 解决**：

```
self.resolution = 0.1        grid_shape = (100, 100, 10)
z_span = (occ_high − occ_low) * resolution     # occ_* 是整数层索引
```

跨度只能是 **0.1 的整数倍**。所以阈值 0.2 = 「占满 3 层」，任何 0.1 < 阈值 ≤ 0.2 的取值都等价于
「占 2 层」—— 而真实地面的立体深度噪声在很多格子里必然跨 2 个 10 cm 层，**地面会直接变成墙**。
2026-08-18 试过把它降到 0.06，正是这个错误。

同理 z 带**不能收窄**：收到 `[-0.19, +0.10]` 只剩 3 层，span ≥ 0.2 就要求占满全部 3 层，
几乎什么都检测不到。现在取 `[-0.3, +0.2]` = **5 层**，占 3 层即判为障碍物，留了 2 层冗余。
多出来的两层全在地面以下（相机在 0.183 m，−0.3 相当于地面下 0.117 m），那里只有深度噪声 ——
换来的是相机俯仰或过坎时地面在 `z_rel` 里上下浮动也不会掉出下界。

**真正的解法是提高栅格分辨率**（0.1 → 0.05 m），代价是栅格内存和 ESDF 计算量各涨 8 倍。
这是一项独立工作，没做。

### 🔑 固件在哪、怎么升级、板上有什么工具

⚠️ **`/home/dm/diffcar_esp32` 不在 git 里**,只有一份 44 KB 的 `README.md`(协议表、接线表、
灯语、标定方法全在里面) —— 改固件前先看它,别凭记忆。改动前手动留 `.bak`。

| 在哪 | 是什么 |
|---|---|
| `diffcar_esp32/ota.sh [ip]` | **不插 USB 升级**:PC 上 `pio run` → scp 到 Looper → 板上 `flash.py` 经 ttyS3 灌进去。会先 `pkill teleop.py`,否则 20 Hz 指令会把 OTA 搅乱 |
| `diffcar_esp32/dev.sh [mon\|flash]` | 有线:串口监视器 / 编译烧录。两个 USB 口插哪个都自动认 |
| 板上 `/root/car/teleop.py` | 键盘遥控。w/s/a/d 点动 + WASD 巡航,空格停,x 急停,z 清零里程计,p 位姿,+/- 调限速。20 Hz 重发(固件失联保护 2 s),顺带显示复位次数和最低电压 |
| 板上 `/root/car/calib.py` | `sweep`(PWM→速度曲线) / `dist <m>`(反推轮周长) / `spin <圈>`(反推轮距) |
| 板上 `/root/car/flash.py` | OTA 的板侧那一半,`ota.sh` 自己会传过去 |

**为什么必须是这种 OTA:** ESP32-S3 的 ROM 引导只在 UART0 和原生 USB 上听下载命令,而焊到
Looper 的是 **UART1**,`esptool` 永远够不着。所以只能让**运行中的固件自己收固件**(`U <字节数>
<md5> [波特率]`):先 `stopAll()`,写进备用分区,MD5 过了才重启切过去。**校验不过老固件原封不动,
不存在烧一半变砖**,而且全程不动轮子。

⚠️ **OTA 自己引导不了自己** —— ACK 流控是 OTA 可靠的前提,而装 ACK 流控本身要先烧一次。
**换电脑/换板子时第一次必须有线烧。**

🔴 **OTA 前必须先 `app_start.sh stop`。** `/dev/ttyS3` 只能有一个持有者,而
`diffcar_control.py` 是常驻持有者 —— 它发的 `p` 混进固件正在按字节计数的固件流,它读的
字节又吃掉固件回的 `0x06` ACK,**两个方向同时废掉**。协议丢一个字节就整个作废,所以症状是
「传了一小段才死」(2026-08-21 实测传到 4%),看着像波特率问题 —— **不是**,同一条线 921600
早就实测过 6.3 秒成功。`ota.sh` 和 `flash.py` 现在都会自己处理:前者先停 app,后者扫
`/proc/*/fd` 查持有者并在失败时自动降速重试。

`tinynav/platforms/diffcar_control.py` 扮演 LeKiwi 那边 `wheel_odometry_node` 的角色 ——
**串口唯一持有者**，同时消费 `/cmd_vel` 和发布里程计。它不是 `wheel_odometry_node` 的一个模式，
因为两者没有任何共享：没有 Feetech 总线、没有三轮运动学、位姿是现成的。

实测：`/wheel/camera_pose` **19.2–19.7 Hz**，`z` 恒为 0.183（相机高度），与 ESP32 的 `p` 一致。

### 两个实现细节

- **必须持续重发**：固件的失联保护是 2 s，且串口指令**不自动续期**。节点以 20 Hz 重发，
  并且 `/cmd_vel` 超过 `cmd_timeout_s`（0.5 s）没来就主动发零 —— 不能靠 2 s 失联保护刹车，太迟钝
- **轮询 `p` 而不是等推送**：固件的 `y` 遥测只推两轮速度、不含位姿。轮询 2 字节命令 + 约 40 字节
  回复，20 Hz 下 840 B/s，115200 波特率（11.5 kB/s）余量充足。要进一步降延迟可以改固件把位姿
  加进遥测流

## 4. 🔴 一个会让车自己动起来的坑

`app_start.sh` 原来把执行器**写死**成 `export TINYNAV_ACTUATOR=wheel`（没有 `:-`），
外部 `export` 覆盖不掉。在差速车上启动 app 会拉起 `wheel_odometry_node` 去开 ttyS3 并
**往 ESP32 写 Feetech 协议报文**，而 ESP32 的命令解析是单字符的（`0x66` = `'f'` = 前进）——
**报文里的字节会被当成行驶命令。** 2026-08-18 实测踩到：节点跑了约 30 s，ESP32 里程计读数非零。

已改成 `export TINYNAV_ACTUATOR="${TINYNAV_ACTUATOR:-wheel}"`。**换底盘时先确认执行器，再启动。**

⚠️ 但 `:-wheel` 这个默认值在这块板子上是错的 —— 它让 `robot_type` 落到 `lekiwi`,UI 里画出
一个圆形 300 mm 机器人、规划器拿到 LeKiwi 的运动学,而且**完全不报错**。2026-08-21 已在
`tool/x5_board/env.sh` 里钉成 `TINYNAV_ACTUATOR="${TINYNAV_ACTUATOR:-diffcar}"`:这是**这块板子
的硬件属性,不是代码默认值**,所以放 env.sh 而不是改 app_start.sh。判据是 `/device/platform`
的 `shape` 要是 `square`、`lengthWidthM` 要是 `[0.28, 0.35]`。

## 5. 启动

```sh
# env.sh 已经把 TINYNAV_ACTUATOR 钉成 diffcar，robot_type 由它推出来，不用再手动 export
bash /userdata/x5/tinynav/tool/x5_board/app_start.sh start a   # a=VIO 建图/VIO 导航
```

方案字母是必填的(`a` / `b` / `c`),漏了会直接报 `scheme must be a, b or c`。
**里程计还没重标之前用 `a`** —— `b` / `c` 都要吃轮速里程计,而它的 x 现在还是反的。

验一眼几何有没有生效(板上没有 curl):

```sh
python3 -c "import json,urllib.request as u; d=json.load(u.urlopen('http://192.168.19.218:8000/device/platform')); print(d['robotType'], d['wheel']['shape'], d['wheel']['lengthWidthM'], d['wheel']['maxVx'])"
```

## 6. 还没做的

| # | 事项 | 为什么重要 |
|---|---|---|
| 1 | `max_vx=0.3` 是**按反应时间压的**，不是实测上限 | 固件能到 0.8 m/s。0.3 来自规划器 p50 1.17 s 的重发周期(一个周期 0.35 m，约等于 `front_blocked_m` 闸门)。量过真实闭环延迟后再往上调 |
| 2 | **重标 `WHEEL_CIRC` / `WHEEL_BASE`** | 现值是卷尺量的标称值，是里程计主要误差源。轮距只影响 θ、轮周长只影响距离，可分开标（方法见 `diffcar_esp32/README.md`） |
| 3 | z 带 `[-0.3, +0.2]` 待现场验证 | 上界对应世界高度 0.383 m，比 0.21 m 的车高留了很大余量，可能把车能钻过去的桌面也当障碍物；下界要看真实地板噪声会不会在地面下两层造出假墙 |
| 4 | 端到端跑一次导航 | 目前只验证了位姿链路，没有闭环驱动过 |
