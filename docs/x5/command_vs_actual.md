# 指令和实际执行不符：哪一类会撞，哪一类不会

> 2026-08-28。起因是一个具体问题：「发 `vx=0.2, w=0.1` 但实际执行 `0.18/0.08`，会不会撞？」
> 结论：**这一类（稳态增益误差）几乎无害；真正会撞的是滞后。** 下面是量出来的。

## 1. 仿真里的实测

在 `tool/simulator/` 里加了执行误差模型（`_actual_cmd` 的增益/死区 + `integrate_cmd` 的
滞后队列，预设见 `x5_presets.py` 的 `ACTUATORS`），并**补上了碰撞判据** —— 在此之前
`scenarios.py` 根本检测不了碰撞（仿真不做碰撞响应，车能穿墙，表格照样打 OK）。

判据 = 车体足迹（4×5 铺满）到最近障碍的最小距离，负数表示压进去了：

| 执行误差 | corridor | narrow_gap | chair_legs | doorway |
|---|---|---|---|---|
| `perfect` 完美执行 | 0.325 | 0.125 | 0.044 | 0.105 |
| `gain_10_20`（vx×0.90 / wz×0.80） | 0.325 | 0.125 | 0.050 | 0.106 |
| `realistic`（增益+死区+0.3 s 滞后） | 0.236 | 0.086 | 0.022 | 0.109 |
| **`latency_800ms`** | 0.119 | 0.034 | **−0.020（压进 108 次）** | 0.028 |

单位 m。`gain_10_20` 就是问题里那组数字：**对净空的影响 6 mm，在趟间散布里。**
0.8 s 滞后把 `chair_legs` 从 +44 mm 推到 −20 mm，真撞。

## 2. 为什么增益误差不致命

因为每个规划周期都**从测到的位姿重新出发**。稳态增益误差是**形状**误差，只在一个承诺
窗口内累积，下一拍重新测量就归零：

```
指令  (0.20, 0.10)  -> 曲率 k1 = 0.500 /m   (半径 2.00 m)
实际  (0.18, 0.08)  -> 曲率 k2 = 0.444 /m   (半径 2.25 m)
dk = 0.056 /m

承诺窗口 s = reaction_time_s(2.0) x 0.18 = 0.36 m 弧长
横向偏差 ~ s^2 * dk / 2 = 0.36^2 * 0.056/2 = 3.6 mm
朝向偏差  = s * dk       = 0.020 rad = 1.1 deg
```

3.6 mm 是闸门余量 `prefix_margin_m = 0.10` 的 3.6%。**关键是它是 s² 项** —— 承诺窗口
越短，掉得越快。任意一组 (v, w) 都能套这个式子。

## 3. 为什么滞后致命

滞后是**时间**误差，闭环里没有任何环节在纠正它 —— 规划器假设它发的指令**此刻生效**。

```
0.8 s x 0.5 m/s = 0.40 m 「正在执行上一条指令」
0.40 m = 闸门余量 0.10 m 的 4 倍
```

这 0.4 m 走的是一条**已经作废**的轨迹，而那条轨迹是按 0.8 秒前的障碍图检查过的。
`reaction_time_s = 2.0` 本来就是为了盖住这个（上游闭环仿真扫出来的：`<=1.0` 撞 /
`1.2` 剩 0.03 / `1.6` 剩 0.09 / `2.0` 剩 0.11），但在椅子腿这种近距离矮障碍上**还是不够**。

## 4. 🔴 我们根本没有「实际执行」这个量

```python
# tinynav/platforms/diffcar_control.py:359
odom.twist.twist.linear.x  = self._cmd[0]      # 发出去的指令，不是轮子真转了多少
odom.twist.twist.angular.z = self._cmd[1]
```

**里程计发布的「实测速度」就是指令本身。** 任何人想拿它检测指令/实际差距，拿到的是指令自己。

而 `cmd_vel_control.py` 有 `self._vx_gain_comp = 1.2` —— 无条件把速度乘 1.2，没有注释说
这 20% 从哪来（同文件其他常数都有长注释）。这等于承认 vx 会欠输出，然后盲补。

**历史上两次真正的指令/实际不符都不是 10% 这个量级，而且都只能靠翻日志考古发现：**

| | 规划器要的 | 实际发出的 | 后果 |
|---|---|---|---|
| 反馈项无界 | `vx=0.250` | **0.500** | 一周期走 0.55 m，而前缘只剩 0.065 m → 撞 |
| 倒车符号（`v_ref` 取了模长） | `vx=-0.060` | **+0.26** | 17/17 条 RETREAT 朝着要退开的障碍开 |

100% 和 400%。担心的方向对，量级找错了地方。

## 5. 解法，按性价比排

**① 先把「实际」测出来 —— 唯一真解，其余都是猜。**
VIO 位姿 20+ Hz 是免费的：相邻两帧位姿差分算出真实 (v, ω)，和当拍指令配对，直接得到
「指令 vs 实际」散点图。做完才知道增益是 0.9 还是 0.7、滞后是 0.1 s 还是 0.8 s。
顺带把 `diffcar_control` 那两行改成真实值（ESP32 有编码器闭环，可回读），否则这个量永远是空的。

**② 用测出来的误差反推余量，而不是拍一个 0.10。**
```
prefix_margin = 基础余量 + v * latency + s^2 * dk_max / 2
                           ^滞后项，线性，主导  ^增益项，二次，很小
```
现在 `prefix_margin_m = 0.10` 是定值，既不含速度也不含滞后 —— 同一个 0.10 在
0.083 m/s 和 0.5 m/s 上意义完全不同。

**③ 缩短承诺窗口，而不是把模型做准。**
滞后项是 `v x latency`，唯一能压小它的是更快重规划 + 只承诺更短的一截。和「碰撞判定
按首次碰撞截断而不是整条 3 s 全否」是同一个改动。

**④ 死区要单独处理。**
`deadband` 那一档实测：`wz` 死区 0.20 rad/s 时，脱困挑的那些 0.15 rad/s 原地转**根本不动**。
实车表现为「车站着不动」而日志一切正常 —— 和地毯上 0.15 rad/s 兑现率只有 55% 是同一件事
（见 `diffcar-front-drive-geometry` memory）。测出死区后，轨迹库里低于死区的档位应该直接不生成。

**⑤ DWA（动态窗口法）的「动态窗口」我们其实没做。**
标准 DWA 只采样「一个周期内加速度够得到」的速度。我们把 0~max_vx **全域**采样了 ——
车静止时 `vx=0.5` 那条弧被当成立刻可达来打分和碰撞检查。这本身就是一种系统性的
指令/实际不符。加上加速度限制后，轨迹库会自动只剩真能执行的那些。

## 6. 顺带记一条待查

**完美执行下 `chair_legs` 的最小净空只有 44 mm，而闸门承诺的是 100 mm。**
门没兑现承诺，最可能的原因是 `_prefix_clearance` 只取 5 个点（中心+4 角），而碰撞内核
取 20 个（4×5 铺满）—— 闸门带着内核已经修掉的那个欠采样 bug。单独查。

## 8. 四个环节 A/B/C/D：谁和谁的误差要紧（2026-09-01）

```
A 发出的指令速度
B 实际速度  ← 🔴 这其实是两个量：B1 轮子实际转速 / B2 车对地实际速度，差的是打滑
C 轮速里程计估算的速度
D VIO 算的速度
```

### C ≈ B1 是构造出来的

编码器直接测转速，`ppr` 手转 20 圈标到 **0.03%**。所以 C 和 B1 之间几乎没有误差。
**"B 和 C 没办法"只对 B2 成立，对 B1 不成立。**

### 🔑 A↔B2 的误差**等于** C/D 的比值

```
A → 固件按 B_assumed 算每轮目标 m/s → PID 闭环在「编码器测速」上   ⇒  C = A
B2 = C × (真实滚动半径/假设半径) × (1 − 打滑)
D 测的是 B2
⇒  A/B2 = C/D
```
所以 **C↔D 不是旁支，它是唯一能看见 B2 的仪器给出的 A↔B 标定。**
2026-09-01 把它从 +4.6%/−2.8% 降到 **+0.6%/+0.5%**（见 `odometry_vio_calibration.md`）。

### 但 A↔B 只在**粗错**时才撞，几个百分点无害

本文第 1、2 节实测：稳态增益误差 10%/20% → 净空影响 **6 mm**；0.8 s 滞后 → **0.40 m**。
历史上真正撞的 A↔B 错误全是 **100%/400%** 量级，而 2026-09-01 修的正是这一类：

| | 症状 |
|---|---|
| 轮距 0.3234（旧车）vs 0.2035（实测） | 偏航被**超发约 48%**（实测转 2.94 圈而固件以为 1.99） |
| 两个电机被装到对方位置 | 前后**方向 100% 反**，而转向正常（两个翻转在偏航上抵消） |

### 🔴 但 C 拟合到 D 之后，还剩一个系统性的、朝着障碍的偏差

**尺度不同源：**
```
障碍距离  ← 深度三角化 ← 立体基线 0.1002 m   →  metric
车的位移  ← VIO 积分                          →  记录显示少报约 5.8%（这台车未复验）
```
所以拟合到 VIO 之后：命令 0.3 m/s，车物理上走约 0.317 m/s，而规划器以为 0.3 ——
**在 0.36 m 的承诺窗口里多走约 21 mm，方向朝着障碍**，占闸门余量 100 mm 的 21%。

🔑 **所以 C 的绝对锚点最终应该是 metric（卷尺 / 深度基线），不是 VIO 的积分。**
"VIO 米制是工作单位"这个说法不准确 —— **障碍不在 VIO 米制里。**
（车体半径 0.122 是物理米，地图/障碍是深度米 ≈ 物理米，这一项自洽，没有额外风险。）

### C↔D 标定的第二个收益：打滑/卡住检测器

现在知道期望比值是 **1.006 ± 0.018**。超出这个范围 = 有东西在滑或车被架起来了。
标定之前那 4.6% 的偏置会把真实打滑完全掩盖掉。

### 重点该放哪（按实测证据排序）

| | 项 | 现状 | 量级 |
|---|---|---|---|
| 🔴 1 | **滞后从没在这台车上测过** | `reaction_time_s=2.0` 是上游闭环仿真扫出来的 | **0.40 m**，第一位 |
| 🔴 2 | **一次卷尺，把 C 锚到 metric** | 目前只有 VIO 一个参考 | 21 mm/窗口，系统性朝障碍 |
| 🔴 3 | **没有 B 的实时观测** | `diffcar_control.py:359` 发的是指令本身；而固件的 `e`/`y` 已经报每轮实测 m/s，只是没接进 odom twist | 使能上面全部 |
| 🟡 4 | **死区没测** | 低于死区的档位照样生成 | 0.15 rad/s 的脱困原地转"根本不动" |
| 🟡 5 | **轨迹库没做动态窗口** | 0~max_vx 全域采样，当成立刻可达，而加速度上限 1.5 m/s² | 结构性的 A↔B 不符 |

滞后可以**纯被动**测：跑导航时同时采指令时间序列和 VIO 微分出的 (v, ω)，做互相关找峰。
不需要额外动作。

## 9. A/B/C/D 四路实测：滞后 0.2 s（好），原地小角速度根本不动（坏）（2026-09-01）

§8 排序里的第 3 项（"我们根本没有 B 的实时观测"）已经修好，第 1、2、4 项跟着一次测完。

### 9.1 修的是什么

`odom.twist` 以前直接抄 `self._cmd` —— **速度表接在油门上**。位姿一直是真的（固件用编码器
积分），只有速度字段是指令回声，所以打滑、堵转、死区在数据里和正常走完全同形。

- 固件：`p` 的回复尾部附带 `vl=/vr=`（每轮编码器实测 m/s，带符号）。挂在已有的 20 Hz
  轮询上，不另开命令；以前这个数只有 5 Hz 的 `y` 遥测和人工的 `e` 能看到。
- `diffcar_control.py`：`_measured_twist()` 用 `(vl+vr)/2` 和 `(vr−vl)/wheel_base` 填 twist。
  旧固件（不报 vl/vr）会 warning 后退回指令 —— 静默退回等于把字段变回回声。
- `tool/x5_board/abcd_probe.py`：三路（指令 / 编码器 / VIO）同步采集 + 离线分析。
  `--drive none` 只订阅不发布，跑导航时可以全程后台开着。

⚠️ `vMeas` 是 α=0.5 / 20 Hz 的一阶低通，群延迟约 50 ms，报滞后时已减掉。

### 9.2 滞后：0.14~0.23 s，四个独立估计一致

| | 直行 | 偏航 |
|---|---|---|
| A→C（编码器） | +0.231 s | +0.170 s |
| A→D（VIO） | +0.182 s | +0.141 s |

（阶梯组另测得 A→C 直行 0.188 / A→D 直行 0.146，互为印证。）

🔑 **这是这台车上第一次真正量到滞后。** 规划器的 `reaction_time_s=2.0` 因此是保守的，
而闭环仿真里"0.8 s 滞后 → chair_legs 净空 −0.020 m、压进 108 次"那个失效模式**离现状还有
4 倍余量**。§8 把滞后排第一位是对的，但它现在不是问题。

### 9.3 直行：A↔B1 精确，A↔B2 差几个百分点

逐段稳态 `C/A` = 0.998 / 0.998 / 0.999 / 1.000（±0.20、±0.30 m/s）—— **PID 在编码器上闭环
是准的，C = A 是构造出来的**，这条实测钉死了 §8 的推导。

`C/D` 速度域给 1.02±0.04（逐段散布 ±8%，每段只有 0.1~0.4 s 平台）。**速度域不适合抠尺度**，
尺度归距离标定的 1.0059（见 [odometry_vio_calibration.md](odometry_vio_calibration.md)）。

### 9.4 🔴 原地转：≤0.15 rad/s 完全不动，0.2~0.3 rad/s 要 1.3 s 才起转

从静止起步、纯原地转（v=0），每 0.25 s 一格的 |w实测|：

| 指令 rad/s | 爬升过程 | |
|---|---|---|
| 0.05 | 0 0 0 0 0 0 0（1.6 s 内） | 完全不动 |
| 0.10 | 0 0 0 0 0 0 0 | 完全不动 |
| 0.15 | 0 0 0 0 0 0 0 0 0.018 **0.113**（2.5 s） | **2.25 s 才起转** |
| 0.20 | 0 0.009 0 0 0 0.084 **0.163**（1.6 s） | **1.25 s 才起转** |
| 0.30 | 0 **0.232** 0.364 …（另一次 1.25 s 才动） | 不稳定 |
| 0.60 | 0 **0.398** 0.540 0.565 | 立刻 |

编码器和 VIO 两路都说没转（w=0.15 时 C=0.0018、D=0.0008），不是测量假象。

**机制已定量对上**（`controlWheel`，kp=200 ki=400 deadband=4 kff=199.9）：

```
w=0.15 → 每轮目标 0.0153 m/s → 前馈 4+199.9×0.0153 = 7 PWM，kp 项 3 PWM，合计 10
w=0.30 → 每轮目标 0.0305 m/s → 前馈 10，kp 项 6，合计 16
w=0.60 → 每轮目标 0.0610 m/s → 前馈 16，kp 项 12，合计 28
实测击穿门限≈24~28 PWM（原地转要拖两条胎横向擦地）→ 只有 0.60 一档瞬时就够
差额全靠积分慢慢爬：err×dt 每拍只有 7.6e-4，爬到够用要 1~2 s，与实测的 1.25/2.25 s 吻合
```

对照实验（`--drive stick`）分离了静摩擦和死区两种解释：

| 场景 | 0.15 rad/s 的增益 |
|---|---|
| 从静止起步 | **0.14 / 0.09** ← 不动 |
| 承接 0.60 不回零 | 0.72 / 0.42 |
| 配 v=0.10 前进 | 0.63 / 1.04 |

⇒ **门限在"从静止破静摩擦"这一步，不在角速度本身。** 轮子只要在滚，小角速度就能执行。

顺带解释了 [[escape-turn-dithering]] 那类摆头：从 0.60 降到 0.15 时实测是
`0.596 → 0.216 → 0.010 → 0 → 0 → 0 → 0.071 → 0.229` —— **减速冲过头停住，然后要重新破
静摩擦**，于是一顿一顿。

### 9.5 直行死区：软的，能动但少给

| 指令 m/s | 0.02 | 0.04 | 0.06 | 0.10 | 0.15 |
|---|---|---|---|---|---|
| 增益 | 0.56 | 0.78 | 0.91 | 0.95 | 0.99 |

比偏航好得多 —— 直行不擦胎，击穿门限只要约 12 PWM。**≥0.06 m/s 基本可用。**

### 9.6 两条修法（未做，要选）

1. **固件加静摩擦击穿**：`tRamp≠0` 且 `|vMeas|<0.005` 持续 0.1 s 时把 PWM 抬到 30。
   30 < `STALL_PWM`=60 所以不会误触堵转保护，轮子一动就自动释放。风险是小目标下变成
   顿-滑蠕动。
2. **规划侧回避**：原地纯转不给低于约 0.45 rad/s 的档位；小角速度一律配 v ≥ 0.08 m/s。
   零风险，但会砍掉一部分轨迹库。

⚠️ `kff`/`deadband` 至今是**轮子架空**标定的（README:420 早已标注要落地重标），
落地后的击穿门限就是上面量到的 24~28，两者差一个数量级。

### 9.7 分析脚本自己踩过的三个坑（都会给出像模像样的假数）

- **插值之后才 unwrap 角度**：VIO 的 yaw 实测跨 ±π，先插值会把跳变插成穿过 0 的斜坡，
  偏航那一路相关系数掉到 −0.003。必须先 unwrap 再插值。
- **稳态掩码只挡阶跃之后**：VIO 差分的 0.2 s 滑窗把下一次阶跃的减速段平均进平台样本，
  把 `C/D 直行` 从 1.006 抬到 1.034，会被误读成 3.4% 的打滑。两侧都要挡。
- **命令信号用线性插值**：阶跃边界被插出中间值（0.30 → 0.12 → 0），段检测被骗。
  命令是零阶保持的量，必须用 ZOH。

合成数据自检（已知滞后 0.30 s / 增益 0.90 / 死区 0.05）修好后能全部量回：0.32 / 0.898 / 0.05。
**先干跑一遍合成数据再上真车**，这三个坑没有一个会报错。

## 10. 静摩擦击穿已实装：地毯上定值 45 PWM（2026-09-01）

采用 §9.6 的方案 1（固件侧），方案 2（规划侧回避）不做。

### 10.1 实现

`controlWheel()` 里，PID 输出之后加一段：目标非零而 `|vMeas| < 0.008` 持续 0.10 s，
就把 PWM 顶到 `g_brk`，轮子一动自动松手。

- **夹在 `STALL_PWM`=60 以下**（`min(g_brk, STALL_PWM-1)`），否则这一脚自己会把堵转保护踩响。
- **方向跟 `tRamp` 而不是跟 PID 输出**：反向起步时 `integ` 还留着旧符号，跟输出会把车往
  反方向踹。
- 判据 `BRK_V`=0.008 比 `STALL_V`=0.02 松一档：那个是"该动却不动"的堵转判据，这个是
  "还没起步"，两件事。
- 新命令 `F [pwm]` 在线改 + 存 NVS（键 `brk`）。**换地面必须重扫**，见下。

### 10.2 地毯上的扫描结果

| 击穿 PWM | 0.10 | 0.15 | 0.30 | 几何均值增益 |
|---|---|---|---|---|
| 0（关闭） | **0.00 / 0.02** | **0.08 / 0.01** | 0.99 / 0.38 | — 不动 |
| 40 | 1.09 / 1.14 | 0.83 / 0.77 | 0.93 / 0.51 | 0.85 |
| **45 ← 采用** | 1.19 / 1.54 | 0.82 / 0.93 | 0.90 / 0.62 | **0.96** |
| 50 | 1.44 / 1.58 | 1.04 / 1.03 | 0.87 / 0.72 | 1.08 |
| 59 | 1.45 / 2.09 | 1.26 / 1.33 | 0.75 / 0.93 | 1.23 |

🔴 **地砖上击穿门限只要 24~28，地毯要 45。** 换地面必须重跑
`tool/x5_board/brk_sweep.py`（要先停 app，串口只有一个主人）。

**起转时刻从"永不 / 2.25 s"变成 0.1~0.2 s。** 顺带把直行低速也修好了（击穿 45 时
0.02 m/s 增益 0.71~0.88，原来地砖上是 0.56）；≥0.06 m/s 本来就没问题，没被搞坏。

### 10.3 残留的两件事（都是二阶，不阻塞导航）

**① ≤0.30 rad/s 在地毯上是顿-滑，不是平稳转。** 实测 w=0.15 的爬升：
`0.000 0.317 0.026 0.082 0.299 0.085 0.039 0.192` —— 击穿踹一脚跳到约 0.30，PID 收油，
又粘住，再踹。**均值对得上（0.154 对 0.15），但过程是一跳一跳的。** 地毯上原地转能
维持的最低角速度大约就是 0.28~0.32，低于这个只能顿-滑。规划器每周期都从实测位姿重新
出发，所以均值对就够用，但不优雅。

**② 0.60 rad/s 要约 2 s 才爬到位**：`0.368 0.382 0.418 0.467 0.497 0.529 0.549 0.577`，
2.1 s 时到 96%。前馈 `kff` 是**轮子架空**标定的，地毯上要的 PWM 大得多，差额全靠积分爬。

两件事的正解是同一个：**落地重标 `kff`/`deadband`**（README:420 早已标注）。但直行的
开环扫描（`o`）会把车往前开，1x1 m 空地做不了 —— 等有场地。用原地转的差分 PWM 扫可以
零位移，但那量到的是**擦胎**工况的曲线，直行会被过驱，不能直接写进 `kff`。

## 11. `abcd_probe.py` 怎么用

```bash
# 跑导航时全程采集（只订阅不发布，26.4% 一个核，nice 让它在排队上输给导航节点）
source /userdata/x5/env.sh && cd /userdata/x5/tinynav
setsid nohup nice -n 10 python3 tool/x5_board/abcd_probe.py \
    --drive none --duration 2400 --out /root/car/nav >/root/car/nav_probe.log 2>&1 &

# 离线自测（自己发阶跃序列，跑完自动回零速）
python3 tool/x5_board/abcd_probe.py --drive step    # 滞后+增益，直行往返 1.32 m
python3 tool/x5_board/abcd_probe.py --drive stair   # 死区阶梯，路径 0.52 m
python3 tool/x5_board/abcd_probe.py --drive stick   # 静摩擦 vs 死区判别
python3 tool/x5_board/abcd_probe.py --drive spin    # 纯原地转，零位移，1x1 m 也能跑

# 分析（在板上或拉回 PC 都行）
python3 tool/x5_board/abcd_probe.py --analyze /root/car/nav_0901_162753
```

- **数据每 2 秒落盘**，不是攒到退出才写 —— 一次导航十几分钟，进程被 kill / 板子重启 /
  网断都会让攒着的数据全丢，而那恰好是最想事后分析的情况。
- **`/teleop/cmd_vel` 单独录**并在分析时按执行器的仲裁规则（0.4 s 优先窗口）合并。
  只录 `/cmd_vel` 会把人推摇杆那段错算成"导航发的指令没被执行"。
- 导航工况没有恒定段，逐段表用不上，所以有一节**执行健康度**：非零指令占时、
  「指令非零但没动」的比例和最长连续时长、以及**累计行程**的 `C/D`。
  ⚠️ 打滑不能看瞬时 `C/D`：顿-滑工况下 C 和 D 都在零附近抖，两个近零数相除会炸出
  `p10=0.23 / p90=2.73` 这种毫无意义的分布（实测栽过）。

### 三个会给出「像模像样的假数」的坑（全部不报错）

1. **插值之后才 unwrap 角度** —— VIO 的 yaw 实测跨 ±π，先插值会把跳变插成穿过 0 的斜坡，
   偏航那一路相关系数掉到 −0.003。
2. **稳态掩码只挡阶跃之后** —— VIO 差分的 0.2 s 滑窗把下一次阶跃的减速段平均进平台样本，
   把 `C/D 直行` 从 1.006 抬到 1.034，会被误读成 3.4% 的打滑。两侧都要挡。
3. **命令用线性插值** —— 阶跃边界被插出中间值（0.30 → 0.12 → 0），段检测被骗。
   命令是阶梯量，必须零阶保持。

**先用合成数据干跑一遍再上真车**：已知真值 0.30 s / 0.90 / 0.05 要能量回 0.32 / 0.898 / 0.05。

# 13. 逐跳延迟实测（2026-09-02）—— 大头是我们自己的队列

> 🔴 **2026-09-07：本节的「排队 230 ms」已作废，见 [latency_chain.md](latency_chain.md)。**
> 那个数是拿 planning 的 `in_age` 减去「相机 152 + bridge 11」推出来的，而 `in_age`
> 量的是**位姿**龄，位姿由 `diffcar_control` 在发布时打 `now`，**一点相机延迟都不含**
> —— 减的是根本不在里面的东西。而且这里的逐跳数是**导航关着**时测的。
> 本节的相机段（约 150 ms）与空闲重测一致；bridge 段应为 1~3 ms 而非 11 ms。


前面各节量的是「指令 → 实际」那一侧。这一节补的是**另一侧：传感到决策**，用板上一个
只读探针（20 s，`ROS_LOCALHOST_ONLY=1`）逐跳量「消息到手时它自己的 `header.stamp`
已经多老」。同一块板同一个时钟，差值可信。

## 13.1 逐跳

| 话题 | Hz | 间隔 p90 | 数据龄 p50 |
|---|---|---|---|
| `/camera/camera/infra1/image_rect_raw` 灰度 | 20.05 | 55 ms | **32 ms** |
| `/camera/camera/depth/image_rect_raw` 固件深度 | 4.75 | 206 ms | **152 ms** |
| `/slam/depth`（bridge 转发后） | 4.80 | 211 ms | 163 ms |
| `/wheel/camera_pose` | 20.05 | 55 ms | **5 ms** |
| `/planning/trajectory_path` | 5.00 | 212 ms | 261 ms（无目标时） |

🔑 **灰度 32 ms 而深度 152 ms —— 多出的 120 ms 是固件的双目深度计算。**
bridge 只加 11 ms，可以忽略。轮速位姿几乎没有延迟（5 ms），不是瓶颈。

## 13.2 planning 每周期内部（`TINYNAV_VERBOSE_TIMER=1`，722 周期，无目标）

```
Planning Loop 总 89 ms  |  raycasting 62 ms  |  traj gen 11 ms
obstacle map 8 ms       |  preprocess 3 ms   |  vis 0 ms
```

导航时 `cycle` p50 是 0.22 s，所以轨迹打分约再 +110 ms。
**计算 ~200 ms vs 深度周期 210 ms —— 贴着实时边缘。**

## 13.3 把导航时的 `stamp_lag = 590 ms` 拆开

```
相机 152 + bridge 11 + 排队 ~230 + 计算 ~200 = ~590 ms   (= 日志 stamp_lag)
+ 执行器 ~200 ms（见第 3 节）→ "已发生但没反映到轮子上" ~790 ms
+ 最多一个重规划周期 220 ms   → 最坏 ~1.0 s
```

**排队那 230 ms 是我们自己的代码扔掉的。** `message_filters` 是 FIFO：在回调里直接干活
就永远在处理队列头那个**最旧的、还没过期的**集合，即使后面已经躺着一个新 0.2 s 的。
唯一挡板 `max_input_age_s=0.5` 只丢超时的、**不保证用最新的**，所以系统稳定在
「贴着过期门限跑」—— 日志里 101 次 `dropping stale synced set: 0.50~0.60s old` 就是它。

⚠️ **队列深度不能动。** `planning_node` 的注释里有实测：30 改成 3 之后发布间隔
p50 1.17 → 3.2 s，`trajectory expired` 从 1 次涨到 342 次，车停了。要改的是**取用策略**。

## 13.4 已加的开关与判据

`TINYNAV_PLAN_LATEST_ONLY`（默认 **0** = 旧的 FIFO 行为）：回调只存 `_pending_set`，
20 Hz 定时器取最新再规划。单线程执行器 + 默认互斥回调组，不会重入。
启动日志打 `FIFO intake` / `latest-only intake`。

决策行新增 **`in_age=`**（进回调时的数据龄）：

```
in_age − 0.163      = 排队掉的时间
stamp_lag − in_age  = 本节点的计算耗时
```

⚠️ **排队是随负载出现的，不是常数。** 真车实测：障碍多但车基本没动时 `in_age` p50
只有 **0.19 s**（≈163 ms 加一点，几乎没排队）；负载上来才堆到 0.33~0.50 s。
所以 **A/B 必须在真的跑起来、障碍图满的时候做**，闲着比不出差别。
