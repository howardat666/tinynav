# 指令和实际执行不符：哪一类会撞，哪一类不会

> 2026-08-28。起因是一个具体问题：「发 `vx=0.2, w=0.1` 但实际执行 `0.18/0.08`，会不会撞？」
> 结论：**这一类（稳态增益误差）几乎无害；真正会撞的是滞后。** 下面是量出来的。

## 1. 仿真里的实测

在 `tool/simulator/` 里加了执行误差模型（`_actual_cmd` 的增益/死区 + `integrate_cmd` 的
滞后队列，预设见 `x5_presets.py` 的 `ACTUATORS`），并**补上了碰撞判据** —— 在此之前
`scenarios.py` 根本检测不了碰撞（仿真不做碰撞响应，车能穿墙，表格照样打 OK）。

判据 = 车体足迹（4×5 铺满）到最近障碍的最小距离，负数表示压进去了：

| 执行误差 | corridor | narrow_gap | chair_legs | doorway |
|---|---|---|---|---|
| `perfect` 完美执行 | 0.325 | 0.125 | 0.044 | 0.105 |
| `gain_10_20`（vx×0.90 / wz×0.80） | 0.325 | 0.125 | 0.050 | 0.106 |
| `realistic`（增益+死区+0.3 s 滞后） | 0.236 | 0.086 | 0.022 | 0.109 |
| **`latency_800ms`** | 0.119 | 0.034 | **−0.020（压进 108 次）** | 0.028 |

单位 m。`gain_10_20` 就是问题里那组数字：**对净空的影响 6 mm，在趟间散布里。**
0.8 s 滞后把 `chair_legs` 从 +44 mm 推到 −20 mm，真撞。

## 2. 为什么增益误差不致命

因为每个规划周期都**从测到的位姿重新出发**。稳态增益误差是**形状**误差，只在一个承诺
窗口内累积，下一拍重新测量就归零：

```
指令  (0.20, 0.10)  -> 曲率 k1 = 0.500 /m   (半径 2.00 m)
实际  (0.18, 0.08)  -> 曲率 k2 = 0.444 /m   (半径 2.25 m)
dk = 0.056 /m

承诺窗口 s = reaction_time_s(2.0) x 0.18 = 0.36 m 弧长
横向偏差 ~ s^2 * dk / 2 = 0.36^2 * 0.056/2 = 3.6 mm
朝向偏差  = s * dk       = 0.020 rad = 1.1 deg
```

3.6 mm 是闸门余量 `prefix_margin_m = 0.10` 的 3.6%。**关键是它是 s² 项** —— 承诺窗口
越短，掉得越快。任意一组 (v, w) 都能套这个式子。

## 3. 为什么滞后致命

滞后是**时间**误差，闭环里没有任何环节在纠正它 —— 规划器假设它发的指令**此刻生效**。

```
0.8 s x 0.5 m/s = 0.40 m 「正在执行上一条指令」
0.40 m = 闸门余量 0.10 m 的 4 倍
```

这 0.4 m 走的是一条**已经作废**的轨迹，而那条轨迹是按 0.8 秒前的障碍图检查过的。
`reaction_time_s = 2.0` 本来就是为了盖住这个（上游闭环仿真扫出来的：`<=1.0` 撞 /
`1.2` 剩 0.03 / `1.6` 剩 0.09 / `2.0` 剩 0.11），但在椅子腿这种近距离矮障碍上**还是不够**。

## 4. 🔴 我们根本没有「实际执行」这个量

```python
# tinynav/platforms/diffcar_control.py:359
odom.twist.twist.linear.x  = self._cmd[0]      # 发出去的指令，不是轮子真转了多少
odom.twist.twist.angular.z = self._cmd[1]
```

**里程计发布的「实测速度」就是指令本身。** 任何人想拿它检测指令/实际差距，拿到的是指令自己。

而 `cmd_vel_control.py` 有 `self._vx_gain_comp = 1.2` —— 无条件把速度乘 1.2，没有注释说
这 20% 从哪来（同文件其他常数都有长注释）。这等于承认 vx 会欠输出，然后盲补。

**历史上两次真正的指令/实际不符都不是 10% 这个量级，而且都只能靠翻日志考古发现：**

| | 规划器要的 | 实际发出的 | 后果 |
|---|---|---|---|
| 反馈项无界 | `vx=0.250` | **0.500** | 一周期走 0.55 m，而前缘只剩 0.065 m → 撞 |
| 倒车符号（`v_ref` 取了模长） | `vx=-0.060` | **+0.26** | 17/17 条 RETREAT 朝着要退开的障碍开 |

100% 和 400%。担心的方向对，量级找错了地方。

## 5. 解法，按性价比排

**① 先把「实际」测出来 —— 唯一真解，其余都是猜。**
VIO 位姿 20+ Hz 是免费的：相邻两帧位姿差分算出真实 (v, ω)，和当拍指令配对，直接得到
「指令 vs 实际」散点图。做完才知道增益是 0.9 还是 0.7、滞后是 0.1 s 还是 0.8 s。
顺带把 `diffcar_control` 那两行改成真实值（ESP32 有编码器闭环，可回读），否则这个量永远是空的。

**② 用测出来的误差反推余量，而不是拍一个 0.10。**
```
prefix_margin = 基础余量 + v * latency + s^2 * dk_max / 2
                           ^滞后项，线性，主导  ^增益项，二次，很小
```
现在 `prefix_margin_m = 0.10` 是定值，既不含速度也不含滞后 —— 同一个 0.10 在
0.083 m/s 和 0.5 m/s 上意义完全不同。

**③ 缩短承诺窗口，而不是把模型做准。**
滞后项是 `v x latency`，唯一能压小它的是更快重规划 + 只承诺更短的一截。和「碰撞判定
按首次碰撞截断而不是整条 3 s 全否」是同一个改动。

**④ 死区要单独处理。**
`deadband` 那一档实测：`wz` 死区 0.20 rad/s 时，脱困挑的那些 0.15 rad/s 原地转**根本不动**。
实车表现为「车站着不动」而日志一切正常 —— 和地毯上 0.15 rad/s 兑现率只有 55% 是同一件事
（见 `diffcar-front-drive-geometry` memory）。测出死区后，轨迹库里低于死区的档位应该直接不生成。

**⑤ DWA（动态窗口法）的「动态窗口」我们其实没做。**
标准 DWA 只采样「一个周期内加速度够得到」的速度。我们把 0~max_vx **全域**采样了 ——
车静止时 `vx=0.5` 那条弧被当成立刻可达来打分和碰撞检查。这本身就是一种系统性的
指令/实际不符。加上加速度限制后，轨迹库会自动只剩真能执行的那些。

## 6. 顺带记一条待查

**完美执行下 `chair_legs` 的最小净空只有 44 mm，而闸门承诺的是 100 mm。**
门没兑现承诺，最可能的原因是 `_prefix_clearance` 只取 5 个点（中心+4 角），而碰撞内核
取 20 个（4×5 铺满）—— 闸门带着内核已经修掉的那个欠采样 bug。单独查。
