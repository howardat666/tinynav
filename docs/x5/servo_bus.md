# LeKiwi 舵机总线（X5 → ttyS3）丢包问题

诊断日期 2026-08-06，**2026-08-07 两次修正**。根因仍在硬件路径上（USB 直连 0.00% 是决定性的）。

**当前最好的理解**：底子约 8%，是硬件路径的；温度约 +0.28 %/°C（单次升温内显著，跨运行不显著）；
app 负载额外约 +1.4~1.8 个百分点；而**运行间漂移 ±4 个百分点比上面两者都大**。
**断电冷却半小时无效** —— 最冷 56.4 °C 仍有 8.37%。

写这份是为了避免重复排查 —— 下面「已证伪」那一节里的每一条都花过时间，
而「负载依赖」「温度」两节各自推翻过前一版的结论，原因都记在里面。

## 一句话

X5 经 `/dev/ttyS3` 读三个 STS3215 轮子，**单次尝试约 29% 失败**；同一批舵机、同一块
Waveshare 适配板、同一个电源，改由**笔记本 USB 直连适配板**则 **2500 周期 0 失败**。
差异只在 `X5 → GH1.25 → 适配板 UART header` 这一段。

## 实测数字

| 路径 / 条件 | 失败率 | p95 延迟 |
|---|---|---|
| **PC —USB— 适配板**（跳线帽 B/USB 位） | **0.00%**（2500 周期，含 150 Hz 三倍速率） | 0.62 ms |
| X5 —GH1.25— 适配板（跳线帽 A/UART 位），3 id，单次尝试 | **29.33% / 29.70%**（两次独立 3000 周期） | — |
| 同上，3 id，带 4 次重试 | 13–28%（**漂移，不可当仪器**） | 21 ms |

**方向分解**（`servo_loss_decompose.py`，四条件交错采样）：

| 条件 | P(全中) | P(一个都没回) |
|---|---|---|
| N=1 `[7]` | 86.17% | 13.83% |
| N=2 `[7,8]` | 77.83% | 12.83% |
| N=3 `[7,8,9]` | 76.83% | 10.33% |
| ctl `[7,20,21]`（查询包同长，仅 1 个真实回包） | 84.17% | 15.83% |

- **发送方向（查询包）丢失约 10–13%** —— `P(一个都没回)` 与 id 数无关，因为查询包只有一个。
  这是上界；要钉死需要「写一次 + 大量重试读回」的方法（未做）
- **查询包长度不影响丢失率**：84.17% vs 86.17%，比值 0.977
- **回包丢失约 4%/个，但强相关**：「三个里只有一个回了」实测 36 次，独立预测 0.3 次（**差 120 倍**）
- **1→2 个回包的代价 9.7 个百分点，2→3 只有 1.3** —— 「有第二个回包」本身很贵

**回包模式**（300 次，按到达顺序）：`7,8,9` 72.7% / 无 11.7% / `8,9` 11 / `7,9` 10 / 单个 8,7,6 / `7,8` 5。
→ **单个回包随机消失、与位置无关**，菊花链（适配板→舵机1→2→3）**链尾没有劣势**。

**非平稳**：单次 60 s 运行内，每 2 秒一段的失败率在 **4% ↔ 56%** 游走。
局部近似独立（簇长 1.52 vs 独立 1.45），但那个 p 自己在漂。

**为什么重试没用**：单次事务失败约 23%，若重试独立，4 次后应为 0.23⁴ = **0.28%**；
实测端到端 17–28%。**差两个数量级就是相关性的大小** ——「突发内相关 + 时间相关」两层叠加。

## ⚠️ 调制源不是「CPU 忙」

第一版这一节里还有三行「加热后停掉负载」「+ 6 个 burner 到 96% CPU」的数据，**已删除：
那次实验的 `kill $BURN` 用了 `jobs -p`，在 busybox `sh` 下没拿到子 shell 的 pid，
6 个 CPU burner 一直跑了近一小时，把那之后的每一次测量都污染了。**判据是 `ps -eLo pcpu=,comm=`
里出现连号的 `sh` 各占约 74%，而 `load` 与各进程 CPU 之和对不上。

去掉污染后的对照反而给出更强的结论：

| | CPU | 失败率 |
|---|---|---|
| app 全跑（干净） | 57% | 19.07% |
| app + 6 个 CPU burner | 96% | 17.77% |

**多烧 39 个百分点的 CPU 没有让丢包变差**（差异在噪声内）。所以调制它的不是 ALU 占用，
而是 app 带来的**相机数据流 / DDS 传输 / 中断负载 / DDR 流量**。这与「UART 中断被 MIPI/ISP/BPU
中断延迟」和「DDR 带宽争用」两个机制假设吻合，与「CPU 抢占」不吻合。

## app 负载的独立贡献：约 +1.4 ~ +1.8 个百分点

用上面的空载拟合去预测 app 负载点，差值就是温度解释不掉的部分：

| 条件 | 温度 | 空载曲线预测 | 实测 | 差 |
|---|---|---|---|---|
| app 全跑 | 75.6 °C | 13.97% | 15.73% | **+1.76** |
| app 全跑（另一次） | 89.0 °C | 17.72% | 19.07% | **+1.35** |

两次独立测量一致，所以这个量比温度斜率更可重复。但注意 **它小于 4.17 个百分点的运行间漂移**，
所以严格说仍在噪声内，只是两次符号和量级都对得上。

⚠️ **本节推翻了本文档上一版的说法**。上一版写「6.73% → 19.07% 是 2.8 倍，归因于 app 负载，
温度不是主因」。分解后：那 12.3 个百分点里，温度（21.4 °C × 0.28）约 6.0、app 约 1.4，
**剩下约 5 个百分点是运行间漂移，无法归因**。上一版把漂移和温度都算进了 app 的账上。

**不是用户态调度抢占**：交错重测 `chrt -f 80` vs 普通，得 16.87 / 27.27 vs 24.53 / 20.87 ——
两个 fifo 之间的差异比组间差异还大，**无效**。（2026-08-06 那次 `chrt` 是空载下测的，
本来就没有抢占可躲，那次「无差异」没有判别力。此次虽在 burner 污染期内，但它是交错对照，
相对结论不受影响。）

**实用推论**：降低 app 的数据流开销会顺带降低总线丢包率；单纯省 CPU 周期不会。
反过来，任何在负载下测的总线数字都不能和空载的比。

## 测量方法论（踩过的坑）

1. **跨时间 A/B 一律不可信** —— 同一条命令、同样 50 Hz 500 周期，一小时内测出 25.2% 和 13.4%，
   而电压温度未变。对照**必须在同一次运行内交错采样**（`servo_loss_decompose.py` 按此写）
2. **仪器要用「3000 周期单次尝试失败率」**（复现性 29.33 / 29.70），
   **不要用带重试的数字**（13–28% 乱漂）
3. `servo_raw_dump.py` 60~100 次试验的波动有 25 个百分点，分辨不出小于 20 点的差异
4. **测量前必须停 `wheel_odometry_node`**，否则 pyserial 报
   `device reports readiness to read but returned no data (multiple access on port?)`。
   ⚠️ 停它的脚本**必须写成文件再执行**，不能用 ssh 一行命令：`ps` 会匹配到调用者自己的命令串，
   而命令串里只要出现过节点名（比如中文 `echo` 里），`kill` 就会杀掉自己的 shell。2026-08-07 踩过
5. **停掉 `wheel_odometry_node` 会同时切断位姿源** → `bridge` 不再出关键帧 → `map_node` 转 idle。
   所以「满载 + 测总线」有结构性上限：ttyS3 被位姿源独占，两者不可兼得
6. **窄范围的相关系数不能用来证伪**（见「已证伪」表里被推翻的那条）
7. **不要拿几个打印样本当分布** —— 「回包是前缀式截断」这个错误结论就是这么来的
8. 🔴 **起了后台负载进程，必须验证它真的被杀掉了**。`( while :; do :; done ) &` 配 `jobs -p` +
   `kill` 在 busybox `sh` 下静默失效，6 个 burner 跑了近一小时污染了后续全部测量。
   判据：`ps -eLo pcpu=,comm=` 找异常占用，以及 **`load` 与各进程 CPU 之和对不上**
   （当时 load 17.9 而进程 CPU 合计只有 367%/800%）。测完 `sleep` 一下再复查一次
9. 单点计时测波特率会被 **约 25 ms 的 tcdrain 调度唤醒延迟**污染（读出 −25%）。
   必须用**斜率法**：同一速率测多个字节数，用 Δbits/Δt 拟合，固定开销落到截距里

## 板上的 UART 拓扑

只有**三个**真实 UART（`/dev/ttyS1/2/4/6/7` 节点存在但 `uart:unknown port:00000000`）：

| 端口 | SoC 引脚 | 用途 |
|---|---|---|
| `ttyS0` | `dsp_uart0_txd/rxd` | 内核控制台 `console=ttyS0,921600n8`，被 agetty 占用 |
| `ttyS3` | `lsio_uart3_tx/rx` | **舵机总线**（8pin 接口） |
| `ttyS5` | **`lsio_spi4_sclk` / `lsio_spi4_ssn`**（复用成 `uart5grp`） | 空闲。注意引脚丝印是 SPI4 |
| 未启用 | `lsio_uart1/2/4/7_tx/rx` | 全被配成 GPIO（`gpiochip4`），**无 ttyS 设备** |

引脚映射从 `/sys/kernel/debug/pinctrl/*/pinmux-pins` 读，可直接查。
**2026-08-06 试过换到另一个机壳外接口，三个 UART 全部环回无回声**（`tx +36, rx +0`），
说明那个接口不通向任何已实例化的 UART —— 很可能走的是上表最后一行那些 GPIO 引脚。
要用它必须改设备树 / pinctrl 重新 mux，属于改相机系统配置。

## 由此暴露的两个代码隐患（与总线是不同的问题，必须单独修）

### 1. 读失败会连带吃掉刹车指令 🔴
`wheel_odometry_node._tick()` 在同一个 50 Hz 回调里**先读后写**，而 `_drive_wheels()` 在**最末尾**
（`:389-390`）—— 读失败的 `return`（`:364`）和 `body_delta is None` 的 `return`（`:376`）**都会跳过它**。

- 真实指令缺失率 = 读失败 17–28% **叠加** 发送丢包 10–13%
- **`/cmd_vel` 超时后的看门狗刹车也走 `_drive_wheels()`，同样被跳过** → 坏时间窗里连续多拍收不到刹车

修法：`_drive_wheels()` 挪到读之前，或放进 `finally`。

### 2. 退出时的停车指令只发一次 🔴
`destroy_node()` 的 `sync_write("Goal_Velocity", 0)` 无 ack、无重试。约 10–13% 概率丢失
→ 运动中停节点大约每八到十次一次「轮子继续转而控制器已经没了」。
修法：重发 N 次 + 读回 `Goal_Velocity` 确认为 0。

### 附带：启动失败不是电源问题
`configure_velocity_mode` 的 `write("Torque_Enable")` 只重试 3 次，撞进高失败率时段整个节点退出
→ **完全没有动力输出**。2026-08-06 复现两次，循环重启才起来。历史上曾被误记为电源问题。

## ⚠️ 判断故障时的关键不对称

`Goal_Velocity` 是**绝对设定值**，舵机保持到收到新值为止。所以**总线丢包只会让车「多走」，
永远不会让车「停」**（「该动时没动」最多晚一拍）。

→ **看到车停住，就一定是有人主动发了 0，不要往总线上找。**
导航中途停车已定案为规划延迟，见 `map_node` / `cmd_vel_control` 日志。

## 数据不全时的处理

`_tick()` 调 `sync_read` **不传 `allow_partial`**（默认 False），一个舵机没回就抛异常 →
记一次 `read_failures` 然后 `return`。**部分数据从不被使用，整拍丢弃。**
这是对的：位置积分跳过一拍只是让下次位置差跨更长间隔，**积分结果仍正确**（只要轮子没转过半圈）
→ 损失的是发布率和时间分辨率，**不是轨迹精度**。
