# LeKiwi 舵机总线（X5 → ttyS3）丢包问题

诊断日期 2026-08-06，**2026-08-07 四次修正**。根因在硬件路径上。
⚠️ 但**不要再引用「USB 直连 0.00% 所以是 UART 接口的问题」** —— 那次对照里那段 UART 根本不在链路里，
详见「笔记本的市电适配器」一节末尾的纠正。

## 🟢 最重要的一条：拔掉 PC 的调试 USB 线，丢包从 22.2% 降到 8.1%
### （其中一半来自笔记本的市电适配器，见下一节）

2026-08-07 交错 ABAB 实验（132 轮 × 500 周期 = 66000 次单次尝试，详见「PC USB 线」一节）：
**插着 22.24% / 拔掉 8.12%，比值 2.74x，8 次拔插事件 8 次方向全对。**
温度、CPU 全程匹配，`usb0` 流量只有 1.4 kB/s，所以不是「顺带砍掉了数据流」。

**这条改写了此前几乎所有数字的解释。** 这个调查里的每一次测量都是在 USB 线插着的状态下做的
（那是唯一能登进板子的路），所以 15–29% 这些数字里约 **14 个百分点是测量设备自己贡献的**。
「运行间漂移 ±4 点」也主要住在这个条件里 —— 拔掉后四个相位是 7.97 / 8.08 / 8.07 / 8.37%，
**极差只有 0.40 个百分点**。

**当前最好的量化理解**：`fail% = 1.36 + 0.404 x 线上字节`（r=0.9999，见「暴露时间模型」）——
**失败率正比于事务占用总线的时间**。而其中的事件密度 λ 是被调制的：
插着 USB λ≈719/s（1.39 ms 一次），拔掉 λ≈242/s（4.13 ms 一次）。
温度约 +0.28 %/°C、app 负载约 +1.4~1.8 点，**都比 USB 线这一项小一个数量级**。
**冷却无效**（56.4 °C 仍 8.37%），**降波特率有害**（9% -> 17%）。软件侧已在最优点。

写这份是为了避免重复排查 —— 下面「已证伪」那一节里的每一条都花过时间，
而「负载依赖」「温度」两节各自推翻过前一版的结论，原因都记在里面。

## 一句话

X5 经 `/dev/ttyS3` 读三个 STS3215 轮子，**单次尝试约 29% 失败**；同一批舵机、同一块
Waveshare 适配板、同一个电源，改由**笔记本 USB 直连适配板**则 **2500 周期 0 失败**。
差异只在 `X5 → GH1.25 → 适配板 UART header` 这一段。

## 实测数字

| 路径 / 条件 | 失败率 | p95 延迟 |
|---|---|---|
| **PC —USB— 适配板**（跳线帽 B/USB 位） | **0.00%**（2500 周期，含 150 Hz 三倍速率） | 0.62 ms |
| X5 —GH1.25— 适配板（跳线帽 A/UART 位），3 id，单次尝试 | **29.33% / 29.70%**（两次独立 3000 周期） | — |
| 同上，3 id，带 4 次重试 | 13–28%（**漂移，不可当仪器**） | 21 ms |

**方向分解**（`servo_loss_decompose.py`，四条件交错采样）：

| 条件 | P(全中) | P(一个都没回) |
|---|---|---|
| N=1 `[7]` | 86.17% | 13.83% |
| N=2 `[7,8]` | 77.83% | 12.83% |
| N=3 `[7,8,9]` | 76.83% | 10.33% |
| ctl `[7,20,21]`（查询包同长，仅 1 个真实回包） | 84.17% | 15.83% |

- **发送方向（查询包）丢失约 10–13%** —— `P(一个都没回)` 与 id 数无关，因为查询包只有一个。
  这是上界；要钉死需要「写一次 + 大量重试读回」的方法（未做）
- **查询包长度不影响丢失率**：84.17% vs 86.17%，比值 0.977
- **回包丢失约 4%/个，但强相关**：「三个里只有一个回了」实测 36 次，独立预测 0.3 次（**差 120 倍**）
- **1→2 个回包的代价 9.7 个百分点，2→3 只有 1.3** —— 「有第二个回包」本身很贵

**回包模式**（300 次，按到达顺序）：`7,8,9` 72.7% / 无 11.7% / `8,9` 11 / `7,9` 10 / 单个 8,7,6 / `7,8` 5。
→ **单个回包随机消失、与位置无关**，菊花链（适配板→舵机1→2→3）**链尾没有劣势**。

**非平稳**：单次 60 s 运行内，每 2 秒一段的失败率在 **4% ↔ 56%** 游走。
局部近似独立（簇长 1.52 vs 独立 1.45），但那个 p 自己在漂。

**为什么重试没用**：单次事务失败约 23%，若重试独立，4 次后应为 0.23⁴ = **0.28%**；
实测端到端 17–28%。**差两个数量级就是相关性的大小** ——「突发内相关 + 时间相关」两层叠加。

## ⚠️ 调制源不是「CPU 忙」

第一版这一节里还有三行「加热后停掉负载」「+ 6 个 burner 到 96% CPU」的数据，**已删除：
那次实验的 `kill $BURN` 用了 `jobs -p`，在 busybox `sh` 下没拿到子 shell 的 pid，
6 个 CPU burner 一直跑了近一小时，把那之后的每一次测量都污染了。**判据是 `ps -eLo pcpu=,comm=`
里出现连号的 `sh` 各占约 74%，而 `load` 与各进程 CPU 之和对不上。

去掉污染后的对照反而给出更强的结论：

| | CPU | 失败率 |
|---|---|---|
| app 全跑（干净） | 57% | 19.07% |
| app + 6 个 CPU burner | 96% | 17.77% |

**多烧 39 个百分点的 CPU 没有让丢包变差**（差异在噪声内）。所以调制它的不是 ALU 占用，
而是 app 带来的**相机数据流 / DDS 传输 / 中断负载 / DDR 流量**。这与「UART 中断被 MIPI/ISP/BPU
中断延迟」和「DDR 带宽争用」两个机制假设吻合，与「CPU 抢占」不吻合。

| 2 | 59.1 °C | 9.50% |

| 拟合 | 斜率 | r | 95% CI |
|---|---|---|---|

## 🔴 冷却不是解药（实测否定）

**断电半小时、最冷的一轮 56.4 °C 仍有 8.37%，比前一天 67.6 °C 时测到的 6.73% 还高 1.64 个
百分点。** 低 11 °C 反而更差。散热改造不能指望解决这个问题。

## app 负载的独立贡献：约 +1.4 ~ +1.8 个百分点

用上面的空载拟合去预测 app 负载点，差值就是温度解释不掉的部分：

| 条件 | 温度 | 空载曲线预测 | 实测 | 差 |
|---|---|---|---|---|
| app 全跑 | 75.6 °C | 13.97% | 15.73% | **+1.76** |
| app 全跑（另一次） | 89.0 °C | 17.72% | 19.07% | **+1.35** |

两次独立测量一致，所以这个量比温度斜率更可重复。但注意 **它小于 4.17 个百分点的运行间漂移**，
所以严格说仍在噪声内，只是两次符号和量级都对得上。

⚠️ **本节推翻了本文档上一版的说法**。上一版写「6.73% → 19.07% 是 2.8 倍，归因于 app 负载，
温度不是主因」。分解后：那 12.3 个百分点里，温度（21.4 °C × 0.28）约 6.0、app 约 1.4，
**剩下约 5 个百分点是运行间漂移，无法归因**。上一版把漂移和温度都算进了 app 的账上。

**不是用户态调度抢占**：交错重测 `chrt -f 80` vs 普通，得 16.87 / 27.27 vs 24.53 / 20.87 ——
两个 fifo 之间的差异比组间差异还大，**无效**。（2026-08-06 那次 `chrt` 是空载下测的，
本来就没有抢占可躲，那次「无差异」没有判别力。此次虽在 burner 污染期内，但它是交错对照，
相对结论不受影响。）

**实用推论**：降低 app 的数据流开销会顺带降低总线丢包率；单纯省 CPU 周期不会。
反过来，任何在负载下测的总线数字都不能和空载的比。

### 混淆项审计（这是这个实验能站住的原因）

| 项 | 插着 | 拔掉 | 判断 |
|---|---|---|---|
| 温度 | 82.5 °C | 82.2 °C | 匹配。按 +0.28 %/°C 只能解释 0.08 点 |
| CPU | 37.7% | 38.2% | 匹配（拔掉的还略高） |
| `usb0` 流量 | 1.4 kB/s | 0 | 相机管线本身是 MB/s 量级，差三个数量级 |
| `dwc3` 中断 | 4.4/s | 0 | 绝对值太小，不可能造成 2.7 倍 |
| `ttyS3` 中断 | 97/s | 108/s | 拔掉时**更多** —— 因为回包丢得少，收到的字节更多。自洽 |
| 机械扰动 | — | — | 拔的是 PC 端，GH1.25 没被碰；且 8/8 翻转排除一次性沉降 |

**内部对照**：第 48 轮起 app 的 CPU 有一个与 USB 无关的台阶（33% → 41%）。分层看
前段 USB 21.49% / NOUSB 7.97%，后段 USB 22.53% / NOUSB 8.17% —— **CPU 变了 8 个点，
USB 的 14 点落差一动不动**。这第三次独立确认了「CPU 占用不是调制源」。

### 顺带解释了三个悬案

1. **「冷却不是解药」**：散热改造在跟一个 14 点的 USB 贡献较劲，6 点的温度效应当然看不出来
2. **「运行间漂移 4.17 点」**：漂移几乎只存在于插着 USB 的条件（相位 sd 1.07）；
   拔掉后 sd 只有 **0.17**，极差 0.40 点。**这条总线在没有调试线时是相当稳定的**
3. **空载 vs 满载的 2.8 倍**：空载（只 `insight_full`，USB 插着）约 10%，
   满载 + USB 插着 22%，满载 + 拔掉 8.1% → 看起来是**交互项**：
   app 活动产生扰动，USB 线提供把它耦合到 UART 参考电平上的路径，**缺一个都不显著**。
   ⚠️ 四格里缺「空载 + 拔掉」这一格，所以交互的说法还没闭合

### 机制还没定，但接地/共模的方向被大幅加强

GH1.25 只有 TX/RX/GND/12V，而**那个 12V 就是相机的供电** —— 相机整机的回流电流和 UART 的
参考电平共用一根细地线。插上 USB 又把相机地接到笔记本地。**拔掉一条地路径就让丢包降到 1/3**，
说明地/共模是活变量。这也是所有假设里唯一能自然产出「字节全好、`oe/fe/pe` 全零、整包消失」
的一个：地一抖，接收端把线看成恒定高（空闲），没有起始位 → 没字节也没错误。

**但具体是哪条耦合路径没定**，至少三个候选没分开：笔记本电源适配器的 Y 电容共模泄漏电流、
USB 线当天线、USB PHY 自身的开关电流。区分它们的三个实验都是零成本的，见「还没做 / 待定」。

### λ 是可加的 —— 三个独立噪声源

| 条件 | 失败率 | λ（事务 350 µs） |
|---|---|---|
| USB 插 + 充电器插 | 22.2 ~ 23.7% | 719 ~ 771 /s |
| USB 插 + 充电器拔 | **12.5%** | 382 /s |
| USB 拔（笔记本完全断开） | **8.1%** | 242 /s |

| 噪声源 | λ | 占比 | 百分点 |
|---|---|---|---|
| **笔记本市电适配器** | 389/s | **50%** | +11.1 |
| **USB 线本身**（笔记本用电池时仍在的耦合） | 140/s | 18% | +4.4 |
| 板子自己（GH1.25 + app + 温度） | 242/s | 31% | 8.1 底子 |

**242 + 140 + 389 = 771，严格相加** —— 正是「多个互相独立的随机破坏事件源」该有的行为
（泊松速率可加）。「USB 拔 + 充电器拔」这一格不需要测：USB 一拔笔记本在电气上完全不在链路里。

### ⚠️ 机制：不要照抄「Y 电容浮地」那套说法

本文档第一版写的是「两脚适配器把机壳悬在半个市电电压上」。**这台笔记本是三脚的**，
Class I 适配器的 DC 输出地接 PE，Y 电容电流走 初级→次级→PE，**不经 USB 出去** —— 那条路被短掉了。
效应仍是实测的（5/5 翻转 + CPU 匹配对），所以要换的是机制不是结论。三脚接地造出的是
**真正的地环路**：`相机地 → USB 地 → 笔记本机壳 → PE → 建筑地`，而机器人是电池浮地的，
这条路径与 USB 线、电源线、建筑布线围出很大的环路面积。

**一个有力旁证**：`AC=1` 期间 `BAT0` 全程 `Not charging`（电池满），**DC 侧几乎没有电流**，
却仍然差 11 个点 → **不是充电电流的传导噪声，是「接地这件事本身」**。

⚠️ 但「三脚插头」**不等于**「DC 输出地真的连到 PE」：很多适配器的地脚只接外壳甚至内部悬空；
插排/墙插的地线也可能没接。**万用表电阻档量「笔记本 USB 金属壳 ↔ 插头地脚」10 秒可验** ——
通则是地环路，不通则第一版的浮地说法反而成立。**两种情况修法相同，所以这个测量只影响文档写法。**

### 🔴 顺带纠正一个一直在误导判断的说法

「USB 直连适配板 0.00%」那次对照里，**`X5 → GH1.25 → 适配板 UART header` 这一整段根本不在链路里**
—— CH343 直接在适配板上驱动舵机总线。所以那个 0.00% **从来不是**「同样的 UART 换成走 USB 就没事」，
而是「那段 UART 压根不存在」。此前把它当成「USB 接口优于 UART 接口」的证据是过度解读。

**为什么加一层相机就出问题，答案不是「多一层器件」，是信号参考被劈成了两半：**

| | USB 直连适配板 | 经相机 |
|---|---|---|
| UART 发端与收端 | **同一块 PCB、同一地平面** | 两块 PCB，靠 GH1.25 一根细地线 |
| 「地电位差」这个自由度 | **物理上不存在** | 存在 |
| UART 参考线是否承载别人的电源回流 | 否 | **是**（相机整机 12V 回流，0.5~1 A 带瞬变） |
| PE 接在哪个节点 | **就接在 UART 参考平面上** | 接在**相机端** |
| 接地电流怎么回电池 | 直接从适配板地回去，不碰任何信号参考 | **只能穿过 GH1.25 地线** → 串在信号参考上 |

→ 噪声注入点从「压在参考平面上」变成「**串在参考导体里**」。这是最坏的一种拓扑，
而且那根导体同时在干「电源回流」和「信号参考」两件事。

### 已实测 vs 仍是假设（别混用）

- **已实测**：USB 线值 14.1 点（8/8 翻转）、充电器值 11.1 点（5/5 翻转）、λ 三项可加
- **未实测**：真实的地噪声电压。3.3 V 逻辑要误判需约 1.5 V 参考偏移；GH1.25 约 0.07 Ω / 300 nH，
  靠 `L·di/dt` 凑 1.5 V 需要 **5 A/µs**，在边界上，不能断言够。也不排除
  **USB 线辐射到不带屏蔽的舵机 3pin 线缆**这条不需要伏级地电流的路径
- 结论的强度分级：**「拓扑很脆弱」「哪个变量值多少点」是实测的；「具体耦合物理」是假设**

## 🔑 暴露时间模型（2026-08-07，目前对这个故障最好的理解）

**失败概率正比于事务占用总线的时间。** 同一波特率、同温度、相邻时间，只改事务长度：

| `--ids` | 线上字节 | @1 M 占用 | 失败率 |
|---|---|---|---|
| `7` | 17 | 170 µs | **8.20%** |
| `7,8` | 26 | 260 µs | **11.90%** |
| `7,8,9` | 35 | 350 µs | **15.47%** |

```
fail% = 1.36 + 0.4039 x (线上字节)        r = 0.9999
      = 1.36% 固定 + 40.4% 每 1000 µs 总线占用
```

**独立验证**：把舵机 7 改成 500 kbaud（同样 17 字节，但占用时间翻倍 = 等效 34 字节），
模型预测 15.09%，**实测 17.03%**，差 1.94 个百分点 —— 在这条总线的漂移范围内。

若把失败看成泊松过程 `P = 1 - exp(-λt)`，则 **λ ≈ 404 次/秒，平均每 2.5 ms 一次干扰事件**。

### 三个直接推论

1. **降波特率是反方向的**。位时间翻倍并不会改善时序余量，只会让事务在总线上待更久 ->
   实测 9.60% / 8.53% -> **17.03%**，几乎翻倍。**已证伪，别再试。**
2. **`sync_read` 已是最优**，不要「改成逐个单读」：一次读三个成功率 84.5%，
   拆成三次单读全部成功只有 77.3%（总线占用 350 µs vs 510 µs）。
3. **软件侧没有剩余杠杆**。`Present_Position` 已是 2 字节的最小读，三个轮子都必须读，
   查询包长度固定。当前实现就在这个模型的最优点上。

### 它对机制假设的影响

这条结果**削弱了「TxEn 方向控制时序余量不足」**那条主假设：如果问题出在信号完整性或换向
时刻，位时间翻倍应当**改善**，实测却成正比恶化。数据更支持
**「总线上以约 400 Hz 的密度随机发生破坏性事件，事务待得越久越容易被击中」**，
这与 DDR 争用 / 中断延迟 / 电源纹波尖峰相容，与边沿质量不相容。

## 测量方法论（踩过的坑）

1. **跨时间 A/B 一律不可信** —— 同一条命令、同样 50 Hz 500 周期，一小时内测出 25.2% 和 13.4%，
   而电压温度未变。对照**必须在同一次运行内交错采样**（`servo_loss_decompose.py` 按此写）
2. **仪器要用「3000 周期单次尝试失败率」**（复现性 29.33 / 29.70），
   **不要用带重试的数字**（13–28% 乱漂）
3. `servo_raw_dump.py` 60~100 次试验的波动有 25 个百分点，分辨不出小于 20 点的差异
4. **测量前必须停 `wheel_odometry_node`**，否则 pyserial 报
   `device reports readiness to read but returned no data (multiple access on port?)`。
   ⚠️ 停它的脚本**必须写成文件再执行**，不能用 ssh 一行命令：`ps` 会匹配到调用者自己的命令串，
   而命令串里只要出现过节点名（比如中文 `echo` 里），`kill` 就会杀掉自己的 shell。2026-08-07 踩过
5. **停掉 `wheel_odometry_node` 会同时切断位姿源** → `bridge` 不再出关键帧 → `map_node` 转 idle。
   所以「满载 + 测总线」有结构性上限：ttyS3 被位姿源独占，两者不可兼得
6. **窄范围的相关系数不能用来证伪**（见「已证伪」表里被推翻的那条）
7. **不要拿几个打印样本当分布** —— 「回包是前缀式截断」这个错误结论就是这么来的
8. 🔴 **起了后台负载进程，必须验证它真的被杀掉了**。`( while :; do :; done ) &` 配 `jobs -p` +
   `kill` 在 busybox `sh` 下静默失效，6 个 burner 跑了近一小时污染了后续全部测量。
   判据：`ps -eLo pcpu=,comm=` 找异常占用，以及 **`load` 与各进程 CPU 之和对不上**
   （当时 load 17.9 而进程 CPU 合计只有 367%/800%）。测完 `sleep` 一下再复查一次
9. 单点计时测波特率会被 **约 25 ms 的 tcdrain 调度唤醒延迟**污染（读出 −25%）。
   必须用**斜率法**：同一速率测多个字节数，用 Δbits/Δt 拟合，固定开销落到截距里

## 板上的 UART 拓扑

只有**三个**真实 UART（`/dev/ttyS1/2/4/6/7` 节点存在但 `uart:unknown port:00000000`）：

| 端口 | SoC 引脚 | 用途 |
|---|---|---|
| `ttyS0` | `dsp_uart0_txd/rxd` | 内核控制台 `console=ttyS0,921600n8`，被 agetty 占用 |
| `ttyS3` | `lsio_uart3_tx/rx` | **舵机总线**（8pin 接口） |
| `ttyS5` | **`lsio_spi4_sclk` / `lsio_spi4_ssn`**（复用成 `uart5grp`） | 空闲。注意引脚丝印是 SPI4 |
| 未启用 | `lsio_uart1/2/4/7_tx/rx` | 全被配成 GPIO（`gpiochip4`），**无 ttyS 设备** |

引脚映射从 `/sys/kernel/debug/pinctrl/*/pinmux-pins` 读，可直接查。
**2026-08-06 试过换到另一个机壳外接口，三个 UART 全部环回无回声**（`tx +36, rx +0`），
说明那个接口不通向任何已实例化的 UART —— 很可能走的是上表最后一行那些 GPIO 引脚。
要用它必须改设备树 / pinctrl 重新 mux，属于改相机系统配置。

## 由此暴露的两个代码隐患（与总线是不同的问题，必须单独修）

### 1. 读失败会连带吃掉刹车指令 🔴
`wheel_odometry_node._tick()` 在同一个 50 Hz 回调里**先读后写**，而 `_drive_wheels()` 在**最末尾**
（`:389-390`）—— 读失败的 `return`（`:364`）和 `body_delta is None` 的 `return`（`:376`）**都会跳过它**。

- 真实指令缺失率 = 读失败 17–28% **叠加** 发送丢包 10–13%
- **`/cmd_vel` 超时后的看门狗刹车也走 `_drive_wheels()`，同样被跳过** → 坏时间窗里连续多拍收不到刹车

修法：`_drive_wheels()` 挪到读之前，或放进 `finally`。

### 2. 退出时的停车指令只发一次 🔴
`destroy_node()` 的 `sync_write("Goal_Velocity", 0)` 无 ack、无重试。约 10–13% 概率丢失
→ 运动中停节点大约每八到十次一次「轮子继续转而控制器已经没了」。
修法：重发 N 次 + 读回 `Goal_Velocity` 确认为 0。

### 附带：启动失败不是电源问题
`configure_velocity_mode` 的 `write("Torque_Enable")` 只重试 3 次，撞进高失败率时段整个节点退出
→ **完全没有动力输出**。2026-08-06 复现两次，循环重启才起来。历史上曾被误记为电源问题。

## ⚠️ 判断故障时的关键不对称

`Goal_Velocity` 是**绝对设定值**，舵机保持到收到新值为止。所以**总线丢包只会让车「多走」，
永远不会让车「停」**（「该动时没动」最多晚一拍）。

→ **看到车停住，就一定是有人主动发了 0，不要往总线上找。**
导航中途停车已定案为规划延迟，见 `map_node` / `cmd_vel_control` 日志。

## 数据不全时的处理

`_tick()` 调 `sync_read` **不传 `allow_partial`**（默认 False），一个舵机没回就抛异常 →
记一次 `read_failures` 然后 `return`。**部分数据从不被使用，整拍丢弃。**
这是对的：位置积分跳过一拍只是让下次位置差跨更长间隔，**积分结果仍正确**（只要轮子没转过半圈）
→ 损失的是发布率和时间分辨率，**不是轨迹精度**。

**USB 隔离器是唯一能同时拿掉两项（11.1 + 4.4 = 15.5 点）又保留网络的方案**，
而且不管机制是地环路、浮地泄漏还是辐射耦合，它都同时切断电流路径和共模连续性 ——
**机制之争不影响该买什么。**
