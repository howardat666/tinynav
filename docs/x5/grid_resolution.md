# 局部栅格分辨率：0.1 → 0.05 m 的完整账

> 2026-09-01。起因是两个现场问题：狭窄过道过不去、矮障碍识别不到被过滤。
> 结论：**单纯把分辨率减半是 8 倍代价，而且矮障碍反而更差；把框从 10 m 缩到 4 m 之后
> 三个维度都细化几乎免费。** 下面的内存数字全是板上/真地图实测。

## 1. 为什么单纯减半是 8 倍

栅格是三维的，而 z 层数是按**物理高度**定的（`planning_node.py:364` 的注释：栅格以相机
为中心只覆盖 ±0.5 m，`robot_z_top` 再大也会被栅格自己截断）。三个维度都翻 → 2³。

| 项（真地图 `map_night` 33×24×2.3 m） | 0.10 m 现状 | 0.05 m |
|---|---|---|
| 局部栅格格数 | 100×100×9 = **90,000** | 200×200×18 = **720,000** |
| 局部 2D EDT | 100×100 | 200×200（4×） |
| 全局地图格数 | 1.84 M | 14.72 M |
| 地图磁盘/常驻（occ+sdf，dense `.npy`） | 9.2 MB | 73.6 MB |
| 🔴 **建图 `_compute_sdf` 进程峰值（实测）** | **142 MB** | **755 MB** |
| 🔴 **A\* 每次调用的 6 个数组（30 B/格）** | **55 MB** | **442 MB** |
| A\* 实测进程峰值（同起终点） | 186 MB | 404 MB |
| 轨迹打分/碰撞（圆盘后是单点查表） | 3,410 次 | **不变** |

**板上 `MemAvailable` 603 MiB、无 swap。755 和 442 两项都过不去。**

## 2. 🔴 而且矮障碍会更差，不是更好

射到物体上的射线**总数与分辨率无关**，但 `occ_threshold` 和"连续两帧"是**按格**判的、
不跨格汇总。泊松模型锚在板上实测的 `step=5 → 单帧召回 70%`（⇒ 每格 λ=1.20）：

| | 每格 λ | 单帧检出/格 | 连续两帧/格 | 一个 0.1 m 障碍整体检出 |
|---|---|---|---|---|
| 0.1 m, step=5（现状） | 1.20 | 0.70 | 0.49 | 占 1 格 → **49%** |
| **0.05 m, step=5** | 0.30 | 0.26 | 0.068 | 占 4 格 → **24%** |
| 0.05 m, **step=2** | 1.88 | 0.85 | 0.72 | 占 4 格 → **99%** |

注意这个摊薄只打**大于一个格子**的物体。比格子小的（椅子腿、线缆）射线全落在一格里，
两种分辨率下 λ 相同；而墙比格子大得多，摊薄会让墙上出洞。

## 3. 收益只有两条，第一条的大头免费

| | 0.1 m | 0.05 m |
|---|---|---|
| **最矮可见障碍**（`min_wall_span_m` 保持 3 层抗噪） | 0.20 ~ 0.30 m | **0.10 ~ 0.15 m** |
| 过道量化损失 | ±0.05/侧 → 净宽预算吃 **0.100 m** | ±0.025/侧 → 0.050 m |

大头一个环境变量就能拿到：`TINYNAV_MIN_WALL_SPAN_M=0.1`（降到 2 层，最矮 0.10~0.20 m，
代价是抗噪层数 3→2）。

过道那 50 mm 更不值钱 —— 圆盘的过道净宽预算：

| 分项 | 占用 | 占预算 | 改的代价 |
|---|---|---|---|
| 碰撞半径 0.122×2 | 0.244 | 38% | 几何，不可改 |
| `comfort_margin` 0.1×2 | **0.200** | **31%** | **一个数，免费** |
| `safety_radius` 0.05×2 | **0.100** | **16%** | **一个数，免费** |
| **xy 量化** 0.05×2 | **0.100** | **16%** | 见上表 |
| 零代价通过 | **0.644 m** | | |
| 硬门限 | 0.444 m | | |

**两个免费的数一共 300 mm，比分辨率的 50 mm 大 6 倍。**

## 4. ✅ 正解：只改局部栅格，并把框从 10 m 缩到 4 m

两个栅格职责不同，而且代码上**已经解耦**：

| | 全局地图（`map_node`） | planning 局部栅格 |
|---|---|---|
| 来源 | 建图产物 `occupancy_grid.npy` + `sdf_map.npy` | 自己射线投影深度图，与全局地图无关 |
| 干什么 | A\* 出路线（bucket-0 = 距建图轨迹 <0.2 m，teach-and-repeat） | **避障** |
| 要 5 cm 吗 | **不要** | **要** |

```python
# planning_node.py
self.resolution  = 0.05
self.grid_shape  = (80, 80, 14)              # 4 x 4 x 0.70 m = 89,600 格 ≈ 现状的 1.0 倍
self.grid_offset = np.array([0.0, 0.0, 0.15])
# robot_config.py DIFFCAR_CONFIG.obstacle
min_wall_span_m = 0.10                        # 3 层，抗噪层数与今天相同
```

| | 现状 | 候选 |
|---|---|---|
| 栅格总格数 | 90,000 | **89,600**（1.00×） |
| 2D 平面格数 | 10,000 | **6,400**（0.64×，更便宜） |
| 全局地图 / 建图 / A\* | — | **完全不动** |

**2 m 半径够用**（三条独立理由都指向 2 m）：
1. 3 s 轨迹 @max_vx 0.5 = 1.5 m；反应距离 2.0 s × 0.5 = 1.0 m；前向探针 1.2 m；最远需求
   1.5 + 0.122 + 0.05 = 1.67 m < 2.0 m
2. 每格射线数 `≈ ((分辨率×f/step)/距离)²`，取 f=309.5：**0.05 m 在 2 m 处 ≈ 今天 0.1 m 在
   3 m 处**，而密度紧张的 2.5 m 以外已经被切掉 → **`step` 很可能不用从 5 加到 2**
3. CPU：见上表，反而更省

⚠️ **必须同时改重定心判据** —— 半径从 5 m 缩到 2 m，`roll_occupancy_grid` 会频繁得多。
⚠️ 第 2 条必须板上量（用 `step=2` 当参考真值测 1~2 m 的单帧占据召回），不能推。

## 5. OctoMap 为什么治不了我们的病

**存储从来不是瓶颈。** 实测 `map_night` 的 occ(uint8, 1.84 MB) + sdf(float32, 7.36 MB)
= 9.2 MB；`zlib` 还能压 **33×/4.4×**；占据体素只占 **1.63%**，稀疏存 int16×3 只要 0.18 MB。
瓶颈是**算法的临时数组** 755 MB / 442 MB，而 OctoMap 一个都不碰：

- `sdf_map` 是**到建图轨迹的欧氏距离场**（`build_map_node.py:489` seed 是 `odom_positions`），
  不是占据图。**OctoMap 不提供距离场** —— 对口的是 voxblox/nvblox，更重，且 nvblox 要
  CUDA 而 X5 只有 BPU。
- 局部栅格上 OctoMap 是**净退步**：89,600 格 dense 只有 717 KB、缓存友好，每周期全是向量化
  数组运算（`roll_occupancy_grid` / ×0.99 衰减 / 沿 z 的 any-max-min / 2D `distance_transform_edt`
  需要 dense 输入），在八叉树上全变成逐节点遍历；而八叉树每节点约 40 字节，在空闲/未知
  边界最密集的机器人周围剪枝效果最差。
- 显式 unknown 我们**已经有**：`occupancy_grid` 就是 0/1/2 三态（实测 77.5% / 20.8% / 1.63%），
  只是 A\* 里 `占据!=2 就可通行` 没用它 —— 改一行判据的事。
- 部署更堵：板上**无 pip**，Python 装在地平线的安装树里；C++ 库要 aarch64 交叉编译，或者
  起 `octomap_server` 多一个进程多一路 DDS 流量（而 CPU 和 DDS 正是当前的硬约束）。
  比已经被否决的纯 Python `tyro` 难一个量级。

**什么时候它才对**：地图大到几百米量级（整栋楼）、或真的需要多分辨率查询。33×24 m 的地图
dense @0.1 只有 9.2 MB，离那个门槛还很远。

## 6. 执行顺序

| | 动作 | 成本 |
|---|---|---|
| 0 | **量一下漏掉的障碍到底多高** —— 拿 0.1/0.15/0.2/0.3 m 的箱子在固定距离摆一排，看 `obstacle_mask` 出不出格子 | 半小时，**是上面全部讨论的前提** |
| 1 | `TINYNAV_MIN_WALL_SPAN_M=0.1` 跑一趟 | 一个环境变量 |
| 2 | 复核 `comfort_margin` / `safety_radius` | 两个数 |
| 3 | 局部栅格 0.05 m + 4 m 框 + 重定心判据 | 几小时 + 一轮板上验证 |
| — | 全局地图 | **保持 0.1 m** |

第 0 步可能直接把第 3 步否掉：如果漏的都是 0.3 m 以上的东西，那是射线召回/连续两帧的问题，
分辨率完全无用（见第 2 节）。

## 7. ✅ 已实施并验证（2026-09-01 晚）

**上面第 3 节说「过道那 50 mm 不值钱，两个免费的数大 6 倍」—— 这个结论要修正。**
现场出现了一个可复现的场景，分辨率是**唯一**能解的：

### 7.1 触发场景

椅子之间物理净宽 0.50 m（机体系 0.05 m 精度实测），车需要 0.344 m —— 本该能过。
但**过道相对栅格轴斜 54°**，0.1 m 轴对齐栅格对斜过道每侧最多吃
`0.1×(|cos54°|+|sin54°|) = 0.140 m`，净宽被栅格化成 **0.30 m** 就判死了。

第 3 节算的是「±0.05/侧 → 0.100 m」，那是**过道正对栅格轴**的最好情况。
🔴 **斜过道是 1.4 倍，而现实里过道不会替你对齐栅格。**

同一帧用原始深度独立重建（绕开 occupancy/矮障碍/ESDF 全部逻辑），逐点得到一样的
0.45 / 0.30 / 0.55 m —— **地图是忠实的，是分辨率不够**。这个对比是判断"感知有没有虚标"
的正路：40 格里 37 格一致，地图只多标 3 格、漏标 10 格。

### 7.2 实施

```python
# planning_node.py
self.grid_shape = (80, 80, 14)     # 4 x 4 x 0.70 m
self.resolution = 0.05
self.grid_offset = np.array([0.0, 0.0, 0.15])
# robot_config.py DIFFCAR_CONFIG
obstacle=ObstacleConfig(..., min_wall_span_m=0.10)
# env.sh
TINYNAV_LOW_OBS_MIN_PTS=2
```

🔴 **两个必须同时改的耦合参数**，漏一个就反向翻车：

| 参数 | 为什么 |
|---|---|
| `min_wall_span_m` 0.2 → **0.10** | `z_span = (occ_high−occ_low)×resolution`。0.2 m 在 0.1 m 下是 3 层，0.05 m 下要 **5 层** —— 每层各自要过 `occ_threshold`+连续两帧，要 5 层比 3 层难得多，墙会更容易出洞。0.10 保持「3 层」抗噪不变 |
| `low_obs_min_pts` 6 → **2** | 每格点数 ∝ `(resolution×f/step/d)²`，格子面积变 1/4 → 点数掉 4 倍。按 (0.05, step3) 折算是原始基线 (0.1, step5) 的 0.69 倍，所以回到 2 正好等效 |

几何自检（务必跑）：`origin=[-2,-2,-0.20]`、`center−robot=[0,0,0]`、band 用掉 12/14 层、
总格数 89,600 vs 旧 90,000。

### 7.3 实测结果：净宽 +0.10 m，而性能**变好**

同一位置、车没动过：

| 前方 | 0.1 m | **0.05 m** |
|---|---|---|
| 0.4 m | 0.45 🟡 | 0.45 🟡 |
| **0.5 m（瓶颈）** | **0.30 🔴** | **0.40 🟡 能过** |
| 0.6 m | 0.55 ✅ | 0.55 ✅ |

| | `0.1m step5` | `0.1m step3` | **`0.05m step3` 4m 框** |
|---|---|---|---|
| 处理周期 p50 | 0.23 s | **0.40 s**(p90 0.77) | **0.197 s**(p90 0.227) |
| 丢帧 | — | 13 次 | **0** |
| planning CPU | 62% | ~100% | **78%** |

**能跟上全部 4.84 Hz 的深度输入，一帧不丢。** 变便宜的来源是框缩小：3D 总格数 1.00×，
但 2D 平面 10,000 → 6,400（EDT 便宜 0.64×），且每条射线穿过的格子数变少。

⚠️ 仍未量：导航时的 `stamp_lag`（要有 POI 目标才打），和实际过这个路口。
